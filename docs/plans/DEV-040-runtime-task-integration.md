# DEV-040：统一调度与 Runtime 纹理异步加载开发计划

## 状态与职责

实施中；调度核心已进入桌面与浏览器验证。本文描述开发依赖、源码落点和阶段完成条件；版本范围、里程碑编号及
发布门禁以 [VER-040](VER-040-0.40.0-cooperative-scheduling.md) 为唯一权威来源。
执行模式和资源事务分别遵循 [ADR-047](../decisions/ADR-047-cooperative-task-execution.md) 与
[ADR-048](../decisions/ADR-048-runtime-asset-preparation.md)。以下接口及数据模型均为计划，不是当前 API。

沿用 `feat/0.40-cooperative-scheduling` 分支。每组验证通过的连贯改动本地提交；完整版本达到
可评审状态后形成一个 PR。2026-09-25 用户已授权本版实现、提交、推送、PR、合并及版本发布完整闭环。

## A：先固定契约与失败语义（M-256）

1. 将 0.39 调度测试分为共用任务语义和真实线程竞争两组，明确协作模式不能依赖阻塞屏障。
2. 确定驱动线程校验、零预算、延迟时钟、递归驱动拒绝、非阻塞回收及桌面等待接口。
3. 同时核对纹理同步路径、缓存租约、RID 引用、GPU 上传失败回传及 Asset IPC 超时规则。
   写出纹理候选准备到发布的状态转换，确认“已应用”所需的后端确认。
4. 确定内部宿主注入桥；Editor 与其 Application 共享宿主执行资源，独立 Runtime 自己持有实例。
   未启用异步加载的公共同步 Application 不无条件创建另一线程池。

完成条件：错误语义、所有权、请求回执和后端确认方案可测试。若 Granit 缺少必要通用确认能力，
先提出最小上游需求及验收，由用户处理；此依赖解决前不把纹理事务阶段标为完成。

## B：实现两种执行模式（M-257～M-258）

1. 提取共用的接受、就绪选择、终态和结果回收逻辑；保持容量、串行取消及依赖失效测试通过。
2. 桌面线程池调用共用逻辑，协作驱动按数量/时间预算执行就绪任务；任务体在调度锁外执行。
3. 引入请求关闭与非阻塞收尾，取消远期任务不等待截止时间；对象析构前验证无运行中的捕获。
4. 分离无线程构建，明确模式不可用时的错误，不以失败后自动退回另一模式掩盖部署问题。

完成条件：共用契约在协作模式和多种线程数下通过，递归驱动与自等待不会挂死。

## C：迁移现有服务及最小浏览器宿主（M-259～M-260）

Editor 在不持有服务锁的帧阶段驱动任务，继续单独消费回执。两资产服务使用一致的作用域收尾，
保留事务、保存竞态和导出暂停回归；协作模式只承诺任务之间窗口能前进。

最小 Web 宿主只链接调度模块，明确事件循环接管后的对象存活期。固定 SDK、异常配置及浏览器版本，
在浏览器验证跨回调执行、延迟、取消与关闭，不仅运行编译或 Node 测试。

完成条件：消费者模式回归和浏览器实测分别有独立结果。Runtime 接入可在 B 完成后开展，
但最小浏览器验证仍为发布门禁，不将桌面 Runtime 的验证充当 Web 验证。

## D：纹理 CPU 准备与 Runtime 接入（M-261）

1. 从同步 acquire_texture 提取纯准备逻辑，覆盖当前 PNG、KTX2 和运行纹理封装的受支持路径。
   现有同步获取复用相同解析，保持诊断、色彩空间、尺寸及 mip 验证结果。
2. 请求拥有规范化 URI、读取上下文、会话/宿主代次、目标 generation、请求序号和批次修订。
   候选拥有像素或编码 payload、描述及一致性检查信息，不持有可变缓存或后端原生对象。
3. 读取与解码使用任务作用域。描述和源文件发生变化时拒绝过期准备或有界重试；禁止无限自动重试。
4. Runtime 增加显式内部纹理加载入口，以同一服务处理首次加载和纹理热更新，保持同步场景入口兼容。
5. 明确并实现输入、解码输出、暂存候选的字节限额，检查尺寸乘法溢出；任务容量满和字节限额满均可诊断。

完成条件：两模式均产生相同有效候选及错误；线程池模式的大文件读取/CPU 解码不在主线程执行，
协作模式明确运行于宿主线程。准备阶段可独立测试，无 GPU 和可变缓存访问。

## E：提交、修订和关闭（M-262）

计划状态流为：接受请求 → 排队 → 准备 → 待提交 → 提交/后端确认 → 应用成功或失败。
取消和过期是明确终态；具体枚举与现有协议映射在 A 阶段收口。

- 主线程校验所有者、资源 generation、修订及批次完整性，再取得提交许可；GPU 操作只进入渲染执行器。
- 建立候选映射和必要依赖，所需确认失败时完整清理候选，旧映射及租约继续有效。
- 未取得提交许可的请求可取消，已取得许可的请求完成或回滚；卸载/重建不能被迟到的完成回执撤销。
- 连续修订采用保序批次或完整覆盖合并。测试不同 URI 的 A、B 修订，避免 B 先完成就将 A 丢弃。
- 纯纹理批次原子应用；混合批次保持现有完整事务，明确其同步成本，不把其中纹理提前发布。
- 关闭先停止接收，再取消未提交准备，处理已提交操作与终态，最后释放服务和调度器。
  收尾不依赖已经销毁的 UI 消费者；浏览器路径不得阻塞等待事件循环回调。

完成条件：首次失败无泄漏，重载失败保留旧画面；取消、过期、卸载、断连与关闭注入测试通过，
线程池与协作模式的业务终态一致。记录已有文件系统事务边界，不宣称跨进程原子读隔离。

## F：联动、测量与发布准备（M-263～M-264）

1. 拆分 runtime_asset_reloader 的接收与完成阶段，保留请求关联标识；Editor 只在真实完成后标记已应用。
   核对已有 IPC 排队、超时、重试、重连及待回复数量限制，避免长任务重复执行和提前成功。
2. 用真实纹理在运行中切换版本，覆盖错误文件后恢复和多个修订；确认可见更新及旧资源安全退役。
3. 在加载期间执行相机、连续 resize、最小化恢复和退出，记录真实渲染帧时、准备/提交/上传耗时、
   排队深度和候选字节峰值。分开记录重复 Release 样本、Debug 与协作模式的长任务停顿。
4. 先建立同步基线与阶段耗时，再确定可解释的回归判据。不可用单次最大值承诺固定帧率；
   必须有线程归属断言和事件顺序证据证明读取/解码已移出线程池模式的主线程。
5. 更新 Guide 和验收 Record，核对公开描述与实测范围。完整桌面及浏览器门禁通过后才进入发布准备，
   未验证的平台、混合批次同步路径和剩余主线程工作在发布说明中明确列出。

## 开发中必须收口的参数

线程数量与后台并发限额、任务与字节预算、驱动时间预算、提交/上传预算，以及 IPC 超时和请求合并策略
均须基于实际输入收口。首版沿用内部接口，不预先设计公共异步 ABI；如确实需要改变公共接口或
扩展上游后端能力，应先更新对应 ADR、兼容性评估与验收范围。
