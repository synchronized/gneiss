# VER-051：0.51.0 源码架构与模块边界收敛

## 状态

2026-10-15，方案已确认，规划完成、实现待开始。基线为已发布 0.50.0。
原视口性能计划迁移为 [0.52 候选](VER-052-0.52.0-editor-render-performance.md)，任务编号保留。
实施顺序与验收见 [DEV-051](DEV-051-architecture-boundaries.md)，接口边界决策见
[ADR-062](../decisions/ADR-062-internal-cpp-and-sdk-boundaries.md)。本次不包含远端发布授权。

## 背景与目标

当前目录已有分层，但功能归属、跨模块调用与资源关闭顺序仍需要进一步收敛。
本版目标：从目录找到功能，从接口判断依赖，从对象确认所有权与销毁顺序。
必须交付实际边界调整、可执行依赖约束与行为回归，不能只搬目录或增加设计图。

## 范围

1. 审计实际模块职责和依赖，形成当前/目标依赖图、对象所有权与生命周期图、关键流程说明。
2. 收敛 Application：保留装配、启动、主循环与生命周期协调，将具体业务状态及实现细节归入对应模块。
3. 优先贯通打开场景、资产准备、候选构造、激活、渲染使用、取消/切换与退出的完整链路。
4. 明确内部 C++ 与外部 C ABI/RAII 包装边界，消除内部不必要的往返转换，不创建第二套运行时。
5. 整理目录、私有头、CMake 源码归属与依赖可见性，增加禁止依赖的反例检查。
6. 整理 Apps 与 Editor 内部职责，补充源码阅读入口、功能归属和关闭顺序说明。

## 已确认原则

- 顶层 apps 保留程序入口、宿主装配及平台接线；不要求入口机械缩减为只有 main。
- 内部模块使用 C++，独立 SDK 和动态游戏模块保留 C ABI；外部 C++ 包装完整覆盖已公开能力。
- 同源码构建宿主只依赖明确的内部模块接口，不能随意包含私有实现头。
- Scene Tree、ECS、Service/RID 与后端依赖方向继续遵守项目约束，第三方类型不泄漏到普通公共接口。
- 最终仍可交付单一 Engine 库，内部模块化不要求每个模块成为 DLL。
- 先明确职责与所有权，再确定详细目录迁移表；不预先为每个步骤新增 Service/Manager。
- 默认保留既有对外契约；必要接口变化须单独评估 C ABI、C++ 包装、示例、消费者与迁移成本。

## 非目标

不开发插件，不整理或发布 Editor 公共 API，不新增 LOD、流送或调度框架，不默认升级 Granit。
不重写整个引擎，不承诺通过架构整理解决所有卡顿，不将内部每个类都映射为 C API。
不改写 0.50 的发布事实、失败样本和冻结门槛。

## 交付与完成标准

- 主要模块有唯一职责说明和允许依赖；构建/检查能够拒绝越界引用。
- 首个完整加载链路完成代码调整，Application 的业务细节有明确归属。
- 关键资源的拥有、借用、线程与关闭关系可从类型、接口及测试确认。
- 加载、取消、失败保留旧场景、重试、切换、退出及对外 SDK 回归通过。
- 重构前后采用同口径性能对照；新增回归的判定方法在实现前冻结。
- 文档区分当前实现和目标，不以文件数量或文件长度作为架构改善的唯一标准。

## 遗留与风险

0.50 的性能超标和验收缺口继续以 [版本归档](../versions/0.50.0.md) 为权威入口。
本版回归会覆盖所改路径，但不默认承诺消除全部历史问题；若发现生命周期缺陷，先记录并优先修复。
新增回归与原有超标须分开报告，不能将所有失败归为历史问题。
详细模块划分、加载协调部分归属及同步回退范围在 M-329 审计后确定。
