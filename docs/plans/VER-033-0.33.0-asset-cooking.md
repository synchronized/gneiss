# VER-033：0.33.0 资产构建与发布优化

## 状态

- 状态：已完成
- 目标版本：0.33.0
- 优先级：P0
- 路线图阶段：游戏交付工作流

## 背景与目标

0.32.0 已能生成可验证、可归档的运行包，但仍直接收集工程资产，缺少从源资产到目标平台运行资产的
统一构建阶段，也无法可靠复用未变化的产物或裁剪 Shipping 未引用内容。0.33.0 将建立确定性的资产
构建图、内容寻址缓存和发布裁剪闭环，使 Development 与 Shipping 包消费经过验证的运行资产。

本版本同时验证 KTX2/Basis Universal 的工具链适用性，但不预先把文件格式解析职责下沉到 Granit。

## 非目标

- 不在本版本完成所有纹理压缩格式、模型格式或 Shader 语言的生产级覆盖。
- 不实现分布式构建、远端缓存、资产服务器、增量补丁或在线内容下载。
- 不实现运行时动态转码，也不让 Runtime 读取 PNG、JPEG 等源资产作为正式发布路径。
- 不把 Gneiss 的资产格式、依赖图、导入设置或 KTX2 容器解析放入 Granit。
- 不以减小体积为由移除启动失败和致命故障诊断。

## 已确认决策

- 资产构建采用“源资产 + 导入设置 + 处理器版本 + 目标平台/配置”生成确定性缓存键；缓存命中不得依赖
  文件时间戳。
- 首版缓存位于工程 `build/.gneiss-cache`，按平台、架构和缓存键隔离；写入使用临时文件及原子提交，
  不共享用户级缓存，也不进入版本控制或发布包。
- 构建图显式记录输入、处理器、派生产物和资产依赖；处理器通过统一接口注册，不把格式分支集中到
  一个大型调度函数。
- Development 构建保留必要的来源映射和诊断元数据；Shipping 从初始场景及显式保留项计算可达资产，
  只收集可达运行产物。
- 发布清单记录最终运行产物；源资产、导入缓存、绝对路径和中间调试文件不进入 Shipping 包。
- KTX2/Basis Universal 首先作为 Gneiss 工具链 Spike：比较 KTX-Software 与 Basis Universal，验证
  Mip、sRGB、透明度、GPU 压缩格式和跨平台构建；结论稳定后再决定 Runtime 容器。
- Granit 继续只接收 GPU 纹理描述和 Mip/层数据。仅当其缺少可复用的压缩格式、Pitch、数组层、
  Cube 或能力查询契约时，整理最小 Granit PR 建议交由用户提交。
- Editor 和 `gneiss_project` 复用同一资产构建服务；UI 只负责配置、进度、缓存统计和错误呈现。

## 测试与验收

- 相同输入、设置、处理器版本和目标配置产生相同缓存键与逐字节一致的运行产物。
- 修改源文件、导入设置、处理器版本、目标平台或影响输出的配置会使相关节点及其依赖正确失效。
- Texture、静态 Mesh 和 Material 能通过构建图生成现有 Runtime 可加载的资产；失败不提交半成品缓存。
- KTX2 Spike 使用代表容器验证 Mip、sRGB、Alpha 和超级压缩元数据；桌面块压缩上传由已识别的
  Granit 通用格式能力缺口约束，并形成可独立提交的上游建议。
- Shipping 包不含未引用资产、源资产、构建缓存和来源映射；显式保留项不会被误删。
- Development 包保留可定位源资产的诊断信息，Editor 能展示阶段、当前资产、缓存命中率和明确错误。
- Windows MSVC/Clang、Linux Clang/GCC、Shared/Static、安装 Consumer 与 Sanitizer 通过。

## 风险与未决问题

- KTX2 是最终 Runtime 容器还是仅作为工具链交换格式，由 M-215 的启动耗时、体积和上传路径结果决定。
- Shader 依赖与变体收集先进入构建图模型；若 Granit 当前 Shader 工具链边界尚不稳定，本版本只完成
  可跟踪的最小节点，不承诺完整离线 Shader 管线。
- Linux 拆分调试信息和平台专用纹理质量档位继续作为后续扩展，不阻塞首批资产构建闭环。
