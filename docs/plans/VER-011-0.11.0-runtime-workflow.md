# VER-011：0.11.0 Runtime 宿主工作流

## 状态

- 状态：实现中
- 目标版本：0.11.0
- 优先级：P0
- 路线图阶段：Runtime 宿主工作流

## 背景与目标

0.10.0 已验证运行时、安装包和未来 Stable 候选接口，但游戏工程目前仍主要由 Editor 或专用示例
承载。0.11.0 建立工程级运行入口，让同一工程能够按以下路径运行：

```text
工程根 → gneiss.project.json → startup_scene → 独立 Runtime 宿主→ 确定性退出
                                      ↑
                              Editor 运行/停止入口
```

版本目标是让 Lantern Gallery 等现有工程不依赖源码树专用 `main` 函数即可启动，并确保 Editor 的
作者状态不会被运行时修改污染。该闭环将为后续脚本、物理、音频和游戏逻辑提供真实宿主，但本版本
不提前实现这些模块。

## 非目标

- 不实现脚本语言、游戏逻辑热重载、物理、音频或网络。
- 不实现完整导出向导、平台安装包、资源加密或商店发布。
- 不允许 Runtime 宿主依赖 Editor、ImGui、资产导入 SDK 或用户最近工程状态。
- 不把运行时对场景的临时修改自动写回作者场景。
- 不在本版本冻结 Runtime 宿主命令行或 Editor 运行协议为 Stable API。
- 不为运行模式复制第二套 Application、Scene 或资源运行时。

## 已确认决策

- Runtime 宿主位于 `apps/runtime/`，是依赖 `gneiss_engine` 的薄宿主；Engine Library 不反向依赖宿主。
- Runtime 宿主与 Editor 都以工程根为入口，并复用同一份工程格式解析与校验能力。
- `startup_scene` 是 Runtime 宿主的默认入口场景；命令行覆盖只作为开发能力评估，不改变工程文件语义。
- Editor 运行采用独立 Application 和独立场景实例，不直接运行正在编辑的作者会话。
- 首版优先采用独立 Runtime 宿主进程。它天然隔离崩溃、全局后端状态和退出清理，也更接近最终游戏。
- Editor 启动 Runtime 宿主前必须先处理未保存修改；默认不静默保存，也不运行内存中未落盘的场景。
- 运行状态和诊断通过最小进程协议或可观察退出状态返回，不让 Runtime 宿主链接 Editor 内部类型。
- 0.11.0 先建立同步的最小统一日志通道：控制台输出、可选轮转文件及 Editor 运行输出捕获；现有
  Application 诊断转换为日志事件，不建立含义重叠的错误系统。
- 完整异步日志、分类过滤、崩溃缓冲和正式 Editor Console 留给后续独立计划；Runtime 不依赖
  Editor Console，日志也不替代结果码、性能分析或崩溃转储。

## 实施顺序

### M-71：工程运行契约与启动诊断

从 Editor 内部提取可复用的工程描述读取与验证能力，明确工程根、资产根、启动场景、错误阶段和
路径上下文。保持工程格式 v1，不因内部复用新增无真实需求的字段。

验收重点：有效工程可生成规范运行描述；缺失工程文件、越界资产根、无效 URI 和启动场景缺失均
返回稳定结果码与可操作诊断；解析器不依赖 Editor UI。

当前进展：工程描述与解析器已从 `apps/editor` 提取到 `apps/common` 内部静态库，Editor 通过轻量
兼容别名继续消费同一实现；加载报告现可提供失败结果、`argument`、`project_root`、`project_file`、
`document`、`schema`、`asset_root`、`startup_scene` 阶段及上下文路径。直接解析测试和 Editor smoke
已通过。M-71 已完成。

### M-72：独立 Runtime 宿主

创建 `gneiss_runtime`，接收 `--project <工程根>`，挂载资产根、加载 `startup_scene`、创建
Application 并运行到窗口关闭或退出请求。无参数、未知参数和启动失败必须输出阶段化错误日志。

Runtime 宿主只负责宿主编排，不拥有与 Engine Library 平行的场景、资源或输入状态。`--smoke`
可固定运行少量帧，用于无交互的集成测试。

首版日志默认写入标准输出/错误，并可写入用户状态目录下的轮转文件；测试可显式覆盖日志路径。
启动、工程解析、Application 创建、场景加载、主循环和退出必须使用一致的阶段字段。

当前进展：`gneiss_runtime --project <工程根> [--smoke]` 已能加载 Editor Demo、创建 Granit
Application、运行启动场景并确定性退出；工程加载和 Application 诊断使用统一结构化事件同步写入
控制台及可覆盖路径的日志文件，文件达到 1 MiB 时保留一个轮转备份。安装规则会部署 Runtime、
Engine 与 Granit 动态库，安装树 smoke 已脱离源码构建产物运行通过。日志不可写不会覆盖原始启动
结果。M-72 已完成。

### M-73：运行会话与作者状态隔离

定义 Editor 发起运行时的保存策略和快照边界。首版运行已保存到磁盘的工程与启动场景；有未保存
修改时显示“保存并运行、取消”，不提供含义含混的隐式临时文件路径。

Runtime 宿主退出后，运行时创建、删除或修改的实体和组件不得改变 Editor 作者会话、撤销栈或脏状态。

当前进展：Editor 内部运行准备策略只生成包含规范工程根的值对象，不携带 Application、World、
Scene Instance、撤销栈或资源句柄。干净场景可直接准备；脏场景返回“需要保存”，仅在显式保存成功
后生成请求，不提供丢弃修改并运行或私有临时场景路径。独立会话修改不影响作者节点与脏状态的测试
已通过。Editor 的“保存并运行、取消”界面将在 M-74 接入实际进程启动时完成，避免出现只改变状态
却没有 Runtime 进程的伪运行入口。该界面现已随 Windows 进程控制器接通，M-73 已完成。

### M-74：Editor 运行、停止与状态反馈

增加运行、停止和运行状态显示。Editor 启动独立 Runtime 宿主进程，防止重复启动；停止动作先请求正常
退出，超时策略必须显式且可测试，不直接遗留后台进程。

Editor 首版只提供最小“运行输出”视图，捕获 Runtime 宿主标准输出/错误并按级别显示；搜索、分类过滤、
来源跳转和持久 Console 布局不进入本版本。

平台进程实现保持在 Editor/工具宿主边界，不进入 ECS、Scene Tree 或公共 C ABI。

当前进展：Runtime 已接受可选的唯一停止信号文件，并以 100 ms 上限间隔检查；收到信号后删除文件、
记录 `stop_request` 事件并通过 Application 正常退出。真实非 Smoke 进程的停止与 `shutdown` 日志已
验证。Windows Editor 已可启动同构建目录的 Runtime、拒绝重复启动、发送停止信号并捕获合并的标准
输出/错误；Run 菜单、F6/F8、保存并运行确认、状态、退出码和最小 Runtime Output 窗口已接通。
停止请求超过 2 秒后强制终止并记录到输出缓冲区。非 Windows 后端当前明确返回 `unsupported`，
下一步实现 POSIX 进程控制并补齐跨平台行为测试。

### M-75：运行失败、退出与重复启动验收

覆盖 Runtime 宿主启动失败、场景加载失败、正常关闭、Editor 请求停止、异常退出、重复运行和 Editor
先退出等路径。每条失败都应在控制台和 Editor 状态区保留阶段、结果码与工程上下文。

进程无法创建窗口或异常退出时，日志文件仍应保留已完成阶段；日志写入失败不得覆盖原始运行结果。

本任务同时记录进程启动到首帧的基线，但 0.11.0 不凭单次测量设置性能门槛。

### M-76：示例工程、安装与版本验收

让 Lantern Gallery 和 Editor Demo 至少一个工程可由构建树与安装后的 `gneiss_runtime` 启动。验证
Windows/Linux、Shared/Static、Granit Fetch/Package、正常交互与 `--smoke`，并形成 0.11.0 验收
记录。

## 测试与验收

- 工程解析测试覆盖成功、字段错误、路径逃逸、资产根缺失和启动场景缺失。
- Runtime 宿主参数解析、错误日志和无参数行为可在不创建图形设备时测试。
- Runtime 宿主使用公开或明确的内部宿主边界，不包含 Editor、ImGui 或资产导入依赖。
- Lantern Gallery 从工程根启动并渲染启动场景，`--smoke` 后确定性退出且无逻辑资源泄漏。
- Editor 可启动、拒绝重复启动、停止并再次启动 Runtime 宿主，状态变化可观察。
- 未保存作者修改不会被静默丢弃，运行会话也不会回写作者场景或污染撤销栈。
- 安装树包含 Runtime 宿主及其所需资产/动态库，脱离源码树仍可运行示例工程。

## 风险与未决问题

| 风险或问题 | 当前处理 |
| --- | --- |
| 进程管理产生平台分叉 | 先定义宿主级最小接口，Windows/Linux 分别实现并用相同行为测试 |
| Editor 停止时 Runtime 宿主卡死 | 先正常请求退出；超时与强制终止策略在 M-74 明确记录 |
| 未保存场景与磁盘场景不一致 | 首版要求保存后运行，不引入临时工程格式 |
| 工程解析逻辑在 Editor/Runtime 宿主重复 | 提取无 UI 的共用内部库，保持单一运行描述 |
| Runtime 宿主被误当作稳定公共 API | 0.11.0 保持 Experimental，稳定面仍以 Engine C ABI 为准 |
| 打包范围过早膨胀 | M-76 只验证可重定位安装和示例，不实现发布向导 |
| 日志系统扩张阻塞 Runtime 宿主| 只实现同步最小 Sink 和运行输出，完整日志平台另立计划 |

## 完成条件

- M-71～M-76 全部完成并形成 0.11.0 验收记录。
- 工程可由独立 Runtime 宿主根据 `startup_scene` 启动，不依赖 Editor 或源码树专用入口。
- Editor 的运行/停止形成可重复闭环，作者状态和运行状态明确隔离。
- 失败路径有可操作日志，正常与异常退出均不遗留运行时逻辑资源或后台 Runtime 宿主。
- 构建树和安装树的代表性工程在目标平台矩阵通过。
