# PLAN-109：异常边界与进程内存耗尽策略收敛

## 状态与范围

2026-11-09：实施中。已建立 fatal、四个自有应用入口的 terminate 兜底、任务执行和渲染线程边界。
普通任务失败保留显式返回，意外异常终止；Debug 子进程和 Release 优化探针通过。
已迁移 metadata、类型/枚举 builder、注册表写入及内置注册/启动初始化调用链，
预期错误保留返回值，扩展回调和分配异常直接传播。已进一步迁移属性读写、instance、各容器视图及
序列化/JSON/value 入口的重复捕获与 noexcept；注册表创建/冻结/查询、底层原生分配失败分类仍待审计。
文件 C 回调及其他模块仍须沿调用链迁移，不能视为全项目策略已经完成。
阶段证据见 [执行边界记录](../records/2026-11-09-exception-boundaries.md)。
长期决策见 [ADR-114](../decisions/ADR-114-exception-boundaries.md)。
本计划独立于 [PLAN-108](PLAN-108-meta-serialization-api.md)，覆盖项目自有代码的错误处理契约，
不把 PLAN-108 的类型访问与序列化迁移扩展成全项目异常改造。
实施时基于最新调用链逐模块迁移；此前的 out_of_memory/internal 转换在对应模块迁移前仍有效。

## 一、现状与问题

- Meta 的 instance、容器视图、registration，以及 Serialization 的模板入口、JSON 入口和快照入口，
  多处重复捕获 bad_alloc 与所有其他异常并返回错误码。
- asset_manager、资源请求、runtime/application 和加载辅助也存在重复转换。
- 不少接口声明 noexcept，却执行 STL 分配或用户回调；直接删除 catch 会触发内层 terminate，
  外层执行边界无法接到异常。
- 现有 Reference 与测试明确依赖异常转换，必须随行为一起迁移，不能只改实现或删除失败测试。
- 一些捕获承担清理、回调隔离、任务完成等职责，不能按文本模式全量删除。

重复捕获增加样板代码，把程序缺陷伪装成可恢复失败；返回 out_of_memory 也不代表系统具备
释放预留内存、清理半成品并安全继续运行的完整能力。

## 二、目标与非目标

目标：普通操作使用 result 表达可预期失败；内部意外异常传播到明确执行边界；
当前阶段不支持进程堆内存耗尽后继续运行；第三方已知可恢复异常只在适配层转换。

非目标：禁用 C++ 异常、改造第三方库、构建异常宏框架、OOM 后自动保存文档、
实现紧急内存池或复杂恢复协议、增加插件系统、改变资源文件格式、远端发布。
不要求每个函数都捕获，也不要求每个函数都允许抛出；noexcept 根据实际契约保留。

## 三、统一错误分类

| 情况 | 目标行为 |
| --- | --- |
| 文件不存在、格式错误、类型不匹配、取消 | result 返回明确错误，调用方正常处理 |
| 文件声明大小不可信、资源预算超限 | 分配前校验并拒绝，不以耗尽内存测试输入合法性 |
| 进程分配失败：bad_alloc，或明确表示主机堆分配失败的空返回值 | 致命错误，尽力输出后终止进程 |
| GPU 资源不足、浏览器配额不足、后端明确可恢复失败 | 保留操作错误，不机械等同于进程 OOM |
| 第三方已知可恢复异常 | 最近的适配层转换为领域错误 |
| 内部意外异常、契约违例 | 传播至执行边界并终止，不吞成 internal 后继续 |
| 正常返回的 error::internal | 按具体来源审核，不因为枚举名称直接终止 |

保留必要的错误枚举；逐个审计 out_of_memory 来源，不做全局替换。
输入导致的超大尺寸应提前校验；length_error 等异常不能不加区分当成可恢复输入错误。

## 四、目标 API 与归属

计划新增 engine/core/fatal.hpp/.cpp，命名空间 gneiss::engine：

```cpp
enum class fatal_reason { out_of_memory, unhandled_exception };
[[noreturn]] void fatal(fatal_reason reason) noexcept;
```

fatal 使用固定文本和不依赖动态分配的紧急输出路径，之后无条件终止；不经过普通日志队列、
不调用用户回调、不获取业务锁、不承诺日志一定落盘。不使用可被 Release 禁用的 assert。
若紧急输出需要平台能力，仅通过现有平台设施接入，不令 Core 依赖 Application 或渲染服务。
终止不承诺完整析构或保存文档，不能为日志再进行格式化分配。

由自有宿主入口显式安装 terminate_handler，处理遗漏的 noexcept/未捕获异常；
不在 Engine DLL 加载或静态初始化中擅自修改嵌入宿主的全局处理器。
嵌入方的全局处理器归嵌入方管理，库自身明确边界仍须执行本契约。
不默认安装全局 new_handler，不替换全局 operator new。

普通内部接口示意：

```cpp
result<value> capture_value(...);
result<scene> load_scene(...);
```

它们用 result 表达预期失败，允许分配或意外回调异常传播；result 不是不抛异常的保证。
析构、明确不抛出的移动操作和简单查询保留 noexcept。虚函数、函数指针、模板适配和调用者的
noexcept 必须一并检查，不能只调整实现函数。

## 五、执行边界清单

| 边界 | 迁移要求 |
| --- | --- |
| Editor、Runtime、导入及命令行工具宿主 | 顶层捕获 bad_alloc/其他异常并调用 fatal；配置 terminate 兜底 |
| 自有线程入口、任务执行器 | 预期失败正常完成请求；意外异常不得逃出线程或被 future 静默保存后遗忘 |
| libuv、浏览器事件及其他 C 回调 | 禁止异常穿越 C 调用栈；在回调跳板就地完成错误转换或终止 |
| 第三方 C++ 适配层 | 只捕获已知可恢复的具体异常；bad_alloc 不得被宽泛捕获降级 |
| C ABI/外部插件边界（若存在） | 不允许异常跨协议；内部兼容 C++ DLL 不因为导出标记就逐函数捕获 |
| 析构与清理 | 不抛异常；正常操作的资源回收采用 RAII；致命路径不依赖复杂清理 |

边界内不得先套一个 noexcept lambda 再期待外层 catch 捕获它的分配异常。
对未来、自定义或第三方任务执行器先检查异常存储/吞掉机制，确保致命异常不会被当成普通任务失败。
正常异步失败仍必须完成一次、通知订阅者并释放临时资源，不能借此次改造删除正常收尾逻辑。

## 六、实施顺序

1. [ ] 基线审计：列出 catch、noexcept、线程/回调/宿主入口，标注转换、清理、重抛和兜底用途；
   核对工具链/运行库兼容性及浏览器异常编译选项，不假定所有平台都支持同样的异常传播。
2. [ ] 建立 fatal 与自有宿主 terminate 兜底；先加执行边界，不先删除内部保护。
3. [ ] 迁移 Meta 与 Serialization：沿完整调用链删除重复转换、调整 noexcept，保留正常 result，
   同步更新用户 getter/setter、traits 和 codec 回调契约，以及相关异常测试。
4. [ ] 迁移资产与文件服务：区分预算拒绝、系统错误、进程 OOM；审计异步投递、线程、C 回调，
   保持取消、任务完成、资源释放的既有正常语义。
5. [ ] 迁移场景、Application、Editor、导入工具及示例；将手动异常清理改为必要 RAII，
   对必须捕获并重抛的局部清理说明理由，不增加通用 TRY/CATCH 宏。
6. [ ] 收尾：审计剩余捕获与 noexcept、更新编码规范及 Reference，完成定向 CPU 验收并记录结果。

每批形成可编译、可评审的完整调用链并本地提交。遇到第三方必须调整才能满足契约时，
记录具体能力缺口，由用户按仓库规则发起跨仓库改动，不直接修改 Granit。

## 七、测试与验收

| 范围 | 验收证据 |
| --- | --- |
| 预期失败 | 缺失文件、非法输入、取消仍返回 result；不误触发 fatal |
| OOM | 人工抛出 bad_alloc/可控分配失败的子进程非零退出；Release 同样终止，不真实耗尽机器内存 |
| 意外异常 | 宿主、线程、C 回调边界的故障注入子进程终止；不测试未定义的跨 C 传播 |
| 第三方适配 | 指定已知异常映射正确；其他异常不被误吞，分配失败不降级 |
| noexcept | 检查完整调用链及回调类型；需要传播的内层不提前 terminate，明确不抛出的操作保留保证 |
| 正常异步生命周期 | 成功、失败、取消均完成一次，无遗留请求、重复通知或资源泄漏 |
| RAII | 可传播异常时临时资源释放；致命路径不声称完整清理 |
| 平台与文档 | 桌面/浏览器实际可用配置分别记录；未验证项明确列出，不用单平台通过替代跨平台结论 |

开发阶段以相关目标编译为主，关键语义使用小型 CPU/子进程测试；最终统一运行受影响 CPU 回归。
不运行 GPU、大场景、耗时远端 CI。子进程测试控制崩溃弹窗和超时，不要求某个具体 abort 退出码。
不能删除异常测试后仅凭编译通过宣告完成，应替换为边界与致命行为测试。

## 八、完成条件与风险

完成必须同时满足：重复捕获清理到明确边界、noexcept 契约一致、正常错误仍可恢复、
致命错误测试通过、所有剩余宽泛捕获有职责说明、当前接口文档与实现一致。
无意吞掉异常、在错误的 noexcept 层提前终止、future 隐藏失败及错误分类混淆是主要迁移风险。

当前无新增产品决策等待确认；首次平台审计若发现现有工具链不支持目标传播方式，
先记录限制与最小替代方案，再实施对应边界，不能通过关闭警告或测试掩盖差异。
