### 同步入口收敛顺序

按 [ADR-064](../decisions/ADR-064-shared-assets-and-scene-instances.md) 收敛为一套异步加载流程，
调用者清单与首批验证见 [同步入口审计](../records/M-331-sync-entry-audit.md)。

1. 移除 Runtime 渲染资产重载的同步回退；异步服务缺失明确失败。
2. 将已采用版本索引组织为可失败的准备、使用者提交与无分配交换，与场景引用切换形成一致事务；
   缓存层闭包入口见 [实施记录](../records/M-331-adoption-transaction.md)。兼容配置域、宿主重载
   及就绪租约查询已接入，见 [宿主记录](../records/M-331-host-adoption.md)；
   初始候选选择见 [新场景记录](../records/M-331-scene-initial-adoption.md)。继续迁移调用者。
3. 迁移 Editor 资产替换、Prefab 放置与恢复；异步回执核对会话及目标对象有效性，
   成功提交后才记录历史。撤销重做保留所需版本租约，不能以等待异步请求替代迁移。
4. 迁移文档事务刷新、文件监听重开场景及 Runtime Scene/Prefab 结构重载，
   分别保留失败回滚、选择与历史语义，不直接用整场景重开代替所有结构编辑。
5. 调用者迁移完成后收敛旧同步加载接口；确有需求的阻塞适配单独说明调用线程及推进方式。

### 已确认：异步编辑采用模态进度界面

2026-10-15 审计 `src/editor/asset_scene_commands.cpp`、`editor_command_history.cpp` 和
`src/host/editor/editor_application.cpp`：资产命令通过同步 execute 执行并记入历史，撤销重做
只在回调成功后移动游标；当前无待完成命令的历史位置或冲突策略。整场景加载显示独立加载界面，
但局部资产替换不能据此推定应屏蔽整个编辑器。

用户已确认首批采用模态进度界面：资源就绪时立即提交；需要准备时显示进度和取消入口，
暂停文档修改、相机操作、撤销重做及保存。窗口移动、resize、最小化恢复和关闭继续响应。
普通后台导入、缩略图和预加载不因此变为模态。异步准备、主线程提交、版本租约保留仍适用。
以下保留当时比较的方案，不代表 B/C 已排期：

| 方案 | 准备期间行为 | 代价 |
| --- | --- | --- |
| A：模态场景编辑（已选） | 只显示进度界面和取消入口；成功后一次提交命令；保留窗口系统操作 | 加载期间暂不能浏览和编辑文档；需覆盖快捷键、Gizmo、命令入口及文件监听应用 |
| B：乐观提交 | 继续编辑；完成时验证目标和文档状态，冲突则丢弃候选并提示重试 | 编辑流畅，但操作可能因后续修改失效，须明确历史顺序与冲突粒度 |
| C：占位命令与队列 | 点击时保留历史位置，后续修改排队或按依赖提交 | 排序、取消、保存和分支历史复杂，超出首批最小迁移 |

示例：点击将材质 A 替换为 B，B 尚未准备好时移动节点再撤销。
所选方案不允许准备期间继续移动或撤销；B 完成后才提交新历史。
A 不暂停主线程或渲染；取消先完成候选清理再解除互斥。文件监听可继续采集，
其文档应用须延后并复验，不得越过编辑事务。打开其他场景或关闭文档时取消请求并等待安全清理，
不阻塞 UI。具体失败、取消和保存交互测试随所选方案补齐。

不预建排队命令系统，也不更改已确认的版本/加载策略。首批资产替换接入见
[模态资产替换记录](../records/M-331-editor-modal-asset-edit.md)与
[网格节点创建记录](../records/M-331-editor-modal-mesh-create.md)；Prefab、子树恢复等入口继续迁移。

### 已确认：Prefab 实例化采用分帧结构事务

2026-10-16 检查 `prefab_runtime_instance::create`：当前依次同步准备渲染资产、
在当前 World 创建全部节点、应用覆盖。`begin_staged` 等分步构造接口用于候选 World，
不能直接用于活动 World 并假定中间节点不会被系统观察。Editor 创建完成后的
`refresh_nodes` 还可能分配失败，迁移时必须一并处理提交与编辑器镜像的一致性。
此处为源码分析，尚无本轮大型 Prefab 实测耗时，不把结构风险表述成已确认性能瓶颈。

已有决定仍然有效：模态进度、取消、失败保留旧状态、实际版本租约支撑撤销重做。
用户已确认选择 B，将大量节点构造与回收也纳入可分帧事务；下表保留方案比较：

| 方案 | 范围与行为 | 限制与代价 |
| --- | --- | --- |
| A：先完成异步资源准备 | 文件读取、解析和资源准备异步；主线程一次性实例化和提交 | 改动较小；大量节点构造、失败清理及撤销重做仍可能长时间占用主线程，不能承诺提交期间窗口及时响应 |
| B：同时支持分帧结构事务（已选） | 准备、分帧构造、发布、分帧取消清理形成完整事务；未发布节点不能被正常系统观察，历史只在发布后提交 | 需明确 World 未发布对象的隔离边界，并覆盖取消、失败、历史恢复；范围明显大于资源加载迁移 |

B 的具体隔离机制须在实现前补充 ADR，不预先决定引入第二个 World，也不以整场景重开
替代局部实例化。若选 A，应明确保留的同步提交限制，并测量实际节点规模与提交耗时。
B 的 Asset Browser 放置及其历史恢复已接入，当前行为和验证边界见
[Prefab 异步闭环记录](../records/M-331-prefab-async-placement.md)。

已确认的历史交互：大型结构命令的撤销/重做允许显示模态进度。迁移前
`editor_command_history::undo/redo` 只在同步回调成功后移动游标，尚无在途历史操作。
采用一个在途历史操作：保留快照和实际版本租约，分帧重建/清理，成功后移动游标，
失败或取消维持原历史位置；不重新读取资产文件，不引入命令队列。此方案需要补齐结构事务
回滚及保存状态的一致性。另一方案是历史持有整套未激活实例，撤销重做切换可见性，
但实体槽位和组件内存会随历史保留，历史淘汰仍需渐进清理。不选用后者规避历史迁移。历史状态基础见[分帧历史记录](../records/M-331-history-operation.md)。

底层取消准备见[分步清理记录](../records/M-331-prefab-staged-cancel.md)。

World 与 Scene Tree 的共同发布门已具备内部基础，见[隔离记录](../records/M-331-scene-publication.md)，

### 已确认：原生宿主与 C 句柄的关闭权

2026-10-16，用户确认方案 A，决策已补入 ADR-062。以下保留方案对照；借用桥接、三个原生宿主拥有链路及原生回调已接入；详见
[原生宿主接入记录](../records/M-332-native-host-ownership.md)。

决策时源码证据：`application_registry.cpp` 的表项持有原生对象共享引用，
`destroy_application` 会先调用对象 shutdown，再移除 RID；共享引用只保活内存，不阻止关闭。
`src/host/runtime/runtime_application.cpp` 当时由 SDK 包装拥有 Application，并把句柄传给资产、场景和
`create_game_context`；后者在 `game_context.cpp` 解析 Application 并保存句柄。
动态游戏模块公开的是 Game Context，不是因此就必须公开原始 Application 指针。

宿主改为直接创建原生对象后，部分待迁移接口和真实 ABI 适配仍需解析同一个对象。
不能简单将原生对象再登记成普通拥有句柄：C destroy 可先关闭它，宿主却仍持有对象引用。
这不是新建第二套运行时的问题，而是必须区分内存保活和关闭权限。

| 方案 | 生命周期规则 | 影响 |
| --- | --- | --- |
| A：原生宿主拥有，兼容桥只借用（建议） | 宿主统一关闭；借用句柄的 destroy 返回 invalid_state，不关闭或移除对象；撤销桥接只使句柄失效 | 内部业务直接用原生对象；少数旧入口经有范围的桥接；须验证关闭期间回调与借用失效顺序 |
| B：继续由拥有型 C 注册表管理宿主实例 | 宿主保留一个拥有型句柄，原生对象仅借用；关闭仍经注册表 | 延续原有销毁语义，但宿主生命周期继续依赖句柄层，不能宣称 Application 原生拥有链路完整迁移 |

建议 A 的最小实施约束：

- 只为原生宿主新增内部借用桥接，不新增公共插件 API，不更改 C ABI 的符号或结构布局。
- 外部 `gneiss_application_create` / SDK 创建的拥有型句柄仍按原有 destroy 规则工作；
  SDK 的拥有类型不得自动接管借用桥接句柄。借用句柄不交付为需要调用者销毁的创建结果。
- 桥接表只借用原生对象，单次已获准调用可短时保活；不能使桥接引用循环或成为隐藏关闭者。
- 宿主开始关闭后停止接收新业务请求，排空模块/请求；关闭通知所需的受限访问必须明确，
  在释放对象和资源前撤销桥接，迟到调用返回失效错误，不靠裸指针存活假设。
- 不给所有原生方法传递 Application C 句柄；句柄只由 ABI 适配使用，Game Context 优先借用
  受控内部接口。旧场景/资产入口的临时桥接逐项列出并随各模块迁移移除。
- 验收覆盖借用 destroy 不伤害对象、撤销桥接不关闭对象、宿主关闭使旧句柄失效、槽位复用、
  错误线程、在途关闭及真正 C 拥有者恰好关闭一次。

本项关闭所有权已确认，后续按 A 继续宿主迁移。原生对象首批实现及已有测试结果保持不变，不将审计当作 Application 迁移完成。
