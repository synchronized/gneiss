# 0.51：CAORS 共享材质接入方案

## 状态与目标

2026-10-20，用户已确认方案 A。asset_manager 的异步材质通道已提供默认关闭的 CAORS 接入；
同步 acquire 保持原路径，尚未将该选项作为默认配置。
承接[Application 输入接入](PLAN-051-caors-application-integration.md)，下一项建议选择
CPU 材质文档，验证共享资源、多版本及依赖处理，再扩大到 Mesh、纹理。
不另立 0.52，不修改上游仓库，不将本项作为性能改善的既成结论。

## 源码核对

- [asset_manager](../../src/engine/function/asset/asset_manager.hpp)当前拥有 Gneiss
  resource_cache、CPU 材质文档索引、渲染加载器和 Prefab 加载器；CAORS 输入宿主尚未收敛到这里。
- [材质解析](../../src/engine/asset/asset_parsing.hpp)输出纯 CPU 参数和五个纹理 URI，
  不创建 RID。同步加载与后台准备共用解析器。
- [后台准备](../../src/engine/asset/asset_preparation.hpp)输出包含来源、摘要、准备配置、
  依赖版本的 prepared_asset；材质各槽位保存确切 texture_versions。
- [渲染加载器](../../src/engine/function/render/render_asset_loader.cpp)创建材质 RID，
  材质资源持有纹理缓存项，确保旧引用有效。
- [资源缓存](../../src/engine/asset/resource_cache.hpp)同时承担固定版本缓存及采用事务；
  版本发布与使用点切换是两件事，失败不得改变当前场景。
- CAORS 输入宿主按 URI 绑定 GUID，每次显式请求 load/reload；这不能直接代替上述版本协议。

## 已确认范围与备选方案

### A：先接 CPU 材质文档，保留渲染发布事务（建议）

CAORS 负责共享 CPU 材质文档的加载与持有；Gneiss 负责纹理依赖准备、RID 创建及场景采用。
二者管理不同对象：前者是不可变解析结果，后者是引用确切纹理版本的渲染产物。
不允许两个缓存分别决定同一材质当前生效版本。

优点：可以用一个材质、两个使用点、一次失败重载验证完整边界，保留现有撤销与场景事务。
限制：此步不消除所有 Gneiss resource_cache，也不等于全部资源已统一到 CAORS。

### B：同时迁移渲染版本缓存和采用事务

CAORS 同时承担共享资源持有，Gneiss 将现有缓存职责拆为版本映射与采用协调，逐步删除旧持有层。
需要覆盖纹理、材质、Mesh、Prefab、场景及撤销链路，不能只验证材质 Loader。
优点是较早完成统一管理；代价是影响面扩大，故障定位及回归成本明显更高。
不建议以一个 CAORS GUID 的 reload 操作冒充整批依赖版本事务。

## 方案 A 的实施顺序

1. 更新 ADR，明确 CPU 文档与渲染产物的所有权。宿主资源管理状态逐步归入既有
   asset_manager；不为材质复制一个含线程、VFS、manager 的独立输入宿主。
2. 抽取材质 CPU 文档 Loader，复用现有解析器和 VFS 快照桥，线程借用既有执行器。
   Loader 不递归创建纹理，不访问 World、编辑器或 RenderService。
3. 明确缓存键：CPU 文档按来源域、URI、类型、内容摘要区分；渲染产物继续按完整
   asset_version_key 区分。GUID 只作为宿主内映射标识，不替代来源身份或内容摘要。
   先核对 CAORS 固定版本注册与持有能力；如不能保留旧版本，记录具体缺口后再决定接法。
4. 从真实后台材质准备入口接入文档结果；依赖 URI 继续交给现有批次准备，全部来源复验后
   才能构成可发布候选。缓存命中文档不代表纹理版本仍然有效。
5. 在所属线程发布 RID，再通过既有采用事务切换使用点。取消或失败释放候选；
   场景和撤销记录持有的旧版本不随 reload 失效。
6. 接入前核对文档大小上限。桥与 Loader 默认 1 MiB，现已支持宿主显式传入完整读取上限，不能无意降低现有材质接口
   接受范围；超限策略必须明确并测试，不静默读取截断内容。
7. 完成开关启用/关闭、共享/静态构建与安装消费者验证后，才宣称生产入口接通。

## 验收

- 两个使用点请求同一版本，复用同一 CPU 文档；释放一个不影响另一个。
- 同 URI 不同来源域不得串用；不同内容版本并存，旧引用读取仍一致。
- 只改变纹理也必须更新渲染产物版本；禁止按 URI 混入其他版本纹理。
- 读取失败、非法文档、来源复验失败、依赖失败、取消均保留旧场景与材质。
- 加载中撤销、切换场景、关闭宿主无迟到应用；任务、回执及资源按关闭顺序释放。
- 成功发布与采用分开验证；采用失败不改变当前选择，撤销重做保持确切版本。
- 真实异步准备入口通过；独立 Loader 测试不替代端到端验收。
- 不向普通公共接口暴露 CAORS 类型；不新增主线程文件等待或独立线程池。

## 当前边界与剩余验收

asset_manager 拥有唯一 CPU 材质文档索引；通过 create_channel 注入批次候选工厂。
整批复验成功且未取消后在所属线程登记，材质缓存项持有 CAORS 文档租约；
取消、来源变化或依赖失败不会登记未验证候选，也不改变原有渲染采用协议。
同步 acquire、直接手工构造而未注入文档缓存的通道仍使用原解析器。
索引为弱引用，CAORS handle 持有实际对象；不另建 CAORS URI reload 缓存或独立线程池。

默认仍关闭 GNEISS_ENABLE_CAORS_MATERIAL；此步不代表全部资源已统一管理。
真实大型场景交互、完整编辑器撤销/重做手动验收、Linux、Emscripten 与性能对比尚未完成。
输入宿主汇入 asset_manager、CAORS 共享库切换、Mesh/纹理资源迁移不属于本次接线。

## 本地阶段验收

Windows Clang Debug 下，材质文档、输入探针、VFS 桥接和真实 Application 四项 CTest
通过。材质验证使用原 VFS 根目录及异步 libuv 打开、宿主线程池解析，覆盖重复请求合并、
成功重载后旧句柄保活、非法文档、复验拒绝、取消、1 MiB 超限和移除缓存后句柄保活。
该测试不创建 GPU 资源，不证明生产版本映射、纹理依赖采用或 Editor 材质编辑已接通。
本轮未重跑安装消费者、其他平台或性能验收；普通公共接口及安装规则未变。

版本索引补充验收：同来源同内容复用、不同内容并存、同 URI/摘要不同来源不命中、
回执摘要/大小/类型/来源缺失拒绝、空文档拒绝、弱项回收、租约跨索引销毁保活均通过。
这不代表自动检测文件变化；调用方仍须按批次复验流程提供可信回执。

### 生产接入位置核对

asset_preparation 当前在 decode_non_texture 解析材质后登记来源回执，随后准备全部依赖，
最后才复验整批输入。后续应在这个准备协议中接入 CPU 文档，不在同步 acquire_material
旁新增一条绕过批次的发布路径。版本索引不能在 decode 阶段把未复验候选当成已验证结果。
纹理槽位的确切版本与最终 asset_version_key 继续由现有准备协议计算。
有界 Loader 的单文档上限与生产批次预算不是同一契约。已去除写死的 1 MiB 限制；
正式切换时须从请求预算推导单文档限额，并给桥、Loader 及来源复验传递一致预算，
仍由现有批次流程核算全部资产及依赖的总预算。

### 单文档限额验收

新增 1 MiB 和 2 MiB 两组边界验证：恰好达到上限的合法材质可完成读取、解析和复验，
超出一个字节拒绝且保留旧缓存；桥和 Loader 的零预算均拒绝。输入映射调用保持原默认值。
读取、摘要与解析会暂存多份缓冲，单文档限额不等于峰值内存上限；本项不宣称解决大资产内存压力。

### 批次解码接入

分步 asset_preparation 已增加不含第三方类型的可选材质解码回调，默认继续使用既有解析器。
CAORS 文档可直接解码批次已经读取的字节，避免在批次内部再次按 URI 打开、读取并建立另一套
进度状态；独立异步 Loader 复用同一解码函数。回调只产生候选，不登记共享版本。
纹理依赖扩展、字节预算、来源登记、整批复验与最终版本生成仍由原准备器负责。

集成测试使用真实分步准备器和 VFS，在后台线程推进，验证成功批次的回执可登记 CAORS 文档；
解码后修改原文件、纹理依赖缺失均拒绝整批且不替换旧缓存。该阶段尚未在 Application
资产管理器装配回调、传递跨批次文档租约或启用生产开关，不等于 Editor 已切换。
后续装配应在既有资产管理器内汇合候选与完成回执，而不是为每个请求另建 manager 或线程池。

本地 Windows Clang Debug：Engine 及相关调用方重建通过；4 项 CAORS 测试和原 CPU 准备
测试共 5 项通过。未重跑安装消费者、跨平台及性能验收。

### 可选生产通道接线

新增 Gneiss 自有 material_document_cache/material_document_batch 内部协议，具体 CAORS
实现只在 .cpp 内装配；创建批次不启动线程、不重新读取文件。所有批次仍受既有准备预算约束，
不引入独立 Loader 默认的 1 MiB 限制。每个成功批次依然读取、解码、复验，之后才共享文档。
prepared_asset 仅携带文档生命周期接口，发布的材质缓存项继承该租约；确切纹理版本不变。

本地 Windows Clang Debug 启用选项：Editor 重建、隐藏冒烟、异步资产通道和 CPU 文档测试通过。
通道测试覆盖 cooperative/thread_pool、固定版本、仅纹理变化、失败回滚、取消与停止；
新增跨批次文档共享、单租约释放与材质缓存销毁后的文档释放验证。
独立静态与共享 Engine 均构建并安装，隔离安装前缀中的 C/C++ 等 4 项 consumer 各自通过。
关闭选项的静态 Engine 重建及安装 consumer 另行验证，配置不再解析 CAORS 依赖。
上述安装矩阵不启用 Granit 窗口；真实编辑器路径另由主开发配置的隐藏冒烟验证。
未把文档共享描述为解析加速或 GPU/大场景性能改善。
