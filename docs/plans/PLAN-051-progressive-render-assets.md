# 0.51：渲染资产逐步就绪与加载结构简化

## 状态与范围

2026-10-22：用户确认默认允许资源逐步出现，更新期间继续显示旧资源；随后授权继续推进，
当前进入消费者审计与基础契约验证，尚未修改运行行为。决策见 [ADR-072](../decisions/ADR-072-progressive-render-assets.md)。
本计划承接[资产管理替换计划](PLAN-051-asset-manager-replacement.md) R4；CAORS 替换已完成。
本页是此次行为调整及实施顺序的权威来源，旧计划中迁移期间保留全部版本保证的要求不是新的目标。

首批进展：S0 已完成源码消费者分类，S1 已补单纹理延迟回执/预算/失败保旧契约测试；
生产行为未改，首次占位、真实异步上传及性能基线未完成，详见
[首批审计记录](../records/2026-10-22-progressive-assets-audit.md)。

目标：普通资产加载不再默认依赖整批版本发布和场景采用；共享渲染资产使用稳定 RID，
由渲染侧在新数据可安全使用时更新；复用现有 CPU 加载、执行器和渲染资源服务。
非目标：直接修改 Granit、重写反射、构建通用流送框架、立即删除全部历史快照、改变 C ABI。
场景结构与游戏模块初始化需要的最低条件仍需满足；允许视觉资源缺失不等于允许无效场景运行。

## 已确认的默认行为

| 情况 | 目标行为 |
| --- | --- |
| 首次 Mesh 未就绪 | 保留逻辑实例，暂不提交该物体的绘制 |
| 首次纹理未就绪 | 渲染适配层绑定适合该纹理槽位的默认资源 |
| 首次材质未就绪 | 建议默认材质；具体默认外观在最小闭环确定 |
| 更新仍在加载或上传 | 继续使用旧的有效资源 |
| 更新成功 | 在渲染安全点切换同一逻辑 RID 的内容，共享使用者一起更新 |
| 更新失败 | 保留旧资源并记录诊断；首次失败继续缺省显示 |
| 多个资产完成时间不同 | 允许分帧陆续生效，不默认提供跨资产原子替换 |

可见代价：短暂缺少物体、默认材质或纹理，以及不同资产更新不同步。
需要一致性的真实操作另行定义局部事务；不把特殊要求传播到全部加载入口。
稳定 RID 仅指同一来源、类型和兼容设备域内的有效逻辑资源；销毁仍使旧 RID 失效，
设备重建、资源类型改变和跨域引用不能沿用过期句柄。

## 现状与具体障碍

| 当前入口 | 已核对的职责 | 改造方向 |
| --- | --- | --- |
| `engine/resource/asset_manager` | 通用 CPU 请求、VFS、CPU 缓存、Prefab 加载；泛型入口目前未覆盖所有渲染准备 | 收敛读取与解码，提供只读结果，不增加 GPU 或场景状态 |
| `resource/types/material_document` 与 `material_document_lease` | 文档和外层来源记录均带摘要/大小，用于登记校验 | 同次读取绑定数据与来源记录，再评估去掉文档包装，不能直接删除校验 |
| `render/texture_load_service` | 自行调度 CPU 准备、批量上传、回滚与发布；实际也处理 Mesh/材质 | 先迁移 CPU 准备，再收缩为渲染侧待处理队列，删除批次全成全败协议 |
| `render/render_asset_loader` | 资源缓存适配、候选、旧 RID 更新、固定版本发布与采用 | 保留查找/创建/替换的必要逻辑；消费者迁移后移除双发布模式和普通路径采用接口 |
| `render/render_resource_service` | RID 表、共享数据和 `replace_*`；旧帧可持有旧数据 | 继续作为 RID 与资源生命周期的权威所有者 |
| `render/backend/granit/granit_render_service` | 渲染命令队列、准备镜像和活动镜像；回执报告渲染命令结果 | 维护上传、缺省资源、安全切换及旧镜像退休，不将其细节上抛到场景 |
| `runtime/loading/scene_load_service`、`scene_session` | 当前提交 fixed_version 批次并 prepare_adoption | 场景结构就绪与视觉资源就绪分开，普通场景不等所有视觉资源 |
| Editor 历史与资产编辑 | 部分命令持有确切旧资源和异步恢复状态 | 逐命令分类；属性值撤销与磁盘资产历史恢复分开处理 |

目前 `poll_texture_preparation` 读取的是渲染命令完成回执，不能称为 GPU fence 完成。
Granit 的 CPU 数据接收、命令排序、异步暂存寿命与 GPU 安全使用条件须按锁定版本接口核对。
若有底层能力缺口，按仓库规则提出最小可复用的上游需求，不直接修改 Granit。

## 目标结构（尚未实现）

```text
Runtime / Editor
  ├─ 逻辑场景、对象引用、编辑命令
  └─ 请求资产 / 引用渲染 RID
             │
engine/resource
  asset_manager → VFS + 显式 Loader + CPU 缓存
             │ 只读数据 + 同次读取绑定的来源记录
             ▼
engine/function/render
  渲染资产接入逻辑：来源/类型/兼容配置 → 稳定 RID
  render_resource_service：RID、当前有效数据、必要的待更新记录
             │ 已有渲染命令队列
             ▼
backend/granit
  GPU 镜像、上传、安全切换、默认资源、旧帧资源退休
```

图中“接入逻辑”“待更新记录”是职责，不要求各建一个类或 Service。
优先收缩/合并已有 loader 和上传协调器，不在外面套新的 manager。
Scene Tree 仍只关联实体 ID；ECS 保存数据和 RID，不持有 CPU 请求或 Granit 对象。
CPU 内容可不可变，渲染逻辑 RID 可稳定：更新是替换所指数据，不要求原地修改共享 CPU 对象。
来源摘要集中在加载/缓存记录；这不自动取消来源变化检测，减少复读另按测量结果评估。

### 最小状态与所有权

每个资源允许“当前有效内容”和“待更新任务”同时存在，避免把正在更新误判为不可绘制。
只保留任务必要阶段（待准备、已提交、成功/失败）及更新序号；具体枚举由实现决定。
没有当前内容时使用缺省策略；有当前内容时优先继续使用。

- 未提交且预算不足：下一轮调度；已提交：等待该任务结果，禁止逐帧重复提交。
- 永久解析错误：记录失败，等待显式重试或新来源变化，不自动逐帧重试。
- 更新序号独立于 RID generation，旧任务晚完成不得覆盖新请求，不能重建历史版本数据库。
- 上传任务保活所需 CPU 数据；GPU 资源按后端队列/帧完成契约退休，取消不提前释放。
- 材质可先绑定默认纹理，纹理完成后更新绑定；必须有依赖通知或待更新标记，不能只改缓存。
- 来源/类型/设备准备配置不兼容的请求不合并；设备丢失、关闭和 RID 销毁必须终止后续采用。

## 分步实施与验收

| 阶段 | 工作与退出条件 |
| --- | --- |
| S0 消费者审计 | 列出 fixed_version、prepare_adoption、旧重载及历史快照调用者；为每项标明直接删除、迁移或特殊保留。记录加载时间、主循环最大间隔与内存基线 |
| S1 最小渲染闭环 | 先覆盖单纹理首次延迟、稳定 RID 更新和失败保旧；确认命令排序及数据寿命。证明下一帧重试不会重复上传 |
| S2 CPU 加载收敛 | 纹理、Mesh、材质逐项复用管理器读取/解码；保留设备配置隔离和协作预算。绑定来源记录后删重复材质元数据，避免新增第二套缓存 |
| S3 渲染流程收缩 | 将上传状态留在渲染侧；材质默认纹理和依赖完成更新闭环通过后，移除普通路径批次回滚与版本采用。每迁移一组消费者删除对应旧入口 |
| S4 场景与历史接入 | 场景结构可用后允许视觉资源渐进出现；区分游戏模块必需依赖。逐条确定历史语义变化，更新测试与说明，特殊快照不作为所有资产前置条件 |
| S5 清理与回归 | 无消费者后删除固定版本索引/选择状态、重复租约和中转接口；更新当前架构文档，执行受影响构建和生命周期检查 |

S1 首次纹理占位还需已有可绘制的 Mesh/材质；随后独立补齐首次 Mesh 跳过和材质缺省测试。
阶段内可短暂保留旧路径，但不能把两个后端/两套发布模式永久作为完成状态。
S0/S1 正在执行，S2～S5 未实施；不把设计图描述为当前源码。

必须覆盖：首次未就绪、更新保旧、上传失败、依赖迟到、连续重载乱序、取消、关闭、
销毁后迟到回执、预算不足、设备失效、跨服务 RID、旧帧仍引用旧内容，以及资源最终回收。
延迟测试使用可控执行器/回执，不依赖随机睡眠。测量线程与协作模式的帧间隔和峰值内存。
公共 ABI 若变化执行 C/C++、静态/共享消费者验证；不因设计简化跳过仍适用的生命周期检查。

## 未决项

1. 材质首次缺省的具体外观；哪些非视觉依赖必须阻挡场景激活。
2. 历史命令哪些只恢复作者值，哪些必须保存独立内容；删除确切版本恢复前列出行为差异。
3. RID 是否在首次请求时分配；若预分配，必须让查询明确区分“合法句柄”和“可绘制内容”。
4. CPU 缓存回收预算、来源复验成本，及上传待处理记录最终归属的具体类。

已确认的是默认渐进显示方向；以上细节不能用增加通用框架代替具体调用点审查。
