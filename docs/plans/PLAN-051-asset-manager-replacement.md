# 0.51：移除 CAORS 与资产加载简化计划

## 状态、目标与非目标

2026-10-22，设计中，代码替换未开始。用户要求移除 CAORS，采用 Granit 示例 Asset Manager，
并先审查迁移方式和复杂度来源。本文承接该方向；具体接入方案仍为推荐设计。
资源模块后续实施以本文为准，暂停扩大 CAORS 接入及其同步发布修复接入；
此前接入记录保留为历史证据，不表示当前代码已经移除 CAORS。

目标：沿用 Granit 示例的 Manager、Source、Loader、强类型观察句柄与只读 CPU 结果模型，
替换现有 CAORS 请求和持有机制；逐项证明简化不损害已有行为。
边界提案见 [ADR-071](../decisions/ADR-071-example-asset-manager.md)。

非目标：重写反射、场景、编辑器历史或渲染；删除既有同步 API；降低警告或测试等级；
修改 Granit 仓库；在本阶段承诺解决所有性能问题或发布新版本。
删除依赖不等于删除固定版本、来源复验、失败原子性和历史保活保证。

## 源码基线与可复用范围

- Gneiss Granit 锁定提交为 `c9803195cc81d2d1cef55e47f5bcff1c42884ccd`。
- 本次只读核对的 Granit checkout 为 `2c108fb192f94f2f892a216f8d827e33fdb9feb7`，工作区干净。
  两提交的 `examples/common/assets`、`tasks` 差异仅为两处 CMake；不能直接依赖相邻 checkout。
- [示例 manager 源码](https://github.com/synchronized/granit/blob/c9803195cc81d2d1cef55e47f5bcff1c42884ccd/examples/common/assets/asset_manager.cpp)
  使用类型与位置作为键，缓存共享请求，主线程发布 CPU 结果；没有同步加载或热重载入口。
- 示例句柄取消观察者，不保证停止底层 I/O；缓存强持有请求，`clear_cache()` 整体清除索引。
  依赖通过 Source 读取字节，不能把它描述成完整递归资源图、版本缓存或自动淘汰系统。
- 示例 `task_system` 是具体类型，零 worker 时 inline 执行；不能直接替换 Gneiss 协作调度。
- 示例为 MIT 许可的私有基础设施，不安装、不构成公共 SDK。复用须保留原版权及许可证。

### 推荐接入方式与替代方案

推荐将上述固定提交的最小实现移植到 Gneiss `engine/resource`，明确记录来源及差异，
改用现有结果类型、VFS 和任务执行器；这是维护有来源记录的移植版，不宣称无修改直接使用上游。
保留 `load<T>`、显式 Source/Loader 注册、共享请求和只读结果的结构，
扩展现有 `asset_manager`，不在其外再建第二个管理器。
移植源码保留 Granit 原版权；第三方原样文件如需保留，放入隔离目录，不混入自有格式化范围。

| 方案 | 优点 | 缺点与判断 |
| --- | --- | --- |
| 直接链接示例 target | 上游代码改动少 | 带入示例任务系统、平台注册和构建约束；PACKAGE 不保证包含示例；不推荐 |
| 固定版本最小移植 | 无需跨仓库改动，可复用现有 I/O/协作执行 | Gneiss 承担差异维护及测试；推荐，实施前冻结文件清单 |
| Granit 提取正式组件 | 长期减少复制，共享修复 | 需要独立上游设计和发布，不作为本轮前置条件 |
| 仅照接口另写实现 | 布局自由 | 可能丢失已有语义并重造框架，不能称为复用示例；不推荐 |

不启用第二个线程池；不增加 Engine 对完整 Granit 图形库的基础依赖；
保留 Granit 平台关闭、静态/共享及 Web 配置。内部类型不进入公共 C ABI 或安装头。
如果固定源码无法在这些约束下小范围移植，先记录具体障碍，不悄悄扩大到任务系统重写。

## 六项额外需求的逐项审查

下文的“推荐”是迁移后的评估方向；第一阶段先保留当前可观察行为。
他人做法来自官方资料，不能由文档没有描述某项保证推断对方完全没有该能力。

### A1：同步与异步加载、发布顺序

**现状**：[asset_manager](../../src/engine/resource/asset_manager.cpp) 的同步输入直接准备数据，
异步输入使用 CAORS；两者尚未统一缓存发布。
[既有探针](UPSTREAM-051-caors-sync-publication.md) 发现锁定 CAORS 同步重载可能被旧异步覆盖，
不是已证明当前 Gneiss 输入会回退。Granit 示例只有异步入口，换入后不会自动获得同步保证。

**问题**：阻塞等待需要当前宿主线程推进的任务可能无法完成；嵌套推进外部队列可能重入。
删除 CAORS 消除了特定依赖障碍，但不会自动解决新实现的乱序发布。

**他人做法**：[Godot 后台加载](https://docs.godotengine.org/en/stable/tutorials/io/background_loading.html)
提供请求、状态查询和取结果，提前取结果会阻塞；Granit 示例则只提供异步请求。

**推荐**：共用纯解码函数和缓存身份；同步在调用线程读取、解析，异步经现有执行器运行。
每个缓存键使用唯一发布顺序规则。同步成功提交后，先前异步结果只能返回原观察者，不能覆盖当前项。
明确同步失败不改变当前项；旧异步是否仍可发布由测试固定，建议失败不撤销其原资格。
异步完成只在宿主安全点发布，不隐式执行编辑或场景回调。

**优缺点**：保留接口语义且避免等待死锁；需要少量顺序状态和确定性乱序测试。
替代方案是禁止同步/异步交叠，代码少但收紧既有调用条件，不能作为无声兼容措施。

**验收**：首次加载、重载、同步失败、旧任务晚完成、新任务正常发布、独立订阅、无执行器同步加载；
协作执行时不得递归驱动宿主队列。优先级 P0，输入切换前完成。

### A2：加载期间来源变化与最终复验

**现状**：[来源账本](../../src/engine/resource/vfs/source_revision_file_system.hpp) 对读取内容记摘要，
准备后复验；支持跨批次一致性检测，但并不提供跨进程文件系统原子快照。

**问题**：重复读取和计算摘要增加成本；简化为路径缓存后可能把来源变化或依赖混合版本当作成功。

**他人做法**：[Godot 导入流程](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html)
把导入结果放入独立目录，并通过源文件校验和变化触发再导入；
[O3DE 运行时资产系统](https://docs.o3de.org/docs/user-guide/assets/runtime/)
区分运行时加载职责。不能据此推断任一系统保证多文件原子快照。

**推荐**：迁移时保留现有复验。另测复读耗时、字节数及变化失败率，再评估
“导入时产出不可变文件和版本清单，运行时读取已发布产物”的方案；散文件开发模式继续校验。

**优缺点**：不可变产物可减少反复扫描；代价是导入发布、存储回收、旧工程兼容及清单维护。
仅用时间戳/大小更便宜但检测能力较弱；暂不替代内容校验。

**验收**：读取间修改源、只修改依赖、同 URI 换挂载来源、复验取消、失败保留旧场景；
必须分别记录 CPU、I/O 和端到端开销。优先级 P1，CAORS 删除时保持原实现。

### A3：资源身份、确切版本与旧引用

**现状**：[resource_cache](../../src/engine/resource/cache/resource_cache.hpp) 区分固定版本与选择域，
来源、依赖和准备配置参与身份；材质/Mesh 另有 CPU 版本索引。
Granit 示例仅用目标类型与位置缓存，不能跨项目来源或准备配置无条件复用。

**问题**：多个索引和多层持有难以追踪；直接改成路径键会错误合并不兼容对象。

**他人做法**：[Godot ResourceLoader](https://docs.godotengine.org/en/stable/classes/class_resourceloader.html)
有缓存复用、忽略和替换模式；Granit 示例返回 `shared_ptr<const T>`。
这些接口本身不能证明支持按任意历史版本查找。

**推荐**：先用普通只读共享对象替代 CAORS handle，保留已有确切版本索引及租约语义。
后续区分“旧引用自然保活”和“管理器可查找全部历史版本”：前者作为默认能力，
后者仅由已有确切版本消费者要求，不能为了统一而给每种资源加历史数据库。
缓存键至少保留真实来源域、类型、URI 和影响结果的配置，持久化不使用 `type_index`。

**优缺点**：可以立即删除 handle 套 shared_ptr，而不改变历史；版本索引仍有成本。
仅保留 URI 最简单，但历史重做和来源切换行为会变，必须另行明确取舍。

**验收**：同源同版本共享；不同源/依赖/配置隔离；新版本不原地改旧对象；历史释放后可回收。
优先级 P0 持有替换，P1 索引收敛。

### A4：整批替换与失败原子性

**现状**：准备批次、版本采用和场景绑定合作，避免材质已换而纹理未就绪；失败保留旧状态。
Granit 示例发布解码结果，不承担 World、GPU 或编辑事务。

**问题**：若 manager 负责所有提交，就会向上依赖场景/编辑器；若直接逐项替换，则发生半提交。

**他人做法**：Granit 示例明确将 GPU 上传与模型切换放在应用侧；
Godot 后台加载教程先取 PackedScene，再由调用者实例化并加入场景。
该例仅说明职责分离，不能证明其多资源替换提供与 Gneiss 相同的事务保证。

**推荐**：manager 仅发布完整 CPU 结果；Runtime 保留候选与安全点提交，Render 保留 GPU 生命周期。
复用现有事务，不移植进通用 manager；按输入替换、单材质、场景切换分别限制事务范围。

**优缺点**：底层可保持简单，场景仍正确；高层必要的准备/回滚不会随换库消失。
逐项更新代码更少，但有可观察半成功状态，不推荐。

**验收**：依赖缺失、上传失败、提交前取消均不改变活动使用者；成功整批可见；无残留 RID。
优先级 P0，迁移全程保留。

### A5：准备成功、发布缓存与实际采用

**现状**：固定版本可先发布，而默认选择需在场景接受后改变；有跨推进步骤的采用准备对象。

**问题**：`ready`、缓存当前项和活动场景版本容易混淆；为 CPU 资源也机械引入完整场景状态机会过重。

**他人做法**：[Flax Content](https://docs.flaxengine.com/api/FlaxEngine.Content.html)
提供异步加载；[Asset](https://docs.flaxengine.com/api/FlaxEngine.Asset.html) 提供加载状态与等待。
这些接口描述资产状态，不足以证明已完成场景采用。Granit manager 同样只发布 CPU 值。

**推荐**：明确 manager 的 ready 只表示 CPU 数据可读；GPU ready、场景 adopted 留给对应使用者。
先保留已存在的选择事务，后续逐个调用点检查是否只需“持有候选并切换引用”，
能删除状态时同时删除相应存储，不能把原状态机换个名字再加一层。

**优缺点**：各层完成条件清楚；调用者仍须组合进度。把所有阶段塞进一个 handle 表面统一，
会把 GPU、场景和编辑状态带入底层，不推荐。

**验收**：CPU ready 后上传失败、候选被替换、采用取消都不错误更新场景或默认选择。
优先级 P1 审查，迁移时保留现有行为。

### A6：分步推进、取消与分步清理

**现状**：[asset_preparation](../../src/engine/resource/loaders/asset_preparation.hpp) 有读取/摘要预算，
Runtime 有旧场景退休与分步清理；部分解析仍为单项同步调用，不保证单步硬时限。

**问题**：示例零线程 inline 执行可能令 `load()` 发起阶段阻塞；观察者取消也不代表任务已清理。

**他人做法**：Granit 的 worker 与 main completion 分开，但 inline worker 仍在调用线程执行；
Godot 后台加载使用线程避免常规加载阻塞，不能据此推断无线程平台自动具备相同响应性。

**推荐**：注入现有任务执行器，保留宿主协作推进和通知；区分请求取消、停止无消费者工作、
完成清理三个条件。保留已有逐步读取/清理，先测最坏单步，再考虑解析器可中断化。
关闭先停止新请求、取消观察、推进/等待实际任务终态，再销毁 Source/Loader；
不能丢弃完成回调后让请求永远停在 loading，也不能为等待退出而隐式驱动任意宿主业务。

**优缺点**：保留 Web 和主循环响应；需修改示例的具体任务系统依赖及关闭协议。
新建独立线程池较易接线，但重复调度且不能解决无线程平台，不推荐。

**验收**：线程/协作两模式、关闭中读取、晚到回调、取消一个观察者不影响其他请求、
全部观察者退出、队列拒绝、缓存清除期间在途请求、主循环最大间隔。优先级 P0。

## 两项横向问题

### A7：编辑历史是否保留确切旧资源

**现状**：Mesh 历史捕获前后租约，Prefab 快照保留来源及渲染绑定，存在异步历史操作。
**问题**：历史可延长 CPU/GPU 资源寿命；但这不是创建 manager 就必须具备的能力。
**他人做法**：[Godot EditorUndoRedoManager](https://docs.godotengine.org/en/stable/classes/class_editorundoredomanager.html)
按场景管理历史并提供引用保留接口；不能据此推断它保存磁盘资产任意旧版本。
**推荐**：依赖替换阶段保持历史语义；单独测历史保留字节，再比较确切资源引用、作者值快照、
仅 URI 重载三种策略。优点是改依赖不影响用户操作；缺点是暂时保留内存成本。
URI 策略简单，但源文件变化后重做结果不同，属于待决定的产品行为，不自动实施。
**验收**：替换后修改/删除来源，再撤销重做；清空历史释放资源；失败不移动历史位置。优先级 P1。

### A8：重复缓存、构建与跨库成本

**现状**：CAORS 请求缓存、CPU 文档索引、版本缓存分担不同工作，且存在双重持有包装；
原生分发还包含 CAORS DLL。并非所有缓存都是重复：CPU 与设备资源不能机械合并。
**他人做法**：Granit 示例用一个请求表与 `shared_ptr<const T>`，但不处理我们的 GPU/版本事务。
**推荐**：为每个索引列出键、值、所有者、回收条件和消费者；只合并同一职责。
迁移完成后移除 FetchContent、链接、安装包依赖、DLL 分发、探针选项和过期边界规则。
**优缺点**：减少依赖与适配；移植维护由 Gneiss 承担，需防止积累另一套无人维护的通用框架。
**验收**：干净离线/在线配置、共享/静态安装及 C/C++ consumer；启用/关闭 Granit 平台；
生产源码与生成安装包不含 CAORS 依赖，历史记录不删除。优先级 P0。

## 验证、成本与未决项

命令以[构建指南](../guides/building.md)为准。先运行资源/输入相关测试、边界负向检查和格式检查；
影响安装后执行共享/静态、C11/C++20 独立头及 C/C++ consumer；Web 至少覆盖既有协作/MEMFS 闭环。
迁移前后使用同输入、构建配置与场景测加载时间、主循环最大间隔、峰值内存、缓存命中、
磁盘读取字节及 CPU/GPU 引用释放，不能用少量样本或单纯删除行数宣称加速。

估算：R1 中到大（同步和取消语义），R2 中（持有与生命周期），R3 中（构建矩阵）；
R4 的不可变导入产物与历史策略可能较大，不在调用点和基线完成前承诺工期。

尚待 R0 明确：最小移植文件清单；失败缓存何时重试；全部观察者取消后任务是否继续为缓存填充；
缓存是否弱持有或有界强持有；现有 URI 直接加载与来源版本键如何避免双重权威。
这些实现选择可在现有授权范围内通过源码和测试确定；改变同步成功条件、历史恢复结果、
来源变化检测强度等可观察行为，须先说明具体差异，不能以换库名义默默改变。
