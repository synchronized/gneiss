# VER-014：0.14.0 Editor UI 工作区

## 状态

- 状态：实现中
- 目标版本：0.14.0
- 优先级：P0
- 路线图阶段：Editor UI 工作区

## 背景与目标

0.13.0 已建立可调整大小的 Editor 窗口、浮动工具面板、顶部运行控制栏和 Console，但现有 Dear
ImGui 版本不提供 Docking。面板位置依赖普通窗口状态，运行工程或改变主窗口尺寸后容易产生遮挡、
越界和布局不稳定，也无法形成 Unity、Godot 一类编辑器的固定工作区体验。

0.14.0 将编辑器 UI 从单体入口中的零散调用整理为内部 `gneiss_editor_ui` 模块，并接入固定提交的
Dear ImGui Docking 分支。版本完成后，Hierarchy、Assets、Scene View、Inspector 和 Console 可以
在单窗口主 DockSpace 中拖动、拆分、吸附和恢复默认布局；用户布局按工程隔离并安全持久化。

## 非目标

- 不自研通用 GUI 框架，也不替换 Dear ImGui 渲染和输入适配。
- 不实现游戏内 HUD、菜单或资产化 Runtime GUI；未来 `gneiss_gui` 与 Editor UI 分开规划。
- 不启用 Dear ImGui Multi-Viewport，不创建脱离主窗口的原生平台窗口。
- 不建立任意第三方插件 ABI、动态面板插件或脚本化编辑器扩展。
- 不在本版本展开完整多语言、复杂字形回退、字体资产导入或无障碍系统。
- 不改变 Scene、ECS、Runtime、Game Module 或公共 C ABI 的职责边界。

## 已确认决策

- 采用 [ADR-027](../decisions/ADR-027-editor-ui-workspace.md) 的单窗口 DockSpace 与内部模块边界。
- `gneiss_editor_ui` 是 Editor 私有静态库，不安装、不导出，不进入 `gneiss_engine` 或公共头文件。
- 业务面板可以继续使用 Dear ImGui API，但主窗口、DockSpace、命令栏、布局和通用控件由 UI 模块
  统一管理；不构造含义模糊的通用 GUI 抽象层。
- 布局属于用户状态而非工程内容。布局文件存入现有用户配置根下，使用规范化工程路径的稳定摘要
  隔离，不写入工程目录或场景文档。
- 默认布局由代码确定性构建；布局文件缺失、损坏、版本不兼容或超出可见区域时回退默认布局。
- Dear ImGui 依赖继续锁定精确提交、关闭不使用的示例后端，并保持第三方类型不泄漏到普通接口。

## 实施顺序

### M-89：Editor UI 边界与依赖 Spike

确认当前 Dear ImGui 来源、补丁和许可证，选择官方 Docking 分支的精确提交。建立最小 DockSpace
Spike，验证现有 Gneiss UI Draw List 可以正确处理 Docking 生成的裁剪、索引和多 Draw List，且不
需要修改 Granit。形成依赖记录和可回退结论。

当前进展：已将 Dear ImGui 从主分支 `v1.92.9b` 切换到官方 Docking 分支精确提交 `fd13a1e`，启用
Docking 并建立最小单窗口主 DockSpace。Windows VS2022 Shared Debug 编译和四项 Editor 工作流测试
通过，现有 UI Draw List 与 Granit Canvas 无需修改。M-89 已完成，详见
[M-89 Docking Spike 记录](../records/M-89-editor-ui-docking-spike.md)。

### M-90：`gneiss_editor_ui` 内部模块

提取 Context 初始化、字体、主题、帧适配、主菜单栏、运行控制栏及通用图标按钮。模块只依赖 Editor
内部状态和现有 Gneiss UI Draw List，不拥有 World、Scene Session、Runtime Process 或业务面板数据。
为 Context 生命周期、零尺寸过渡帧和布局路径计算增加测试。

当前进展：已建立不安装、不导出的 `gneiss_editor_ui` 静态库，统一拥有 ImGui Context/帧适配、字体、
主题、主 DockSpace 和无业务状态的工具栏图标按钮。`gneiss_editor` 只链接该模块，Runtime Process、
Scene Session 和面板数据仍由应用层持有。Windows 编译及 Project Manager、Editor、Runtime Process、
Lantern Gallery 五项工作流测试通过；零尺寸过渡帧继续由既有 smoke 路径覆盖。M-90 已完成。

### M-91：单窗口 DockSpace 与默认工作区

建立覆盖主客户区的主 DockSpace。默认布局为左侧 Hierarchy/Assets、中央 Scene View、右侧
Inspector、底部 Console，顶部菜单和运行控制栏保持固定。首次启动和恢复默认布局使用同一确定性
构建函数，窗口缩放后不让面板落到可见区域外。

当前进展：已使用稳定 DockSpace ID 和 DockBuilder 建立确定性五区布局，Hierarchy 与 Assets 位于
左侧上下区域，Scene View 居中，Inspector 位于右侧，Console 位于底部；顶部菜单和运行控制栏先于
DockSpace 提交。五个主要面板已移除绝对初始坐标，默认布局只在 Dock 节点不存在时构建，不覆盖当前
会话的手动调整。Windows 编译和四项 Editor 工作流测试通过。M-91 已完成。

### M-92：布局持久化与恢复

在用户配置根下按工程保存版本化布局。使用临时文件和原子替换写入，限制文件大小；损坏或未知版本
不阻止 Editor 启动。增加 `Window > Reset Layout`，并覆盖首次启动、保存重载、工程隔离、损坏恢复、
只读配置目录和旧布局迁移。

### M-93：面板迁移与视觉基础

将 Scene Hierarchy、Asset Browser、Scene View、Inspector 和 Console 迁入 Dock 节点，移除普通浮动
窗口的初始绝对坐标。统一字体采样、DPI、图标几何、间距、最小面板尺寸、选中/悬停/禁用对比度，
保持 Catppuccin 风格但优先保证可读性。

### M-94：工作流与跨平台验收

验证工程选择、场景编辑、资产导入、Runtime 启停、Console、主窗口缩放、布局保存和恢复默认布局。
覆盖 Windows/Linux、共享/静态、构建树和安装树；无头测试必须使用确定性默认布局，不依赖开发机
已有的 ImGui 状态文件。

## 测试与验收

- 第一次打开任意工程时得到确定的五区默认工作区，主要面板均可见且可操作。
- 面板可拖动、拆分、吸附和形成标签页；关闭后可从菜单重新打开。
- 重启同一工程恢复布局，打开另一工程不会误用前一工程布局。
- 损坏、过大、只读或版本不兼容的布局文件不会导致 Editor 启动失败。
- `Reset Layout` 在当前帧安全清理旧状态，并在下一帧恢复默认工作区。
- 1280×720、高 DPI 和主窗口最小化/恢复不会产生零尺寸致命错误或永久越界面板。
- Runtime 运行、停止及 Console 日志不会改变 Dock 拓扑或挤乱面板。
- 公共 C/C++ 头、Engine、Runtime 和不构建 Editor 的配置不依赖 Dear ImGui Docking 类型或宏。
- Windows/Linux 代表性矩阵与安装后 Editor 工程通过。

## 风险与未决问题

| 风险或问题 | 当前处理 |
| --- | --- |
| Docking 分支不是稳定发布分支 | 锁定精确提交并记录升级验证，不跟随浮动分支 |
| `imgui.ini` 格式由第三方维护 | 外层增加 Gneiss 布局版本与大小校验，不把内容作为公共格式 |
| 布局路径包含工程隐私 | 文件名只保存稳定摘要，映射信息留在用户配置状态中 |
| 面板迁移继续膨胀 `main.cpp` | 以业务面板为单位提取渲染函数和状态接口，不复制运行时状态 |
| Docking 需要 Granit 新能力 | 先用现有 Draw List Spike 验证；确有通用缺口时只向用户提出 Granit PR 建议 |
| UI 抽象过度限制 ImGui | 只封装工作区策略与重复控件，不隐藏全部 ImGui API |

## 完成条件

- M-89～M-94 全部完成并形成 0.14.0 验收记录。
- 默认 Docking 工作区、工程隔离持久化和恢复默认布局形成稳定闭环。
- 现有 Editor 创作、Runtime 和 Console 工作流无功能回归。
- 依赖锁定、许可证、布局所有权、失败恢复和跨平台行为均有文档与自动化验证。
