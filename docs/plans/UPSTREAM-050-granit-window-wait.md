# UPSTREAM-050：窗口事件等待与跨线程唤醒

## 状态与审计范围

2026-10-07，U50-01 为待评审建议，尚未提交上游 Issue/PR，未修改 Granit。
用户负责上游提交，Gneiss 已独立实现有限条件变量等待并继续验收；不能将此建议描述为已经接入的能力。
范围见 [VER-050](VER-050-0.50.0-main-loop-latency.md)，证据见 [M-318](../records/M-318-main-loop-observation.md)。

已核对实际构建使用的 Granit 0.44.0（369adc7ebc9e202056c5d583bfd8d65243de6a4d），
另只读核对上游 main 提交 cff4b48eb7038ba60dc5698f21129bb7c13867e2 的窗口公开头与循环实现。
[公开窗口接口](https://github.com/synchronized/granit/blob/cff4b48eb7038ba60dc5698f21129bb7c13867e2/include/granit/window/window.h)
提供 process_events 与队列 poll，没有带截止期限的事件等待和跨线程 wake。
[窗口循环实现](https://github.com/synchronized/granit/blob/cff4b48eb7038ba60dc5698f21129bb7c13867e2/src/window/window_loop_api.cpp)
在原生 IDLE 路径 sleep_for(16 ms)，浏览器使用宿主回调；不具备任务完成后立即唤醒等待的契约。
此审计仅针对上述提交，不表示所有后续上游版本都缺少此能力。

## U50-01：可唤醒的有限事件等待

- 目标：在没有立即可做的工作时阻塞等待，并由窗口输入、宿主通知或截止期限结束等待。
- 通用性：编辑器、模型查看器、独立渲染线程宿主均可复用；不涉及 Gneiss 场景、资产、RID 或调度策略。
- 建议 PR 标题：Window：增加有限事件等待与线程安全唤醒。
- 当前影响：Gneiss 已使用进展通知与有限等待减少重复轮询，但窗口输入仍依靠截止期限重新检查，
  不能直接唤醒条件变量。本需求让原生窗口事件也参与唤醒，不是已经证明的全部卡顿修复。
- 按 [ADR-059](../decisions/ADR-059-main-loop-progress-wait.md)，不作为 0.50 有限等待的前置。

## 建议最小接口与行为

建议在 Window 模块提供下列 C API 及对应轻量 C++ 包装，最终命名以 Granit 评审为准：

```c
/* 接口草案，尚未实现。timeout_ms 为有限毫秒期限，0 为非阻塞检查。 */
granit_result granit_window_system_wait_events(granit_window_system system, uint32_t timeout_ms);
/* 可从工作线程通知所属窗口线程；不执行用户回调。 */
granit_result granit_window_system_wake(granit_window_system system);
```

- wait 只允许窗口所属线程调用。窗口消息、已排队的 Window/Input 事件、wake 或超时均可使其返回；
  返回成功不保证存在事件，调用者仍须检查自己的工作队列。允许提前返回，不承诺硬实时唤醒上限。
- 等待不消费公开事件队列、不调用引擎逻辑、不提交 GPU 工作，也不把任务模型引入 Granit。
  SDL 等后端若需要接收原生事件才能等待，必须保存事件供后续正常处理，不能丢失或重复。
- wake 可在线程间调用。先于 wait 到达的通知须保留到下一次 wait，不能在“检查队列→开始等待”之间丢失。
  多次通知允许合并；它是重新检查宿主队列的信号，不是任务计数器。
- 句柄失效和错误线程调用明确返回错误。宿主销毁窗口系统前停止通知来源；
  与销毁竞争的 wake 不得访问已释放对象。失败与重复通知不得令后续等待永久卡死。
- C++ 包装不创建第二个运行时或线程，不暴露 HWND、HANDLE、SDL 或平台描述符。
- 首先覆盖 Win32 与实际支持的原生后端。暂不支持的后端明确返回 unsupported；
  浏览器主线程不得阻塞，继续采用宿主帧回调，不能退化为忙循环冒充等待实现。
- 超大期限的溢出/无穷等待语义必须在上游明确；建议首版仅接受有限期限，避免平台哨兵值混用。

## 上游验收

1. 无事件等待可超时；timeout=0 不阻塞；错误线程和失效句柄返回明确错误。
2. 原生窗口输入能够结束等待，后续 process_events/poll 的事件内容与顺序保持。
3. 用同步屏障覆盖 wake 先到、等待中到达及检查/等待边界竞争；重复运行不得丢通知。
4. 多工作线程并发 wake 可合并，关闭/失效路径不悬挂、不访问释放资源。
5. 空闲期间 CPU 明显下降，同时有输入与后台通知的唤醒观测；不能用单次 sleep 时长替代功能测试。
6. C11、C++20 包装与相关原生后端回归；浏览器明确保持非阻塞语义。

## Gneiss 接入方案与保留事项

由窗口适配层转接等待/唤醒，宿主决定下一次更新期限；任务与渲染 Service 仅发送就绪通知。
等待前检查本地就绪工作，唤醒后重新检查队列；任务提交、取消、上传回执、IPC 退出和窗口输入
都必须有可验证的到达路径。cooperative 有可运行步骤时不能阻塞等待自己。

需要先用 ADR 明确宿主更新节奏、通知对象寿命和退出顺序，再接入，不改公共 Application ABI。
不能只等待 GPU：启动、无相机、最小化及没有渲染包时仍须处理输入、IPC 与任务。
原生与浏览器的等待策略分开，数据所有权、候选预算和取消/清理契约保持。

CPU 下降、加载吞吐和响应性共同验收；不能把循环次数减少直接描述为帧率提高。
历史 129 ms、窗口泵的偶发长耗时及系统调度因素仍需独立归因，不因接入等待自动标记为已修复。
