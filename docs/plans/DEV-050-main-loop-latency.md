## M-318

先审计旧测量语义。保留 0.49 间隔字段，新增明确起止点的原始样本，不静默替换旧指标。
测试宿主主动 sleep、scheduler.run_ready、poll_scene_load 单独计时，回调外间隔暂列未分解。
随后根据样本细分引擎事件、渲染提交与回收；用采样调用栈区分执行和等待。

详细诊断默认关闭，记录最后未闭合间隔，避免把未知值当作零。

## M-319 与 M-320

### 已冻结的 CPU 与吞吐门槛

2026-10-07，在生产等待策略改动前，依据同设备日常/完整各三次关闭诊断基线，
先冻结消除重复轮询这一方向的门槛。数值证据以 [M-318](../records/M-318-main-loop-observation.md)
及其 CPU 归档为准；这不等同于 M-319 的长间隔归因和交互门槛已经完成。

- 同设备、同输入和缓存策略，优化后两种规模各至少三次；以关闭诊断的组中位数判定 CPU 和吞吐。
- 主线程 CPU 时间 / 进程墙钟时间的组中位数不高于 0.25，即平均不超过四分之一个核心。
- 日常和完整场景进程耗时中位数分别不超过对应基线的 110%；不通过延后激活或提前退出获得通过。
- 整个进程 CPU 时间中位数不超过对应基线的 105%，避免把忙轮询简单转移到其他线程。
- 采样工作集峰值不超过相同规模三次基线最大值的 110%；此为回归警戒线，
  仍须独立保留 2 GiB 候选预算与 GPU 资源生命周期检查，不能用进程采样替代资源账本。
- 实际 Runtime 诊断对照保留全部超限计数，三次加载不得出现超过 100 ms 的引擎循环；
  该门槛仅用于固定设备回归，不承诺跨设备硬实时，也不以缩短采样范围获得通过。

窗口输入与任务到达的响应夹具已补齐，取消/清理沿用 0.49 门槛，补充见文末。
通知生命周期决策见 [ADR-059](../decisions/ADR-059-main-loop-progress-wait.md)。最长 128 个循环不能代替全量分位数，
不能把 CPU 降低当作旧 129 ms 已修复。上游等待能力仍为待评审建议。

## 响应门槛与归因边界补充

2026-10-07，生产等待策略修改前完成独立发送线程的响应基线：三次普通样本各 64 次按键、
64 次后台任务及一次窗口关闭全部接收；输入最大 22.72 ms，任务最大 22.58 ms，关闭最大 0.0126 ms。
注入 50 ms 主线程停顿的正对照捕获输入 71.47 ms，确认发送线程不会跟随被测主循环一起停顿。
证据见[响应基线](../records/artifacts/0.50-response-baseline.json)。

冻结同夹具输入和任务接收 P95 <= 33.3 ms、最大 <= 100 ms，关闭接收 <= 100 ms；
按键投递到 Gneiss 输入接收计时，不宣称真实硬件端到端延迟。大资产交互与既有生命周期矩阵仍须复测，
取消终态 <= 250 ms、实际清理 <= 1000 ms 沿用 0.49 门槛，不因等待策略放宽。

内核采样权限缺失不通过绕过权限解决；已取得的线程 CPU 计数与源码足以确认重复轮询，
本版仅针对这一可验证问题实施修复。偶发长间隔的未解释残余保留为限制，不宣称全部消除。
有限等待及生命周期决策在实施前记录 ADR；上游事件等待不是有限条件变量等待的前置，
但没有上游接口时窗口输入/IPC 只能按有限截止期限重新轮询，不能宣称立即唤醒。

## 后续定位补充

改用可复查的第三方时间线作为后续定位入口，边界见
[ADR-060](../decisions/ADR-060-optional-cpu-profiler.md)。实施顺序：

1. 增加默认关闭的 Tracy 构建开关和进程内共享 client，保留优化符号。
2. 标记主循环、事件、场景推进及任务提交/执行/终态/接收，以 owner + task id 关联。
3. 验证开关两侧的构建、生命周期、安装消费者与一次保存/读取采集文件的闭环。
4. 用完整资产采集异常时间窗，再决定修复；GPU 内部标记和插件 API 不在本次范围。

保留 CSV 冻结门槛与既有失败；profiling 结果不作为性能达标替代。

用户要求从主线程实际工作继续分析，调用路径审计和待验证细分计时见
[M-319 记录](../records/M-319-main-thread-path-audit.md)。先拆分任务提交的取锁/锁内工作与
循环等待的初次取锁/条件等待，保留原完整循环口径；不以新增插桩宣称偶发长间隔已修复。

协作来源复验已记录单次哈希调用 157.03 ms。已将协作资产准备与来源复验的单次字节预算
从 16 MiB 降至 4 MiB，线程池保留 16 MiB；这是任务块大小调整，不是硬实时保证。
服务级测试与完整场景首载预验收通过，后续复测完整协作矩阵，保留首轮失败和吞吐变化。
未完成复测前不将该调整描述为解决资产阶段 257.69 ms 超标。

输入探针关联已将一轮加载末段的延迟定位到场景推进。构建器细分、线程计数、入口栈与
不暂停线程的页面驻留对照支持继续调查冷代码首次执行路径；尚未解释原始 266.238 ms。
预取对照未支持直接加入生产预热；随后新的超标样本已关联到首次复验任务提交外层，
取锁与锁内耗时很小。补齐提交函数体、回调构造和 executor 调用观测后优先沿该路径定位，
不直接加入平台专用预热或无锁队列。实验、限制与发布阻塞统一归档于 M-321。
