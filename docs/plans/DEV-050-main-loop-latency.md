### 已冻结的 CPU 与吞吐门槛

2026-10-07，在生产等待策略改动前，依据同设备日常/完整各三次关闭诊断基线，
先冻结消除重复轮询这一方向的门槛。数值证据以 [M-318](../records/M-318-main-loop-observation.md)
及其 CPU 归档为准；这不等同于 M-319 的长间隔归因和交互门槛已经完成。

- 同设备、同输入和缓存策略，优化后两种规模各至少三次；以关闭诊断的组中位数判定 CPU 和吞吐。
- 主线程 CPU 时间 / 进程墙钟时间的组中位数不高于 0.25，即平均不超过四分之一个核心。
- 日常和完整场景进程耗时中位数分别不超过对应基线的 110%；不通过延后激活或提前退出获得通过。
- 整个进程 CPU 时间中位数不超过对应基线的 105%，避免把忙轮询简单转移到其他线程。
- 采样工作集峰值不超过相同规模三次基线最大值的 110%；此为回归警戒线，
  仍须独立保留 2 GiB 候选预算与 GPU 资源生命周期检查，不能用进程采样替代资源账本。
- 实际 Runtime 诊断对照保留全部超限计数，三次加载不得出现超过 100 ms 的引擎循环；
  该门槛仅用于固定设备回归，不承诺跨设备硬实时，也不以缩短采样范围获得通过。

尚需补齐窗口输入、取消/清理和任务到达的响应夹具与基线，再冻结相应门槛及通知生命周期 ADR。
M-320 在这些前置完成前不修改生产等待策略；最长 128 个循环不能代替全量分位数，
不能把 CPU 降低当作旧 129 ms 已修复。上游等待能力仍为待评审建议。
