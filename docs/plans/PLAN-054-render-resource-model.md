## 背景与现状

| 当前实现 | 问题 | 本轮推荐处理 |
| --- | --- | --- |
| render_asset_ref 是缓存 entry 的强引用 | 调用方需要额外辨认资源类型 | 对外返回类型化引用；只有证明确有必要时才保留缓存内部类型擦除 |
| mesh_asset、texture_asset、material_asset 隐藏在 Loader 实现中 | RID 所有者及其析构约束不明显 | 迁移为明确的运行资源对象，不叠加第二套所有者 |
| mesh_resource 是 mesh_data 的别名 | 资源身份与顶点数组混用 | mesh_resource 表示身份，mesh_data 表示 CPU 负载 |
| material_resource 保存纹理 RID，material_asset 另存纹理强引用 | 材质参数和依赖所有权分散 | 运行材质保存参数及纹理强引用，后端生成 RID 绑定 |
| texture_resource 混有元信息、负载、恢复来源及上传弱引用 | 长期状态与临时上传数据混杂 | 分离运行对象、任务数据和明确保留的恢复数据 |
| render_resource_service 保存 CPU 内容，render_service 保存 GPU mirror | 查询、更新、回收跨多个入口 | 资源表和 GPU 记录逐步收进 render_service 实现 |
| 场景实例持有资源租约，ECS 和 render_snapshot 保存 RID | 快照本身不保活资源 | 组件和提交快照直接持有资源强引用，后端另行保活在途内容 |

## 目标和本轮范围

本轮只完成阶段一、二：建立类型化运行资源，统一 Render 生命周期。
继续使用现有 asset_ref、统一缓存、异步文件读取和 CPU 解码机制；保留现有 CPU 恢复能力。
业务、ECS 和 Render 上层输入统一使用资源强引用；RID 收到 Render 内部，Granit 类型保持在其私有实现。
普通加载成功与进度只覆盖文件读取、CPU 解码及本次请求约定的 CPU 内容就绪，不等待 GPU 上传。

非目标：本轮不做 Mip/LOD 需求调度、预算驱逐、虚拟纹理、GPU 剔除、持久化渲染实例、
任意 Shader 材质系统、公共对象 SDK 或跨资源事务；不为迁移另建缓存、线程池和全局对象注册表。
不以改名替代职责迁移，不强制所有运行资源继承通用 Object 或注册反射。

## 参考实践与取舍

| 实践 | 可借鉴点 | 本项目取舍 |
| --- | --- | --- |
| Godot Resource 与 RenderingServer | 上层资源引用持有依赖，服务内部维护渲染状态 | 保留此边界，暂不复制其常驻渲染实例体系 |
| Unity 可选 CPU 副本 | 资源存活与大块 CPU 字节驻留是不同决策 | 本轮先保留恢复数据，后续具备异步重建才允许释放 |
| Flax 数据按需获取 | 可从资产存储、CPU 缓存或 GPU 取得数据 | 优先异步文件重读，不把 GPU 回读作为当前必要能力 |
| O3DE Asset 与运行实例 | 可保存数据与运行状态分离 | 区分职责，但不机械复制完整 Asset/RPI/RHI 类型层级 |

收益：身份稳定，所有权集中，后续流送不改变调用方引用。
代价：需要迁移 Loader、ECS 组件和帧提交路径，组件不再平凡可复制，并明确线程及服务关闭规则。

## 已确认对象模型

以下对象模型已在阶段一、二落地；精确当前契约见 [Render Reference](../reference/render.md)。

| 对象 | 持有内容 | 明确不承担 |
| --- | --- | --- |
| *_description | 可序列化设置、资源来源和依赖定位 | GPU 句柄、任务状态 |
| mesh_resource | 稳定 RID、包围盒/布局/数量等轻量信息 | 把顶点数组当成自身身份 |
| texture_resource | 稳定 RID、尺寸/格式/Mip 元信息 | 隐含持有全部高清 Mip |
| material_resource | RID、参数、texture_resource 强引用 | 跨资产原子提交 |
| mesh_data / texture_data | 拥有型 CPU 字节和解码结果 | URI 缓存身份 |
| Render 私有记录 | 当前后端对象、在途上传、GPU 使用和释放状态 | 文件读取、场景和编辑器语义 |

不是每类资产都必须同时新增四个文件或四个类。元信息需要区分未知与有效，不能把未完成加载的默认值视为有效尺寸。
现有 material_description、texture_description 优先复用；网格来源描述是否需要独立类型，取决于现有格式的真实需求。

```text
规划关系：
asset_manager：来源域 + URI + 类型 → 稳定运行资源
                               ↑ asset_ref<T>
业务 / ECS / 帧快照 → mesh_resource / material_resource → texture_resource
                               ↓ 内部 RID
                  render_service 私有资源记录 → Granit 对象

文件服务 → CPU 解码 → 临时 *_data → 上传任务
                                   └→ 本轮明确保留的恢复数据
```

上层使用以下只读强引用别名：

```cpp
using mesh = asset_ref<const mesh_resource>;
using texture = asset_ref<const texture_resource>;
using material = asset_ref<const material_resource>;
```

不为了统一管理而强行类型擦除。可在同一个资产管理器内按类型分表，保持相同去重和加载规则；
只有真实异构操作需要时才保留最小擦除边界，不新增通用资源基类或反射前提。
运行对象暴露只读查询和受控修改入口。不允许任意修改字段后依赖偶然的地址变化更新 GPU。
共享材质修改影响全部使用者；实例独立外观通过显式创建独立运行材质实现，保存时转为 description。
网格暂时维持现有实例材质绑定方式；多 Surface 和默认材质槽在多材质模型需求落地时扩展。

## 加载、更新和错误语义

1. 首次请求由统一管理器去重，返回稳定类型化资源身份；引用非空不代表 CPU/GPU 已就绪。
2. 文件服务异步读取，解码器只处理 CPU 数据；本次请求约定的 CPU 内容就绪即加载成功。
3. 普通加载百分比只包含 I/O/CPU 工作；删除向普通调用方传播的 GPU 上传百分比和完成等待。
4. Render 独立安排上传，内部保留完成/失败回执及暂存字节保活；提交不等于可绘制。
5. Mesh 尚不可用时跳过绘制；Texture 尚不可用时使用默认纹理；材质依赖逐步就绪。
6. 重载 CPU 失败保留旧 CPU 内容；CPU 成功后，GPU 更新失败仍保留旧 GPU 内容并记录渲染诊断，
   不把已经完成的 CPU 加载改成失败，也不承诺 CPU/GPU 内容始终同时切换。
7. 请求序号拒绝迟到结果；销毁目标使未采用结果失效。“加载成功”和“当前可绘制”必须区分。

缓存负责查找，加载任务负责 I/O/解码状态，Render 负责后端可用性；不要复制互相独立的 ready 标志。
允许当前 GPU 内容和一次在途更新，不建立版本树、候选 RID、批量发布或回滚协议。
上传错误和统计保留在 Render 诊断中；需要精确等待的工具以后单独设计，不污染普通加载 API。
CPU 加载不必等待所有依赖 GPU 就绪；依赖的 CPU 完成条件由具体类型加载契约明确，
例如材质参数和纹理引用可以先就绪，纹理自身仍在加载，不能伪报整个依赖树完成。
未来流送按请求区分描述加载与 Mip/LOD 负载加载，不把完成定义为全部高清数据常驻。

## 所有权与线程契约

- ECS 组件、业务和上层帧快照直接保存 mesh/material/texture 强引用；节点仍通过实体 ID 关联组件。
- 删除仅为组件 RID 补充保活的平行场景资源集合；确有预加载用途的资源集合可保留并明确用途。
- 材质保活纹理依赖；序列化保存资源来源标识，不保存指针、引用计数或内部 RID。
- ECS 必须支持非平凡组件的构造、复制、移动和析构；禁止把这些组件按原始字节复制或持久化。
- 强引用只保证存活，可变元信息和参数仍由所属线程更新；工作任务不任意修改共享资源。
- 缓存策略集中一处，可沿用 release_unused；缓存及上传任务的强引用同样计入存活条件。
- 帧快照的资源引用保活逻辑对象；Render 接收帧后还必须固定具体后端内容，
  否则重载替换后端对象仍可能影响旧帧。按现有帧/上传完成机制释放，不新增版本协议。
- 内部 RID 撤销后拒绝后续查找；已接收工作继续安全持有旧后端内容直至完成。

## 销毁队列决策

采用应用级资源销毁队列，处理 mesh_resource、texture_resource、material_resource 的最终析构。
理由：现有 asset_ref 基于 shared_ptr，最后释放可以发生在 ECS 工作任务或渲染帧释放线程；
隐藏资产析构目前会访问资源服务，直接在任意线程执行不适合新模型。
不将所有 asset_ref 强制改成延迟销毁：纯 CPU 的 *_data、解码结果和 description 继续普通 RAII。

规划路径：

```text
任意线程释放最后一个强引用
  → 自定义删除器仅登记待销毁对象（不执行析构、不访问服务）
  → 主线程安全点消费队列
  → 析构运行资源，释放材质依赖，撤销/释放内部后端关联
  → Render 执行器在所属线程处理后端释放
  → GPU 在途使用结束后回收实际资源
```

- 删除器安装在资源创建时的唯一 shared_ptr 控制块，复用现有 asset_ref；禁止第二控制块和裸指针重建引用。
- 引用计数归零时弱引用立即不能重新锁定；物理内存可以稍后回收。队列接管待销毁对象的唯一清理责任。
- 多生产者、单主线程消费者即可，初版使用短临界区和预留/内嵌队列节点，无需无锁通用调度器。
- 入队路径 noexcept 且不再分配内存；不能在分配失败时退回工作线程析构服务相关对象，不能静默丢弃销毁请求。
- 主线程释放也统一排队，避免递归析构；取出一批后解锁再析构，材质释放纹理产生的新项进入后续批次。
- 每帧固定安全点处理，可限制每批数量；关闭阶段持续排空到依赖级联结束，不依赖下一帧继续消费。
- 队列端点独立保活，不强持有应用或服务。入队/关闭需要同一同步协议，防止关闭检查后仍向无人消费的队列写入。
- 正常析构会发出后端释放命令，但主线程不直接销毁要求渲染线程执行的 Granit 对象；
  主线程队列不替代已有后端命令队列或 GPU 完成同步。

关闭顺序：停止接收请求、取消/收尾生产任务、释放场景及缓存引用、收尾在途帧与上传、
主线程排空资源队列及后端释放，再关闭服务。服务管理的记录必须能统一失效，
残留资源对象只通过端点/内部标识关联服务，不能保存可在关闭后解引用的服务裸指针。

明确关闭后的例外：服务完全关闭且端点转为 detached 后，残留外部引用的最后释放允许在任意线程
析构已经无服务依赖的 CPU 外壳及其依赖引用，不能再发服务调用。与关闭竞争的释放要么被队列接收并排空，
要么走 detached 路径，不得泄漏。运行对象析构不能有其他未经迁移的主线程副作用。
因此保证是“运行期间资源对象在主线程销毁、后端在正确线程安全回收”，而不是要求已经退出的主线程继续工作。

### 调用点审计与保留边界

| 调用点 | 本轮结果 | 保留原因 |
| --- | --- | --- |
| Loader `acquire_mesh/material/texture` | 返回类型化强引用，同步/异步共用准备与采用入口 | 不再另写解析路径 |

| 最后释放与关闭 | 一个控制块、一个预分配销毁节点；关闭后禁止复活槽位 | 后端仍沿用 Granit 的 GPU 延迟回收 |

| 四：基础流送 | 先可定位 Mip 数据，再网格 LOD；验证格式范围读取和后端上传能力 | 同一资源引用/RID 下逐步改变驻留，具备预算、优先级与逐出规则 |
| 五：性能扩展 | 根据测量决定增量渲染实例、并行剔除或 GPU 剔除 | 有明确瓶颈和收益，不与资源模型强绑定 |

后续最终目标：强引用保持资源身份与依赖，不固定全部 GPU 驻留；业务持续使用同一资源，
流送只调整当前可用精度。元信息加载、初始可用、目标质量达到是不同事实。
本轮不承诺分块文件格式、恢复一致性或流送预算已经实现。

## 风险与实施前需落实的细节

- 收拢服务不能形成 asset_manager → Render 的底层反向依赖，类型加载器仍由功能层装配。
- 队列节点布局、每帧消费点、帧保活载体和实际 GPU 完成点实施时核对；不得重复建设现有 GPU 完成机制。
- 本轮默认保留 CPU 恢复数据，不提前实施 discard_after_upload；避免迁移同时破坏设备恢复。
- 文件重读可能得到修改后的内容，阶段三需定义恢复采用最新文件还是固定导入产物，不能暗中重建来源版本协议。
- 多设备/多 profile 缓存身份需先审计现有行为；本轮不新增多设备能力，但不能错误复用不兼容后端数据。
- 程序生成资源没有 URI，应走相同运行对象与 Render 创建路径，不伪造文件来源。
- 如果缺少 Granit 通用底层能力，按仓库约定提出最小上游需求，由用户提交；本计划不授权跨仓库修改。
