# VER-015：0.15.0 Editor–Runtime 双向控制通道

## 状态

- 状态：计划中
- 目标版本：0.15.0
- 优先级：P0
- 路线图阶段：Editor–Runtime 双向控制通道

## 背景与目标

0.14.0 已完成 Editor 工作区，现有独立 Runtime 进程能够接收工程参数、输出结构化日志并通过停止文件
正常退出，但 Editor 不能准确区分连接、加载、运行和暂停状态。0.15.0 将建立私有 libuv 异步 I/O
基础和版本化本机 IPC，使 Editor 能驱动 Runtime 的 Play、Pause、Resume 和 Stop，并可靠接收状态、
日志、错误和退出原因。

版本完成后，Lantern Gallery 应能由 Editor 启动为独立 Runtime：完成鉴权握手后报告 Ready 和
Running，暂停时停止游戏逻辑更新，恢复后继续，停止或故障后向 Editor 给出明确结果，并可重复建立
全新会话。

## 非目标

- 不建立公共 Network Service，不实现 UDP、DNS、TLS、公网连接或远程设备调试。
- 不把 Runtime 渲染表面嵌入 Editor，不同步场景、属性或后端资源。
- 不实现游戏模块热重载、多 Runtime 管理或脚本调试协议。
- 不替换现有结构化日志文件、标准流、退出码与强制终止降级路径。
- 不建立 Stable IPC ABI；Transport、协议和 libuv 后端保持内部 Experimental。
- 不开展自研 GUI、完整字体、多语言或复杂字形回退。

## 已确认决策

- 采用 [ADR-028](../decisions/ADR-028-editor-runtime-ipc.md) 的 Editor Server、Runtime Client 和
  专用 I/O 线程模型。
- 首版使用仅绑定回环地址的 TCP；系统分配端口，每次运行使用独立会话 ID 和随机令牌。
- `uv_runtime`、Transport 与业务协议分层；libuv 是私有实现依赖，不进入普通公共接口。
- 主线程不直接操作 libuv handle，I/O 回调不直接访问 Engine、Scene、ECS、ImGui 或游戏模块。
- 协议使用显式有界帧和版本协商；首版负载采用 JSON，未知兼容消息可以跳过。
- 进程状态、IPC 连接状态和游戏运行状态分别建模，不压缩为单一 `is_running` 布尔值。

## 实施顺序

### M-95：IPC 架构与协议 Spike

验证回环监听、Runtime 连接、跨线程投递、消息分帧、断线检测和无泄漏关闭。形成 libuv 依赖记录，
明确锁定版本、MIT 许可证、Fetch/Package 策略、Shared/Static 行为及安装传播边界。Spike 只验证风险，
不创建公共 API。

状态：已完成基础依赖与线程模型验证，结果见
[M-95 Editor–Runtime IPC Spike 记录](../records/M-95-editor-runtime-ipc-spike.md)。TCP 分帧与断线验证按
分层边界进入 M-97，不在 Spike 中保留一次性实现。

### M-96：libuv I/O Core

实现内部 `uv_runtime`：专用线程、`uv_loop_t` 生命周期、`uv_async_t` 唤醒、定时器、错误映射和有界
任务队列。关闭流程必须停止接收新任务、关闭全部 handle、运行关闭回调、关闭 loop 并 join 线程。

状态：已完成。多生产者投递、并发 Stop、析构排空、错误映射和关闭竞态结果见
[M-96 libuv I/O Core 实施记录](../records/M-96-libuv-io-core.md)。Transport 所需的具体 handle 继续由
M-97 在该线程所有权模型上扩展。

### M-97：IPC Transport

实现 Server、Client、异步读写、帧解码、连接事件与有界发送队列。Transport 只处理字节和连接，不
理解 Play 等业务语义。限制单帧、缓存、队列与每帧事件预算，并保证控制消息不被日志洪水阻塞。

### M-98：Editor–Runtime 协议

实现 `hello`、`hello_ack`、`ready`、`state_changed`、`pause`、`resume`、`stop`、`log_event`、
`error`、`ping`、`pong` 和 `shutdown_complete`。覆盖令牌验证、主次版本协商、能力集合、未知消息、
非法帧、握手和心跳超时。

### M-99：Runtime 控制状态机

建立 Starting、Connecting、Loading、Ready、Running、Paused、Stopping、Exited 和 Failed 状态。
Pause 只暂停固定更新和逐帧游戏逻辑；平台事件、IPC、诊断和必要渲染继续工作。Editor 失联超过
约定时间时，由 Editor 启动的 Runtime 安全退出。

### M-100：Editor Play 工作流

顶部控制栏绑定真实状态：构建、连接、运行、暂停、停止与失败分别提供明确反馈。Console 接收 IPC
结构化事件，同时保留标准流原文。IPC Stop 超时后复用 `child_process` 强制终止，并允许再次 Play。

### M-101：示例与跨平台验收

为 Lantern Gallery 增加可观察的运行逻辑，验证暂停后状态保持、恢复后继续、正常停止、崩溃诊断和
重复会话。完成 Windows/Linux、Shared/Static、构建树、安装树和 libuv handle/线程退出验收。

## 测试与验收

- 单元测试覆盖帧的半包、粘包、未知消息、超长负载、版本不兼容和令牌错误。
- 并发测试覆盖跨线程提交、队列满、关闭竞态、活动定时器和未完成写入。
- 进程测试覆盖监听失败、连接失败、握手超时、Runtime 启动或运行中崩溃、Editor 先退出、Stop 无响应
  和重复启动。
- Play、Pause、Resume、Stop 必须产生真实游戏逻辑效果，不能只切换按钮状态。
- Windows 与 Linux 使用相同行为测试；Shared/Static 配置不得向普通 Consumer 泄漏 libuv 类型或
  不必要链接依赖。
- Runtime 仍可不带 Editor 独立从命令行启动；无 IPC 时不得把未来能力描述为已经连接。
- 最终形成 0.15.0 验收记录，并在发布前手动执行所需远端矩阵。

## 风险与未决问题

- libuv 获取策略需结合 Granit 和 Gneiss 当前依赖树确认，避免同一进程出现两个不兼容实例。
- JSON 控制负载先以可诊断性为主；只有性能证据出现后才评估二进制负载。
- 停止信号文件在 IPC 故障矩阵稳定后再决定移除时间，不在首个实现提交中删除。
- 命名管道、Unix Domain Socket、场景同步和远程调试留给独立后续版本，不扩张本计划。
