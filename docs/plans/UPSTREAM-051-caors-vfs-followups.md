## C51-08：重挂载与缓存一致性

### 当前事实与问题

依据：`docs/guides/async-vfs-integration.md`、`include/caors/resources/database.h`、
`src/caors/resources/source.cpp`。同一次加载使用来源快照，已有 GUID 的在途操作沿用首次来源和调度；
remount 不自动使缓存失效，需要显式 reload 或独立资源上下文。
这是当前契约，不应直接视为错误；自动替换所有资源也不是本议题的预设答案。

研究场景：同 URI 从目录 A 重挂载到目录 B，GUID 不变；A 的缓存或加载仍存在时，
调用者需要明确选择继续使用 A、加载 B，或将默认绑定切换到 B，而非偶然加入旧请求。

### 可选方案

| 方案 | 优点 | 限制 |
| --- | --- | --- |
| 保持现状，补充 reload 的完整契约 | 改动小，宿主控制切换 | 必须能明确表达旧请求仍在途时的重新加载 |
| 显式失效/刷新，按来源修订区分在途请求 | 共享缓存可保留，避免新请求误用旧来源 | 需处理迟到结果及原子发布 |
| 按来源/版本组织独立资源上下文 | 隔离明确，适合多个项目同时打开 | 共享、内存和上下文管理成本更高 |

建议先验证第一种是否足够；不足时补第二种的最小显式操作，不默认全量自动刷新。
失效、驱逐缓存、取消加载、销毁对象是不同操作，公开接口不得混用这些含义。

### 必须确定的契约

- 普通 request_load、显式 reload、失效后首次 load 各自选择哪个快照和缓存版本。
- 旧 load 尚未完成时，reload 是否使用新来源；哪些请求共享，哪些必须独立。
- 同 GUID 的两个 reload 先后开始、反序完成时，谁有资格更新默认绑定；旧完成不能覆盖新选择。
- 准备失败或取消保留旧可用对象；成功在所属线程发布，外部旧强引用仍安全。
- 来源标记、provider 配置修订、内容修订的作用不同；磁盘原地修改不会必然改变挂载标记。
- 依赖资源刷新是仅根资源、明确依赖闭包还是由调用者选择；不能静默混合未定义的来源版本。
- 如果只承诺单资源发布，不宣称提供跨资源/场景事务；批次原子性继续由宿主协调。

### 验收

1. A 已缓存，重挂载 B：普通加载与显式 reload 各自行为符合所选契约。
2. A 在途，重挂载 B 并发起刷新：结果来源可验证，不能静默共享错误来源。
3. A/B 两次操作反序完成：旧操作不覆盖已发布的新选择。
4. B 失败、取消、完成队列拒绝：旧 A 保持可用，无半发布或永久 pending。
5. 外部继续持有 A 的 handle，B 发布后 A 仍可安全使用和释放。
6. 材质/纹理等通用模拟依赖场景，明确依赖闭包是否刷新；测试不依赖 Gneiss 类型。

## C51-09：分块读取与逐块消费

### 当前事实与问题

`src/caors/io/async_file.cpp` 的 `read_all_bounded()` 当前将整个文件大小作为单次
`request_read()` 长度。它限制总结果大小，但没有自动分块；后端限制小于文件长度时也需明确处理。
现有 request_read 已支持精确范围，不需要另一套文件打开或路由系统。

### 两种能力必须分开

| 能力 | 返回值 | 内存语义 |
| --- | --- | --- |
| 分块聚合读取 | 完整 byte_buffer | 限制单次 I/O，最终结果仍占文件大小量级内存 |
| 逐块消费 | 消费回调/受控消费协议及最终状态 | 已消费块可释放，辅助缓冲受块大小与在途数限制 |

建议复用现有 request_read 实现串行分块，不强制先设计复杂异步流框架。
是否扩展 read_all_bounded 或新增 helper 由上游决定，但不能改变旧调用的完整结果含义。
逐块消费可作为独立后续提交；需要降低内存峰值的调用者不能用聚合读取冒充流式处理。

### 建议最小行为

- 调用者设置总字节预算、块大小上限；有效块大小同时受文件后端 max_read_size 限制。
- 不固定 1 MiB；检查零块大小、长度溢出、offset 越界和 size_t 可表示性。
- 首版最多一个在途块；读取 N、消费并确认 N 后才申请 N+1，形成自然背压。
- 块按偏移顺序交付；回调只能借用块到返回，或明确转移所有权，不能使用有效期不明的 span。
- 若允许异步消费者，必须显式确认/释放当前块后推进，取消能终止等待；不隐式排队全部块。
- 消费在指定 executor 上执行，不在 libuv 回调中做重型解析；拒绝/丢弃进入可观察失败终态。
- 单块内部短段由既有精确读取累计，提前 EOF 返回 short_read；完整处理才报告成功。
- 进度单调并注明统计读取完成还是消费完成；不把已排队字节算成已完成。
- 取消不继续启动新块；在途请求和迟到回调依原协议清理，析构不等待 I/O。
- 消费者错误与读取错误均有唯一终态；已经产生的消费副作用不会自动回滚，调用者自行暂存再提交。
- helper 借用拥有式文件 handle，不关闭调用者共享文件；若另提供打开即消费的便利接口，必须说明关闭责任。

### 验收

1. 模拟大文件且后端单次上限很小：每次请求不超过上限，最终内容/摘要正确。
2. 零文件、恰好整块、非整块尾段、EOF、截断、超总预算与分配失败。
3. 逐块消费使用不保留内容的摘要消费者：峰值缓冲随块大小/在途数受限，不随文件总长增长。
4. 聚合读取明确测得完整结果内存，不声明等同于逐块消费的内存特性。
5. 慢消费者不导致无界预读；消费者拒绝、异常和执行器关闭均能收尾。
6. 取消前、块间、读取中、消费中与最终完成竞争：唯一终态，无泄漏和重复消费。
7. 即时完成/inline executor 处理大量小块时不发生递归栈增长；使用迭代推进或受控调度。

## C51-10：来源快照复制成本

### 当前事实与待测影响

`src/caors/resources/source.cpp` 的 `provider::snapshot()` 遍历 `locations_`，
为各 GUID 构造位置副本并写入快照映射，使用 snapshot_context 捕获路由。
该路径具有随绑定数增长的工作量；尚未测出它在 Gneiss 场景中的耗时或主线程影响。
不能仅凭源码就把它称为当前卡顿根因。

### 基准方案

- 数据规模：1 千、1 万、10 万绑定；更大规模在内存允许且有实际需求时扩展。
- 覆盖单后端、多后端、嵌套路由、长短路径、依赖预加载共用快照。
- 分别测首次捕获、无修改重复捕获、单次 rebind/remount 后捕获、连续修改后捕获。
- 同时测试 cache 命中与在途请求共享是否触发捕获，避免把不执行的路径算进成本。
- 记录耗时分位数与最大值、分配次数/字节、峰值内存、旧快照保留内存、更新耗时。
- 在实际调用线程测量捕获成本；Windows/Linux Release 固定编译器、机器和样本次数。
  Debug 可用于正确性，但不与 Release 混作性能结论。

### 比较方案

| 方案 | 收益假设 | 必须解决的问题 |
| --- | --- | --- |
| 当前全量复制 | 实现直接，语义明确 | 用实测判断是否足够 |
| 同修订复用不可变快照 | 重复加载时少复制 | 复用条件必须覆盖 provider 和嵌套路由变化 |
| 写时复制/结构共享绑定表 | 小更新少复制，快照捕获轻量 | 写入成本、内存滞留和同步复杂度 |
| 仅捕获请求依赖闭包 | 小请求避免复制全表 | 动态依赖和后续解析是否仍保持同一次快照语义 |

建议先试可验证的修订复用，不为尚未测得的成本直接引入复杂持久化容器。
只检查 provider 自身 generation 不够：绑定未改但底层 resolver remount 时也必须捕获新路由。
若无法观察外部可变 source，应明确不复用、冻结配置或要求显式修订通知，不能返回陈旧快照。
内容变化检测仍属于内容/资产层，不能用路由 generation 代替文件摘要。

### 验收

- 优化前后使用同一工作负载，提交原始数据及比较结果，不预设无依据的耗时门槛。
- 无变化时确实减少复制/分配；变化后不会错误复用旧路由。
- 旧快照继续解析旧来源，新快照解析新来源；并发读取和配置更新遵守既有线程契约。
- 嵌套 remount、provider rebind/unbind、配置替换、来源销毁均有回归。
- 不把捕获开销无条件转移为更大的每次写入停顿；明确保留多个快照的内存上界或限制。
- 故障注入、循环路由、模块 pin 与 allocator 寿命测试继续通过。
