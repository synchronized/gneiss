# VER-025：0.25.0 Granit 0.7 与独立渲染线程

## 状态

- 状态：设计中
- 目标版本：0.25.0
- 优先级：P0
- 路线图阶段：渲染执行与上传可观察性

## 背景与目标

当前 Application 创建并直接调用 Granit Render Service，窗口事件、Scene/ECS 更新、GPU 资源同步、
命令录制、提交和 Present 位于同一主循环。GPU 上传或帧槽等待会阻塞窗口消息和 Editor 交互。

0.25.0 先把 Granit 依赖升级到 0.7.0，再参考 Granit Model Viewer 已验证的执行模型，让桌面平台由
常驻渲染线程独占 Granit GPU 对象。主线程提交有界、不可变的帧包和不可丢弃命令，并异步取得完成
回执、上传进度和失败诊断。Editor 与 Runtime 复用同一 Engine 内部实现。

## 非目标

- 不复制或公开 Granit Model Viewer 的示例私有执行器。
- 不新增公共 Render Thread C ABI，也不向公共接口泄漏 Granit 类型。
- 不实现多个渲染线程、多 GPU、多窗口并行渲染或通用任务系统。
- 不引入无锁队列、协程调度器、后台 Shader 编译或 GPU 驱动内部逐字节进度。
- 不改变 Scene Tree、ECS、资产格式、RID 编码或 Editor–Runtime IPC 协议。
- 不让 Worker 线程创建、修改或销毁 GPU 对象。

## 已确认决策

- Granit 0.7.0 升级作为线程改造的独立前置里程碑，先验证 API、依赖解析和完整构建矩阵。
- Application 主线程继续拥有窗口事件、输入、Scene/ECS 更新及 Editor UI 构建；渲染线程独占
  Renderer、Swapchain、Pipeline、GPU 资源镜像、上传、命令提交和 Present。
- 每次提交的帧包拥有该帧的 Camera、可见实例、Transform、动态参数、UI 和 Debug Draw 数据；
  Mesh、Texture 等稳定资源只携带 RID 与修订，不复制资源正文。
- “不可变”表示提交后数据不再被生产者改写，不限制动画等内容逐帧变化。动画每帧产生新的姿态
  快照；后续可用回执管理的多缓冲帧槽减少复制。
- 队列区分可替换的 Frame 与不可丢弃的 Command。Frame 积压时替换最旧的未执行帧并保留最新帧；
  Command 满载时返回 `not_ready`，由生产者重试或报告过载。
- 资源创建、上传、修订替换、销毁、Resize 和恢复均按序列号进入命令边界。完成队列返回结果、
  阶段进度和诊断；GPU 资源成功创建前，现有有效 RID 投影保持不变。
- Resize、Surface Lost 和需要改变交换链或 Pipeline 的操作使用排空屏障；关闭遵循停止生产、排空、
  渲染线程释放 GPU 对象、停止线程并 Join 的确定顺序。
- 详细所有权和队列语义见
  [ADR-038](../decisions/ADR-038-render-thread-ownership.md)。

不借用 Scene/ECS、ImGui 或下一帧可变内存，并保持当前渲染结果不变。

状态：待开始。

### M-164：有界渲染任务队列

状态：待开始。

### M-165：GPU 所有权与上传命令迁移

让桌面渲染线程唯一调用 Granit GPU 接口，依次迁移初始化后的 Renderer 状态、资源镜像创建与销毁、
Upload Batch、帧获取、录制、提交和 Present。CPU 解码仍可留在调用线程或既有 Worker 边界。

状态：待开始。

### M-166：上传进度与失败原子性

按资源准备、命令排队、批次提交和完成确认发布可查询进度。覆盖上传失败、队列过载、过期修订和
连续替换，确保失败不会破坏现有有效资源投影，并接入现有诊断与日志。

状态：待开始。

### M-167：窗口恢复与确定关闭

把 Resize、最小化、Surface Lost、运行停止和初始化中途失败纳入排空边界，保证窗口消息持续响应、
没有跨线程 Granit 调用，并验证资源逆序销毁与线程 Join。

状态：待开始。

### M-168：Editor、Runtime 与跨平台验收

使用 Lantern Gallery 覆盖 Editor 场景视图、独立 Runtime、资源热重载和结构热重载；记录队列等待、

Sanitizer 验证。

状态：待开始。

## 测试与验收

- Granit Fetch、PACKAGE、父工程目标与旧默认缓存升级路径均锁定并验证 0.7.0。
- 帧包在源 Scene/ECS、动画姿态和 UI 数据进入下一帧修改后仍保持提交时内容。
- Frame 队列覆盖 FIFO、满载替换和完成回执；Command 队列覆盖不丢失、过载重试和相对顺序。
- Renderer、Swapchain、Pipeline、GPU 镜像及 Upload Batch 只在指定渲染线程访问。
- 上传失败保留旧资源；成功回执后 RID 对应的后端投影一次性切换到新修订。
- 持续上传、窗口拖动、Resize、最小化和关闭期间主线程继续处理事件且不会死锁。
- 同步执行边界与线程执行边界的场景、UI 和 Debug Draw 结果一致。
- Windows/Linux Clang/GCC Shared/Static、Granit Runtime Shared/Static、安装消费和 Sanitizer 通过。

## 风险与未决问题

- 现有资源服务的 CPU 数据与 Granit 后端镜像需要明确拆分；不得简单把整个资源服务移到渲染线程。
- SDL Surface 恢复可能要求访问主线程拥有的 Window；M-162 审计 Granit 0.7.0 契约后确定排空握手。
- Upload Batch 同步提交只能把等待移出主线程，不能提供驱动内部真实百分比；首版进度只表达 Gneiss
  已确认的阶段和工作量。
- UI 与 Debug Draw 深拷贝可能增加 CPU 成本；先记录基线，再决定是否引入回执管理的帧槽。
- 浏览器或不允许独立渲染线程的平台保留同步执行器，首版不承诺 Web 多线程。
