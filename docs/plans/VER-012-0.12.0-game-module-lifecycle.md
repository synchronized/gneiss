# VER-012：0.12.0 游戏模块与生命周期

## 状态

- 状态：实现中
- 目标版本：0.12.0
- 优先级：P0
- 路线图阶段：游戏模块与生命周期

## 背景与目标

0.11.0 已建立按工程启动的独立 Runtime 宿主及 Editor 进程隔离工作流，但运行内容仍只有 Engine
内建的场景、输入和渲染更新。0.12.0 要让工程提供独立编译的游戏逻辑模块，并由 Runtime 以确定的
生命周期调用。

版本完成后，示例工程应能在不修改 `gneiss_runtime` 的情况下加载游戏模块，根据输入更新场景对象，
并在 Editor 启动的独立 Runtime 中运行。模块加载失败和生命周期失败必须进入现有阶段化日志链路。

## 非目标

- 不引入 Lua、C#、WebAssembly 或其他脚本运行时。
- 不实现动态库热重载、状态迁移或旧代码地址修复。
- 不允许模块依赖 Editor、ImGui、资产导入 SDK 或 Granit 原生类型。
- 不向模块开放任意 Engine 内部对象、后端句柄或跨线程直接访问。
- 不实现完整项目生成器、发布向导、游戏打包或崩溃恢复。
- 不在 0.12.0 将 Game Module ABI 标记为 Stable。

## 已确认决策

- 使用 [ADR-025](../decisions/ADR-025-native-game-module-boundary.md) 定义的原生动态模块与单一 C 查询入口。
- Engine Library 提供 Experimental Game Module C ABI；C++20 只提供轻量包装和示例辅助层。
- 工程文件保存平台无关模块基名，Runtime 在工程根内解析本机动态库，不通过 VFS 加载可执行代码。
- Runtime 拥有主循环、Game Context 和调用顺序；模块拥有私有状态。
- 固定更新使用累加器和有界追帧次数；逐帧更新每帧至多调用一次。
- Editor 首版通过停止、构建、重新启动独立 Runtime 迭代，不承诺进程内热重载。

## 实施顺序

### M-77：Game Module ABI 契约

定义 C11 可独立包含的 Experimental 头文件、ABI 版本、描述结构、单一查询符号、回调签名、Game
Context 句柄和错误规则。补充 C/C++ 头文件测试、旧/新结构大小、缺失回调、版本不匹配和异常模块
描述测试。

当前进展：已增加 C11 `game_module.h`、C++20 轻量包装、Game Context 定宽句柄、更新计时结构、单一
查询入口类型和四个生命周期回调。Engine 描述校验覆盖结构大小、ABI 版本、模块标识、必需回调和
保留字段；C/C++ 行为测试、独立头文件编译和 API 稳定性清单均已通过。M-77 已完成。

### M-78：Runtime 模块加载与生命周期

增加隔离的动态库后端及 Runtime 编排层。覆盖文件缺失、符号缺失、ABI 不匹配、初始化失败、更新
失败、正常关闭和提前退出；保证库在最后一个回调完成且模块状态销毁后卸载。

当前进展：已增加 Win32/POSIX 原生动态库后端与不支持平台回退，以及 Runtime 独占的模块会话。
会话完成固定查询入口解析、描述校验、初始化、更新、幂等保护和析构关闭；自动化夹具已覆盖文件或
符号缺失、ABI 不匹配、初始化与更新失败、正常关闭、重复关闭和提前退出析构顺序。M-78 已完成。

### M-79：Game Context 与受控 Engine 访问

让模块通过借用 Game Context 获取当前 World、输入动作状态、退出请求和启动场景根实体。首版只开放
示例闭环必需能力，每项访问都明确有效期、线程限制和失败行为，不建立第二套服务注册表。

当前进展：已增加 Engine 持有的 generation Game Context 注册表和 C/C++ 访问接口，复用现有
Application 提供 World、动作查询、动作状态与退出请求，并保存启动场景首个作者根实体。Runtime 在
场景加载后创建 Context、在场景卸载前销毁；测试覆盖正常访问、跨线程拒绝、销毁失效和重复销毁。
M-79 已完成。

### M-80：固定步长与逐帧更新调度

在 Runtime 主循环加入固定更新累加器、最大帧间隔和最大追帧次数。记录丢弃积压时间的诊断，测试
零间隔、长帧、稳定帧率、更新失败和退出请求，避免“死亡螺旋”。

当前进展：已增加独立 Runtime 更新调度器，默认固定步长约 60 Hz、最大接受帧间隔 250 ms、单帧
最多追赶 8 次。调度器会报告帧裁剪与丢弃积压，固定更新失败时跳过逐帧更新，逐帧更新每帧至多
一次；测试覆盖零间隔、累加、长帧裁剪、追赶上限、积压丢弃、重置和回调失败。M-80 已完成。

### M-81：Editor 构建与运行工作流

工程存在 Game Module 时，Editor 在运行前检查模块产物及新旧状态，调用可配置但受约束的 CMake
构建入口，成功后启动 Runtime。构建输出进入独立区域；构建失败不得关闭作者会话或启动旧模块。

当前进展：工程格式 v2 已增加可选 Game Module 基名、工程内产物目录及受约束的 CMake preset/target，
同时保留 v1 无模块工程兼容。Runtime 已完成本机文件名映射、工程根包含校验、加载初始化、帧调度、
失败日志和逆序关闭。Editor Run 会异步执行固定 CMake preset/target，构建成功并重新验证产物后才
启动 Runtime；构建失败或中止不会启动旧模块，输出保留在 Runtime Output。测试覆盖构建失败不启动、
构建成功后启动、显式停止及真实动态库工程 smoke。M-81 已完成。

### M-82：可交互示例、安装与跨平台验收

为 Lantern Gallery 或新建最小工程增加游戏模块，通过输入移动或旋转场景对象并支持确定性 smoke。
验证 Windows/Linux、Shared/Static、构建树、安装树、模块 ABI 失败矩阵和 Runtime 重复启动。

当前进展：Lantern Gallery 已升级为 v2 模块工程，工程级 `input_map` 会在场景和模块之前加载；独立
动态模块通过 `move_horizontal` 动作旋转不包含相机的灯笼根节点，A/D 可交互且 smoke 确定。构建树
工程提供 Editor 可调用的 `game-debug` preset；安装树携带预构建模块、模块源码和只依赖安装 SDK 的
CMake 工程，并已在 Windows Debug 中完成重新配置、构建和 Runtime smoke。Linux、Static 及完整
回归矩阵仍待验证，M-82 尚未完成。

## 测试与验收

- C11 查询 ABI 和 C++20 包装可独立包含，Shared/Static Consumer 均可编译运行。
- Windows/POSIX 动态库后端覆盖成功、路径越界、缺失文件、缺失符号、重复卸载和仍有回调时拒绝卸载。
- 生命周期顺序固定，初始化失败不调用更新，初始化成功后关闭恰好一次。
- 固定更新在模拟长帧下有界，不无限追帧；逐帧更新不会因固定更新次数而重复。
- 模块只能在 Runtime 主线程借用 Game Context；保存借用对象或跨线程访问有明确拒绝行为。
- Editor 构建失败、模块过期、运行失败和停止后重建均有自动化覆盖。
- 示例无需修改 Runtime 源码即可交互，并从隔离安装树运行。
- 代表性 Windows/Linux 手动 Actions 通过后形成 0.12.0 验收记录。

## 风险与未决问题

| 风险或问题 | 当前处理 |
| --- | --- |
| Experimental ABI 过早膨胀 | M-79 只开放首个交互示例需要的访问能力 |
| Windows DLL 被占用导致重建失败 | Editor 必须先停止 Runtime 进程，再调用构建入口 |
| 模块回调阻塞主循环 | 首版限定主线程同步调用并记录耗时；任务系统另立计划 |
| 固定更新长帧产生死亡螺旋 | 限制帧间隔和单帧追帧次数，记录积压丢弃诊断 |
| 模块路径成为任意代码加载入口 | 只接受工程根内平台映射后的原生文件，并规范化校验路径 |
| 模块状态引用已销毁 Engine 对象 | Engine 先停止更新并调用模块关闭，再销毁场景、World 和 Application |
| 静态链接游戏需求 | 原生模块构建期要求 Shared Engine；静态宿主保留生命周期语义，另立 ADR 设计 |

## 完成条件

- M-77～M-82 全部完成并形成 0.12.0 验收记录。
- 至少一个独立游戏模块在 Windows/Linux 由 Runtime 和 Editor 工作流运行。
- 模块 ABI、生命周期、所有权、线程限制和失败语义均有文档与自动化测试。
- 构建树和隔离安装树的模块工程均不依赖 Gneiss 源码路径。
