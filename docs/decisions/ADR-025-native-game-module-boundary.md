# ADR-025：原生游戏模块与 Engine 生命周期边界

- 状态：已接受
- 日期：2026-08-31

## 背景

`gneiss_runtime` 已能从工程入口加载场景，但工程逻辑仍固化在宿主或专用示例中。若每个游戏都修改
Runtime，宿主会逐渐包含项目代码；若立即引入脚本语言，则需要同时决定 VM、绑定、调试、热重载和
资产格式，无法先验证 Engine 对游戏逻辑提供的最小边界。

## 决策

- 0.12.0 首版使用原生动态 Game Module；脚本运行时未来作为另一类模块接入。
- 模块只导出一个固定名称的 C 查询入口。入口返回带 `struct_size`、ABI 版本、模块标识和生命周期
  回调的描述结构，不导出 C++ 类或第三方类型。
- 生命周期最小集合为 `initialize`、`fixed_update`、`update` 和 `shutdown`。初始化成功后才允许更新，
  关闭最多调用一次；失败结果不得穿过 C ABI 抛出异常。
- Engine 创建并拥有 Game Context。模块只借用上下文及其中的 World、输入和场景访问能力，不持有
  Granit 原生对象、Editor 状态或宿主内部指针。
- 模块私有状态由模块创建和销毁，Engine 仅原样传回对应回调；模块卸载前必须先执行 `shutdown`。
- 工程描述保存平台无关的模块基名，Runtime 按平台映射动态库前后缀并只允许加载工程根内的原生
  文件。动态库不经 VFS、HTTP 或 Packed Filesystem 加载。
- 首版 ABI、工程字段和加载协议均为 Experimental。每次加载都校验 Engine ABI 版本、描述结构大小、
  必需回调和模块标识。
- Runtime 仍是唯一主循环所有者；模块不能自行驱动 Application、创建第二套 Engine 状态或阻塞事件
  循环。
- 0.12.0 不支持二进制热重载。Editor 通过停止 Runtime、重新构建模块并启动新进程完成迭代。

## 影响

- 游戏逻辑可以独立于 Runtime 和 Editor 编译、部署与失败隔离。
- C 查询入口降低编译器和 C++ ABI 差异，但 Experimental ABI 变化仍要求重新编译模块。
- 平台动态库加载需要 Windows/POSIX 后端和明确的错误阶段、路径及卸载顺序测试。
- 固定更新由 Runtime 调度，模块只接收确定的步长；逐帧更新接收受上限约束的帧间隔。
- 脚本、静态链接游戏和热重载可以复用生命周期语义，但需分别建立后续 ADR。

## 替代方案

- 将游戏源码直接链接进 `gneiss_runtime`：构建简单，但每个项目都要生成专用宿主，不能验证模块边界。
- 首版使用 C++ 虚接口：表达方便，但会冻结编译器 ABI、异常和 STL 边界。
- 立即接入 Lua、C# 或其他脚本 VM：最终可能需要，但会让 VM 选择掩盖 Engine 生命周期的基础问题。
- 首版同时支持热重载：需要处理线程、回调、资源和旧代码地址失效，超出最小可验证闭环。
