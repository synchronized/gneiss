# ADR-011：使用 libspng 解码首版 PNG 纹理

- 状态：已接受
- 日期：2026-08-27

## 背景

M-27 需要从 VFS 内存数据解码一种常见、带 Alpha 的无损图片格式，并转换为 Texture 契约要求的
RGBA8。解码器处理不可信资产，必须有明确错误、尺寸校验、许可证和跨平台构建路径。

## 决策

- 首版只承诺 PNG，采用 libspng `0.7.4`，使用 BSD-2-Clause 许可证。
- 使用 miniz `3.1.2` 提供 Deflate，使用 MIT 许可证，避免 Windows 依赖系统 zlib。
- 两项依赖均锁定标签对应提交，通过独立 CMake target 接入，不安装头文件、不导出链接依赖。
- 仅启用内存解码和 RGBA8 输出；编码、流式解码、浮点输出及其他图片格式不进入本版本。
- 解码前后执行 Gneiss 自有尺寸与 256 MiB 上限校验；第三方错误转换为稳定结果码和内部诊断。

## 影响

依赖范围与 `0.4.0` 用例一致，且 libspng 持续接入 OSS-Fuzz。代价是新增两个内部 C 依赖，未来支持
JPEG、HDR 或压缩纹理时需要独立解码器或离线内容管线，不能假设 libspng 是通用图片层。

## 替代方案

- stb_image `2.30`：单头文件且格式丰富，但格式面超出当前范围，错误与颜色管理能力较弱。
- Wuffs：内存安全、性能好且支持 PNG，但首版低层 API 和生成代码集成成本明显更高。
- LodePNG：无外部依赖且接口简单，但没有稳定发布标签，Gamma/颜色管理与模糊测试证据较弱。
- 系统 libpng：成熟但 API 与跨平台依赖传播更复杂，不适合当前最小 Fetch 构建。
