# ADR-026：结构化日志事件与进程传输边界

- 状态：已接受
- 日期：2026-08-31

## 背景

Runtime 已有启动阶段文本日志和轮转文件，Editor 也能捕获独立 Runtime 的标准输出，但两者没有稳定
事件边界。Game Module 若直接写文件或标准流，会绕过 Engine 的来源标记、线程约束和 Editor 会话
管理；若复用诊断回调，又会混淆“Engine 报告已识别事件”和“组件主动记录运行信息”的语义。

日志同时跨越公共 C ABI、Game Module、Engine、Runtime 子进程和 Editor UI，需要先确定所有权、背压
与传输边界，再扩展具体界面。

## 决策

- Engine 定义不可变日志事件。首版字段包含版本、严重级别、来源、分类、UTF-8 消息、时间戳、线程
  标识和可选结果码，不提供任意键值集合。
- 公共提交接口只借用字符串指针，并在返回前复制必要数据；调用方不持有事件或 Sink。C++ 包装仅提供
  强类型和 `std::string_view` 便利接口。
- 日志提交可由多个线程调用，事件进入有界队列；Sink 投递串行执行。队列满时丢弃新事件并累计计数，
  后续通过不依赖该队列的降级路径报告。
- Application 诊断保留现有同步回调契约。宿主可以将诊断转换为日志事件，但一次诊断只转换一次，并
  保留模块、分类与结果码。
- Game Module 通过 Game Context 提交日志。Engine 根据已加载模块补充来源，模块不能选择 Sink、日志
  文件或伪造 Engine 来源。
- Runtime 向 Editor 传输时，在标准输出中写入带固定前缀和协议版本的单行 JSON 事件。Editor 只解析
  带前缀行；标准错误、未知版本和普通文本保留为 Raw 输出。
- 文件和控制台格式是内部 Sink 行为，不属于公共 ABI。首版不新增第三方日志依赖，未来可替换内部
  队列或 Sink 实现。

## 影响

- Engine、Runtime 和游戏代码获得统一事件语义，而 Editor 不需要链接 Runtime 内部实现。
- 固定前缀允许现有子进程管道同时承载协议事件和第三方普通输出，无需在首版增加专用 IPC 通道。
- 有界队列避免恶意或失控模块耗尽内存，但使用者必须能观察到丢弃计数。
- JSON 仅用于低耦合的跨进程传输，不成为进程内日志表示或长期存档格式。
- 诊断与日志接口会同时存在，需要 Reference 明确两者用途并测试单向转换不重复。

## 替代方案

- 直接让模块写标准输出或文件：实现简单，但无法可靠标记来源、控制并发和归属 Editor 会话。
- 将普通日志全部改成诊断：接口更少，但普通调试信息没有结果码或 Engine 事件语义，会污染诊断契约。
- 立即引入 `spdlog`：可以提供成熟 Sink，但不能替代公共 C ABI、Game Context 权限和跨进程协议设计。
- 新建本地套接字或共享内存 IPC：吞吐更高，但生命周期、鉴权和平台实现明显超出首版需求。
- 让 stdout 只输出裸 JSON：解析直接，但第三方输出或崩溃文本会破坏协议识别和兼容降级。
