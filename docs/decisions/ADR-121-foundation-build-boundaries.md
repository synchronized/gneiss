# ADR-121：基础模块的构建与符号归属

## 状态

2026-11-17：接受模块划分原则，分阶段实施，进度见
[PLAN-119](../plans/PLAN-119-engine-build-test-layout.md)。

## 背景

历史接口目标转发相同 include 根，平台消费者因值类型目标间接获得数学依赖。
目标数量不是质量指标；目录也不自动构成链接边界。

## 决策

- Core 提供不依赖数学、反射、平台和 Engine 的基础能力；首阶段只有错误文本与 Fatal 实现，
  加上基础头文件使用要求，采用独立静态库 `gneiss::core`。
- `gneiss::math` 与 `gneiss::events` 分别传播数学和事件模板使用要求；
  `gneiss::tasks` 独立提供调度实现。平台库依赖 Core，不因通用错误类型获得 GLM。
- Engine 以构建树 PUBLIC 依赖提供调用者真正需要的基础能力；独立消费者可直接链接对应模块。
  不创建只转发同一组依赖的兼容目标。
- Core 首阶段允许无状态函数在不同链接模块各有实现；Fatal 不保存自己的 handler 状态，
  宿主仍显式安装标准库 terminate handler，库不自动安装。
- 字符串驻留表、运行类型身份表、反射注册表不放进会被多个 DLL 分别链接的静态 Core。
  当前仍由 Engine 提供其正式实现。迁移它们之前须确定唯一共享库所有者及独立导出宏，
  验证跨模块身份一致性，而不是机械搬动源文件。
- value 涉及数学和对象引用，不属于这个最底层 Core。日志完整模块的归属另按实际消费者迁移。
- 本轮不新增安装 SDK：构建树 Core 不导出到安装包；静态 Engine 包含其基础实现。
  数学头文件能力与 Engine 中的数学反射实现区分，不声称数学目录已全部独立。

## 使用与生命周期

宿主链接 `gneiss::engine`，按既有应用入口创建、运行和关闭；任务独立消费者链接
`gneiss::tasks`，提交、接收任务并关闭调度器，不需要 Engine 或数学。
这些构建目标本身不引入运行时初始化、服务对象或额外关闭顺序。
预期失败仍返回 result/error；不可恢复异常沿既有 Fatal 边界退出。

## 取舍

优点是依赖表达实际能力，基础测试无需加载 Engine；减少无意的第三方依赖。
代价是 Core 尚非全部基础类型实现的所有者，不能把此阶段当作完整模块化；
共享状态迁移需要显式 ABI 与所有权设计。避免为了统一库名引入重复注册表。
