# ADR-046：任务调度与 Service 的执行边界

- 状态：已接受，0.39.0 已实现，发布验收中。
- 日期：2026-09-25。

## 背景

渲染执行器、libuv loop 执行器与 0.38 资产工作线程已经分别承担任务排队及生命周期管理。
作者资产后台检查带来第二个通用后台工作场景，继续为每项功能创建线程会重复管理容量、取消和关闭。
另一方面，GPU 对象、事件循环和主线程场景状态各有线程归属，不能靠通用线程池自动获得线程安全。

## 决策

引入 Gneiss 内部任务调度模块，置于基础层，仅依赖标准库和基础错误类型。
Editor/工具宿主持有实例并注入使用它的服务；模块不反向依赖 Editor、Scene/ECS、资产格式、Granit 或 libuv，
不导出新公共 ABI，不要求 Runtime 创建尚无实际消费者的线程池。

Service 持有资源、操作规则与任务作用域；调度器持有执行资源、任务依赖、状态及完成回执。
任务作用域在服务销毁前收尾，任务采用拥有的数据或明确受作用域保护的生命周期，不捕获失效对象。

| 执行域 | 决策 |
| --- | --- |
| 通用后台任务 | 复用有界工作线程池执行可独立处理的哈希、解析和检查 |
| 工程资产串行队列 | 在同一工程内顺序处理写入和索引操作，可借用线程池，不保证固定线程身份 |
| 主线程完成队列 | 消费结果、校验当前文档状态，修改 Scene/ECS、UI 及撤销历史 |
| 渲染执行器 | 保留独立线程及帧包/命令契约，继续独占 GPU 对象 |
| libuv 执行器 | 保留自己的事件循环和线程，禁止在通用池内运行常驻 loop |

统一任务生命周期语义不要求各 Service 继承共同的 `update()` 基类，也不引入中央服务轮询器。
渲染/I/O 本版不强行改用通用任务接口，未来适配需保留其线程亲和性及原有背压规则。

任务依赖只指向先前提交的任务，形成不可变的有向无环关系；依赖等待不占用工作线程。
串行队列用于防止共享资源操作重叠，不代表业务依赖成功；任务失败传播由显式依赖决定。
队列容量包含未完成及尚未回收的结果，拒绝必须可观察；不得无限积压或丢弃已接受任务的完成通知。

调度取消是协作式请求，业务提交许可仍由资产服务控制。已进入提交的工作必须完成或回滚，
调度器不得把正在写入的任务提前报告为已取消。关闭由所有者从工作线程之外发起并等待实际收尾，
主线程结果消费与后台收尾不能形成循环等待。

第一批消费者为 Import Service 和作者资产检查；状态与性能诊断先作为内部查询接口提供。
默认 3 个工作线程、256 个保留任务和最多 2 个并发后台任务；普通任务优先，连续调度 8 个普通
任务后为就绪后台任务让出一次机会。每任务最多 32 个显式前置依赖。延迟任务等待由调度器处理，
不占工作槽；主线程按帧消费结果并驱动下一批有限任务。作者扫描每批最多枚举 8 项，结果未消费
时停止继续提交；后台检查结果不直接修改场景。

具体首版契约、阶段和测试见 [VER-039](../plans/VER-039-0.39.0-task-scheduling.md)。

## 与既有决策的关系

保留 [ADR-038](ADR-038-render-thread-ownership.md) 的渲染所有权规则。
本决策替代 [ADR-045](ADR-045-editor-background-assets.md) 中的“资产执行器独占一条线程”：
当前改为服务拥有任务作用域，调度器提供执行资源；暂存、源修订、提交许可和回滚规则保持不变。
ADR-045 的事务和提交许可规则继续有效；执行资源及作者文件检查位置以本决策为准。

## 影响与替代方案

- 相比每个服务一条线程，可统一容量和诊断并复用执行资源，但依赖、背压和销毁规则需要确定性测试。
- 相比所有工作共用一个池，混合执行域保留线程亲和性，降低长阻塞工作影响窗口和渲染的风险。
- 首版采用简单可验证的任务队列，不预先引入工作窃取、协程或完整 ECS 自动调度；扩展以测量为依据。
- 此决策不消除 Windows Debug 调试堆的进程内争用，也不把不可抢占解析变成可强制中断调用。
