# ADR-057：资产准备的显式分步执行

- 状态：已接受，实施中
- 日期：2026-10-07

## 背景

0.49 初始测量中，完整 Cook 场景的最终来源复验连续耗时约 67 秒。
资产批次还会同步读取和校验纹理来源，单纯限制调度器每帧任务数量不能限制任务体耗时。
需要让资产层在读取、摘要、单项解析和最终复验边界保存进度。
首次分步复测仍有约 3 秒停顿，分项计时确认一次原生 64 KiB ReadFile 耗时约 3.02 秒。
字节切片无法约束系统同步 I/O 的等待时间，因此 Windows 路径还需要可轮询读取。

## 决策

- 使用 Asset 层自有的准备状态和校验游标，执行器只调度一个有限步骤并返回回执。
  不增加线程池、抢占式调度或可重入事件泵，不改变公共 C/C++ SDK。
- 内部 VFS 增加明确用于分步验证的读取入口。该入口只打开来源，不同步扫描全文件；
  调用方在分块计算完整摘要后完成版本登记。普通 open_read 的既有行为保持。
- 版本跟踪包装将验证完成回执传递给嵌套来源，复用同一次完整扫描；登记账本由读取对象
  共享持有，不能捕获可能已销毁的文件系统裸指针。这里只处理通用内容身份，不引入纹理格式。
- 资产准备状态拥有候选数据、来源、摘要进度和依赖列表。材质依赖按单项准备，最后完整复验后
  才提交候选。失败、取消与版本冲突丢弃未发布结果，服务负责 RID/GPU 生命周期。
- 单步限制读取/哈希字节及处理项数；JSON/PNG 等解析调用仍需实际测量。只支持整文件的旧后端
  保留同步兼容行为，并明确不能承诺同样的单步上界。
- 同步入口复用同一准备实现连续推进；异步服务在步骤之间返回宿主，不维护第二套业务状态。
- read_source 可选提供独立拥有缓冲和文件对象的区间请求，poll 以 NOT_READY 表示未完成。
  请求不借用任务栈或调用方输出；取消销毁必须等内核确认后才能释放缓冲，不能遗留在途指针。
  Windows 原生后端采用 OVERLAPPED 与事件，协作模式没有隐式线程池。准备与复验等待请求时
  返回宿主，同步 API 显式使用原有同步路径，不忙等轮询。
- 未提供可轮询读取的后端保留同步区间回退，Linux 原生文件当前也走该回退。
  不把 Windows 实景结果扩大成跨平台存储等待上界；平台后续可实现同一内部契约。
- 在现有批次内对短 Mesh 来源做有界预读，最多 8 个、单项不超过 1 MiB。
  预读只提前发起读取，不提前解析、登记已验证身份或发布资源；处理到该项时仍完整计算摘要。
  取消与失败统一回收这些请求，未提供可轮询读取的后端不预读。

## 影响

场景未发布资产域的取消、上传回执与清理报告采用
[ADR-058](ADR-058-scene-cancellation-cleanup.md) 的独立生命周期约定。

新增内部读取验证契约，必须覆盖来源生命周期、嵌套跟踪、取消、短读、文件变化、预算及同步兼容。
时间切片不是抢占保证；大场景结果仍按 M-312 的冻结门槛验收，不能因设计本身宣称达标。

## 替代方案

仅减少每帧任务数无法分割已有长任务。协作模式偷偷启用线程不满足无线程执行契约。
跳过来源校验或仅以路径/文件时间判断内容会削弱原有一致性检查，均不采用。
