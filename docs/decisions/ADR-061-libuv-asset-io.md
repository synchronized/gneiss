# ADR-061：资产文件 I/O 优先复用 libuv

- 状态：已接受，实施中
- 日期：2026-10-13

## 背景

当前 Windows 区间读取使用 OVERLAPPED 与事件，非 Windows 使用同步标准流回退。
这使跨平台执行行为和维护成本不同。用户确认优先使用已经引入的 libuv，只有它无法
满足已验证需求时才考虑原生实现。此决策不宣称 libuv 能消除系统 CPU 调度延迟。

## 决策

- 桌面资产文件操作优先复用 `platform/io/uv`；平台层仅提供通用文件与执行能力，
  不依赖资产格式、RID、Scene/ECS 或编辑器。资产层保留来源隔离、版本校验和预算语义。
- 保留 `read_source/read_operation` 的区间、生命周期和结果语义，不建立第二套服务状态。
  打开阶段需要异步推进时扩展内部状态，普通公共 C/C++ API 不泄漏 libuv 类型。
- 异步完成只向原有推进机制发布回执；计算任务仍由现有调度器执行。
  libuv 文件线程池是共享资源，不将独立 loop 描述为独立文件线程池；由提交侧限制并发和内存。
- 请求、文件、缓冲存活到完成回调确认；取消不能假设立即中断系统调用。
  先禁止新请求并处理迟到完成，再关闭文件，最后停止所属执行器；不得阻塞主线程或在 loop
  内等待自身完成。同步 API 保留明确阻塞语义。
- 无线程构建不链接或启动线程式文件后端。协作模式保留既有不隐式启用线程的契约，
  使用明确的能力选择与同步回退，回退没有存储等待上界；不把桌面结果宣传为 Web 异步支持。
- 保留根目录隔离、完整摘要、版本冲突和取消事务语义；路径转换不能只换函数名而改变编码、
  符号链接处理或越界判定。Windows/Linux 验收通过后移除被替代的专用实现。
- 原生后端作为有证据的例外：记录 libuv 的具体能力缺口、对照结果、维护成本与契约测试后
  再决策。本版不新增 IOCP 后端，不固定 1 MiB 分块，不因迁移提高预算或放宽响应门槛。

## 执行器与文件生命周期

Application 在线程池执行模式下持有资产 I/O loop，在挂载后、资产服务开始前注入后端。
内部 task_executor 提供模式查询，未知自定义执行器默认协作模式；协作模式不创建此 loop。
这不新增 CPU 任务池，文件请求仍使用 libuv 共享线程池。

异步文件保留关闭通知句柄；读取请求持有文件，最后一个使用者释放时通知 loop 关闭，
销毁回执不 join、不等待磁盘。宿主先关闭资产服务并释放场景，再停止并排空 loop。
文件请求数与缓冲字节共同受限，完成但未释放的回执仍占容量。异步 close 提交本身失败时，
仅在 I/O loop 上用同步 libuv close 兜底回收，不在取消请求的调用线程执行。
此生命周期要求是内部接口契约，不承诺宿主最终停机有固定存储等待上界。

## 影响与替代方案

优先减少平台分支，代价是桌面文件请求会使用 libuv 的工作线程资源；独立 loop 不解决
共享线程池饱和。先以背压与测量控制影响，不预先调大线程池或另写完成端口。

本决策对 [ADR-057](ADR-057-incremental-asset-preparation.md) 的桌面后端选型作后续调整，
保留其分步准备和无线程边界；迁移未完成前，ADR-057 中原实现仍是当前事实。
实施顺序及验收以 [DEV-050 M-322](../plans/DEV-050-main-loop-latency.md)
为准；既有卡顿证据和发布限制继续维护在 M-321，不作为本决策已实现的结果。
