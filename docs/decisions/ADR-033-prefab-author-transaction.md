# ADR-033：Prefab 作者写入使用可恢复的多文档事务

- 状态：已接受
- 日期：2026-09-03

## 背景

创建 Prefab 会先生成来源资产，再以实例替换原场景子树；Apply 会同时修改 Prefab 来源和清除场景
覆盖。现有 Editor 保存只原子替换单个场景文件，无法避免第二个文件写入失败或进程退出时留下来源
与场景不一致。仅比较修改时间也会漏掉时间戳精度内的外部编辑。

## 决策

- 多文档写入属于 Editor 作者层，不进入 Engine 公共 ABI，也不扩展通用 VFS 写接口。
- 每项变更保存路径、完整基线内容和替代内容；不存在的文件使用显式空状态表达。
- 准备阶段先序列化并验证全部替代内容，再读取全部目标并与完整基线逐字节比较。内容摘要只用于修订
  标识和诊断，不能替代冲突判断。
- 磁盘提交使用工程 `.gneiss/transactions/` 下的恢复目录：先写入替代文件、原文件备份和清单，再按
  稳定路径顺序替换目标。所有目标完成后才写入提交标记。
- 启动恢复遇到未提交清单时恢复全部基线；遇到已提交清单时保留新值并清理恢复目录。因此崩溃后
  对外只选择完整旧状态或完整新状态，不尝试猜测用户意图。
- 运行中任一步失败必须恢复已替换目标；恢复本身失败时保留清单和备份并返回明确 I/O 错误。
- Undo 和 Redo 各自建立新的事务，并以当时预期内容重新检查冲突，不长期复用一次提交的恢复目录。
- 首版只允许资产根内 Native FileSystem 的普通文件参与写事务；只读或其他 VFS 挂载明确拒绝。

## 影响

- Create Prefab、Apply 和后续跨作者文件操作可以共享同一提交与恢复边界。
- 完整基线会增加短期内存和磁盘占用，但作者 JSON 规模可控，并能提供无碰撞歧义的冲突判断。
- Editor 启动需要在开放工程作者文档前恢复或清理遗留事务。
- M-130 的内存参考模型只验证准备、冲突、提交失败、Undo 和 Redo 状态机；M-131 负责恢复清单、
  路径约束、持久化顺序与真实故障注入。

## 替代方案

- 先保存 Prefab 再保存场景：实现简单，但第二步失败会暴露半完成状态。
- 仅使用两个临时文件后连续 rename：正常运行可回滚，却无法判断进程在两个 rename 之间退出后的状态。
- 使用修改时间和大小作为修订：成本较低，但无法可靠识别内容不同且元数据相同的外部修改。
- 把写事务下沉到 VFS：会迫使只读、归档和网络后端承担作者事务语义，扩大不必要的公共边界。
