# ADR-059：主循环进展通知与有限等待

## 状态与背景

2026-10-07，已接受，目标 0.50；实现及验收尚未完成。
[M-318](../records/M-318-main-loop-observation.md) 确认原生 Runtime 大量重复轮询，
日常与完整加载主线程接近占满一个核心。不能仅据此归因所有偶发长间隔。

## 决策

在原生 Granit Application 内使用可合并的进展通知与有限条件等待。
不增加工作线程、不改变公共 SDK，不把平台句柄或业务任务下沉到 Granit。

- 宿主持有通知对象，循环处理事件与更新前取得通知代次，循环尾部仅在代次未变化时等待。
  终态、取消终态及渲染回执发布后通知；先到通知、等待边界通知不丢失，允许合并与虚假唤醒。
- 通知只是重新检查现有队列，不是结果容器、不执行宿主回调、不转移 Scene/ECS/GPU 所有权。
  通知实现不回调调度器或渲染 Service，避免锁顺序反转。
- 任务描述与渲染执行器持有通知对象共享引用，通知对象不持有 Application 或 Service。
  宿主停止并回收生产者后释放；迟到通知仅访问独立对象，不访问已销毁宿主。
- 每次等待采用最多 4 ms 的请求期限；后台完成通知可提前结束等待。
  在无原生窗口等待接口时，输入、IPC、无相机、最小化及其他宿主工作由截止期限保障重新轮询。
  OS 可能延迟唤醒，不宣称实际响应必定小于 4 ms；响应与吞吐按冻结门槛实测。
- 完成本轮退出请求或已达 run 帧数上限时不再等待。等待单独计时，仍包含在完整循环指标中。
  不通过从指标里删去等待获取改善，也不改变测量宿主旧 sleep 的统计语义。
- 协作执行的任务完成也发布通知，使同轮有进展时继续推进；不等待尚需自己执行的完成条件。
  有限截止期限保证延迟步骤仍能推进；Web/无线程宿主不实例化或执行条件等待，保持原有回调驱动。
- Headless 路径保持原样。原生回调仍是可变时间步，不承诺无限速回调频率；没有新增帧率或固定更新 API。

## 上游与替代方案

[UPSTREAM-050](../plans/UPSTREAM-050-granit-window-wait.md) 可使窗口输入也立即参与等待结束，
属于后续更完善的等待能力，当前有限等待不依赖该接口。不修改 Granit 或自行复制 Win32/SDL 等窗口后端。

单纯 sleep 无法在任务完成时唤醒；只等待 GPU 会阻塞没有相机或窗口最小化时的任务和退出。
把所有任务改为后台或增加线程池不能消除宿主重复轮询，也不能自动修复系统调度长间隔。

## 验收

覆盖通知先到/等待中到/合并、超时、失效宿主后的通知对象寿命、任务失败/取消以及协作模式。
窗口输入、任务到达和关闭使用独立发送线程；注入停顿证明夹具能够发现被测主循环卡顿。
日常与完整场景重复 CPU、吞吐和内存对照及取消、清理、切换、窗口生命周期回归均须通过。
量化门槛见 [DEV-050](../plans/DEV-050-main-loop-latency.md)，不因结果失败事后放宽。
