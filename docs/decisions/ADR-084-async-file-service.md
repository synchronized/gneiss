# ADR-084：统一回调式文件服务

- 状态：已接受，分阶段实施
- 日期：2026-10-25

## 背景

旧 VFS、asset_source 和平台回执共同承担读取编排，上层难以统一回调线程和关闭生命周期。
桌面 libuv、浏览器 Fetch/FS/IDBFS 的执行机制、能力和持久化语义不同。

## 决策

使用 PImpl file_service 作为资源层的异步文件入口，负责路由、请求所有权和所属线程完成分发。
后端保持类型明确的异步操作，支持后台完成；旧轮询回执仅在后端内部非阻塞适配。
普通读不允许同步文件 I/O 回退，主线程无 wait/get 阻塞接口。
读链仅对 not_found 回退；写唯一后端；挂载启动后冻结。不要求各平台实现全部能力。
回调与读取数据都由请求拥有，取消产生唯一终态，关闭必须先收尾请求再结束平台执行器。
文件服务管理字节，asset_manager 管理反序列化和资源引用，不恢复版本/事务协议。
write 与 flush 分开；浏览器 IDBFS 恢复、写入、持久化具有独立时序。
使用现有调度能力，不新增通用 Service 基类或线程池；JS Promise 仅作可选适配。

## 影响

能够隐藏平台差异和开放/读取/关闭细节，调用方通过回调组合工作。
需要迁移宿主分发、资产任务状态和同步加载调用点，保留资源缓存的挂载来源身份。
后端能力不足显式失败；IDBFS 无法承担任意大文件低内存持久化承诺。
实施与验收以[异步文件服务计划](../plans/PLAN-051-async-file-service.md)为准。

## 替代方案

- 继续公开旧 VFS 和轮询回执：迁移小，但平台编排持续泄漏到资源层。
- future/get：不解决事件循环调度，容易阻塞主线程；暂不采用。
- 完整 Godot Object/Signal 或通用服务框架：引入无实际需求的依赖和复杂度，不采用。
