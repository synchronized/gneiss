# ADR-023：公共 API 稳定级别与 1.x 兼容边界

- 状态：已接受
- 日期：2026-08-28

## 背景

Gneiss 进入 1.0.0 前需要区分长期运行时契约与仍在演进的工具、编辑器和高级接口。仅以头文件是否
安装或符号是否导出判断稳定性，会让实验能力获得无法兑现的隐含兼容承诺。

## 决策

- 公共能力分为 `Stable`、`Experimental` 和 `Internal`。稳定级别的权威说明位于
  [兼容与稳定性参考](../reference/compatibility.md)。
- `Stable` C11 ABI 是 1.x 二进制兼容边界。1.x 不删除或改变既有符号、结果码、常量和已发布字段，
  可扩展结构只在尾部追加字段，并继续接受旧 `struct_size`。
- C++20 包装基于 C ABI，只承诺 1.x 源码兼容；不同编译器、运行库和标准库之间不承诺 C++ ABI。
- `Experimental` 可以安装和导出，但必须在头文件、文档和兼容清单中可识别；1.x 可在提供迁移说明
  后调整，不进入 Stable ABI 基线。
- `Internal` 不安装、不导出，也不构成兼容契约。
- 持久格式独立版本化，其兼容规则由对应格式 Reference 定义，不由库版本号隐式替代。
- 1.0.0 冻结前允许修正 0.x 公共接口，但必须记录迁移方式并在发布候选前完成。

## 影响

- 导出符号清单必须同时记录稳定级别，不能把“当前存在”误写为“已经稳定”。
- 新增 Stable API 需要覆盖旧头文件 Consumer、结构追加、错误语义和跨版本加载测试。
- Editor、资产编译器和工具协议默认保持 Experimental，除非经过独立评审进入 Stable。
- C `enum`、未定义扩展策略的结构和所有权不清晰的接口不能直接进入 Stable 清单。

## 替代方案

- 将全部已安装接口一次性冻结：范围过大，且会固化仍未完成 ABI 审计的结构。
- 1.0.0 只承诺源码兼容：无法满足稳定 C ABI 和共享库升级目标。
- 拆分多个动态库表达稳定性：当前模块规模不需要增加二进制边界，文档与清单足以先建立契约。
