# ADR-048：Runtime 资产分离异步准备与受控提交

- 状态：已实现，0.40.0 验收通过。
- 日期：2026-09-25。

## 背景

现有 render_asset_loader 将纹理读取、解码和资源创建放在同步获取路径，Runtime 的修订协调器
同步调用资源应用后立即返回终态。只把整个函数放到线程池，会让后台访问资源缓存、RID 表和
Application 状态，破坏主线程与渲染执行器的所有权。

[ADR-036](ADR-036-asset-hot-reload.md) 要求修订批次失败时保留旧资源；异步化必须保留这条规则。
[ADR-047](ADR-047-cooperative-task-execution.md) 提供统一任务契约与两种执行模式，本决策规定实际消费者边界。

## 决策

由宿主持有调度器并通过内部接入点注入纹理加载服务；Editor、Runtime 使用相同实现，各进程独立持有实例。
服务拥有请求、任务作用域和候选数据，宿主控制应用安全点，调度器不管理资产身份和事务。
首个闭环为显式纹理加载和已加载纹理热更新，不将所有资源服务并发化。
内部 `task_executor` 只提供宿主调度器的虚调用入口，没有另一套运行时状态；Application 不链接或
创建第二份池，避免共享库与可执行文件各自持有线程局部执行上下文。

纯纹理异步重载保持已加载纹理的 RID 和缓存身份，提交时交换不可变数据版本；材质继续引用相同 RID，
已提交帧的共享快照保留旧数据。只有首次加载才新增缓存映射。提交前再次检查缓存身份、RID generation
和原数据版本；卸载、同步替换或外部修改使候选失效。此策略不改变混合批次的原有同步事务路径。

| 阶段 | 执行位置与所有权 |
| --- | --- |
| 接收请求 | 所属主线程记录会话/宿主代次、目标 generation、修订及容量，返回已接受或拒绝 |
| CPU 准备 | 调度任务读取并验证描述与源数据，解码为拥有内存的候选；无工作线程时由宿主协作执行 |
| 校验与提交许可 | 主线程检查请求是否仍有效、候选是否完整、批次依赖是否满足，决定提交或丢弃 |
| GPU 准备与确认 | 现有渲染执行器拥有后端操作；保持候选、成功确认与失败清理，不在后台任务中调用 Granit |
| 发布与退役 | 在所需确认成功后切换资源映射及引用；旧实例按现有帧引用和 GPU 生命周期退役 |

拆分同步加载器内部的准备与提交逻辑，复用解析和格式验证；同步入口可以顺序调用同一逻辑。
不复制第二个纹理解码器或缓存，不让主线程为提交再次执行大文件读取、哈希和解码。
对 VFS 采用拥有且有效期明确的读取上下文，不能默认其可变挂载和缓存已经线程安全。

服务结果区分已接受、准备完成与实际应用终态。Runtime 的 IPC 请求关联标识保留到异步应用完成；
排队不会提前推进 applied_revision。关闭、断连和重连必须定义未完成请求的归属与清理。
同会话中多个不同 URI 的修订不能只用最大编号丢弃旧请求；采用保序批次，或在证明完整覆盖后合并。

纯纹理批次整体准备并整体提交；混合渲染资产批次保留整体事务，可走现有同步路径。
GPU 失败、CPU 准备失败和候选过期均不能发布半个批次；首次加载失败无残留资源，重载失败保留旧资源。
提交许可前允许取消并丢弃候选，许可后完成或回滚再报告终态。资源卸载或宿主代次变化后旧结果不可复活资源。

按任务数和拥有的字节数施加背压，候选转交、缓存复用、取消和失败路径明确谁释放内存。
主线程提交与渲染上传分别限额；预算只限制批次之间的工作，不能保证单个大操作不超时。

## 影响与替代方案

- 相比把同步函数整体放进线程池，分阶段保持资源所有权清晰，但需要异步请求和失败收尾状态机。
- 相比每个 Service 新建线程，复用宿主调度器便于预算和诊断；长任务仍需受限并发。
- 不把当前公共同步 C API 改为隐式异步返回；首版使用内部接入点，不增加公共 ABI。
- 不把 Runtime 导入源资产作为加载方案；Runtime 继续消费已经提交的资产，作者工具链留在 Editor/离线工具。
- 不为本版要求全部 Service 通过 service_registry 装配；生命周期注册与工作调度保持独立。

本决策计划细化 ADR-036 的候选构造位置，不改变修订批次原子性。
初始场景和混合批次保留同步加载，渲染所有权继续遵守
[ADR-038](ADR-038-render-thread-ownership.md)。
开发顺序及后端能力核对见 [0.40 开发计划](../plans/DEV-040-runtime-task-integration.md)。
