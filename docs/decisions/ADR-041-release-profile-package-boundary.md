# ADR-041：发布配置与可运行包边界

- 状态：已接受
- 日期：2026-09-06

## 背景

0.31.0 的目录包证明了 Runtime、Game Module、资产与动态依赖可以脱离 SDK 运行，但工程只声明一组
Debug 预设，导出入口接收外部 Runtime 路径，也没有描述包内容的稳定清单。继续在命令行或 Editor
中拼接特殊参数会使工程配置、二进制兼容和交付规则逐渐分叉。

## 决策

- Gneiss 定义 Debug、Development 与 Shipping 的配置语义，工程文件显式映射到 CMake 预设。
- 完整发布操作拥有配置、构建、文件收集、清单、包内验证与归档步骤；UI 仅提供输入和状态展示。
- 目录包仍是权威中间产物，ZIP 只是确定性封装，不产生第二套内容规则。
- 版本化包清单记录入口和全部文件的大小、SHA-256，并使用相对包根的规范路径。
- Shipping 排除开发专用内容，但必须保留启动失败和致命故障诊断。
- 发布事务不覆盖输出；任何阶段失败均清理临时产物，并返回所属阶段和具体路径。

## 影响

自定义工程需要显式提供配置到预设的映射，Gneiss 无需理解其生成器和构建布局。旧工程继续按单一
Debug 配置解释。清单和确定性归档增加导出成本，但使缓存、分发、复现与完整性检查具有稳定基础。
安装器、签名、补丁、商店发布和完整资产烘焙保持为后续独立能力。

## 替代方案

- 仅约定固定预设名称：实现较少，但限制外部工程并把构建系统细节变成隐式 ABI。
- 直接生成 ZIP 而不保留目录包：减少一种输出形式，但不利于调试、包内启动验证和内容审查。
- 将 Debug/Shipping 只作为 CLI 参数：无需扩展工程格式，但 Editor、自动化与工程配置无法共享事实来源。
