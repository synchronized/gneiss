# ADR-013：glTF 离线导入与工具边界

- 状态：已接受
- 日期：2026-08-27

## 背景

手写 Mesh v3、Material、Texture 和 Scene 已足以验证基础 3D 闭环，但不适合作为长期内容生产方式。
项目需要从 Blender 等数字内容创作工具导入模型，同时避免外部格式、第三方类型和解析成本进入游戏
运行时。首个真实需求是 glTF 2.0/GLB，不需要同时承诺 FBX、OBJ 或 USD。

## 决策

- glTF 2.0/GLB 是首个正式导入格式，使用 fastgltf 作为仅限工具层的解析依赖。
- 建立内部资产导入核心，由 `gneiss_assetc` 命令行前端和未来编辑器共同复用。
- 导入核心先转换为 Gneiss 自有 Import IR，再校验并写出运行时 Mesh、Material、Texture 和 Scene。
- Runtime、公共 C ABI、安装 package 和自有资产格式均不得暴露或依赖 fastgltf 类型。
- 首版 CLI 先验证接口和错误语义；编辑器优先以子进程调用，公共 SDK 等真实编辑器用例验证后再稳定。
- FBX、OBJ 等格式只有出现真实需求时才增加独立后端；所有后端必须汇入同一 Import IR。

## 影响

运行时保持轻量且不解析外部创作格式，编辑器和 CLI 可以共享转换、诊断及依赖收集逻辑。工具层需要
维护 glTF 坐标、材质和扩展到 Gneiss 契约的明确映射，也需要为导入结果建立可重复生成规则。公共
SDK 延后意味着首版编辑器通过进程协议获得隔离，但暂时无法直接导入内存中的模型。

## 替代方案

- Assimp：格式覆盖广且适合离线转换，但当前只需要 glTF，其统一中间模型可能损失 glTF 扩展语义。
- Runtime 直接加载 glTF：入口简单，但会把解析依赖、外部格式演进和转换成本带入发布游戏。
- 立即发布导入 SDK：便于编辑器链接，但缺少真实调用经验，容易过早冻结任务、诊断和内存所有权。
- 直接从 fastgltf 写出资产：代码更少，但会耦合解析器与持久化格式，妨碍测试和未来增加其他后端。
