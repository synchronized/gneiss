# 测试设计与维护

## 适用范围

适用于开发期新增测试和修改受影响测试。构建、运行命令以[构建指南](building.md)为准。
已有测试逐步按本指南审查，不要求一次重写；首轮整理见
[PLAN-114](../plans/PLAN-114-test-maintenance.md)。

## 目录归属

引擎测试位于 `tests/engine/`，按 core、meta、serialization、asset、scene、render、
application、platform 等领域就近维护 CMake 目标；World 与场景层级测试统一归 scene。
Tooling、Editor、Runtime、Project、Protocol 测试位于同名目录，跨模块流程归 integration。
共享辅助和输入保留在 support、data、fixtures；不要为目录迁移复制夹具或生产源码。
独立浏览器任务宿主位于 `tests/engine/task_web/`，不加入桌面默认构建。

## 测试目标的 CMake 约定

- 测试可执行目标、仅供测试使用的夹具库、头文件编译目标和手动测试/基准目标统一设置
  `FOLDER "Tests"`，目标定义与属性放在同一领域的 CMake 文件中。
- 从生产模块复用的库保留其生产归属，不因被测试链接而改为 Tests；单纯的 `add_test()`
  脚本用例没有构建目标，不设置此属性。
- 顶层工程启用 `USE_FOLDERS`。`FOLDER` 只控制支持该属性的 IDE 生成器中的组织，
  不代替 CTest 的 `LABELS`、超时、依赖和启用条件，也不意味着该测试已经通过。

```cmake
add_executable(gneiss_example_test example_test.cpp)
set_target_properties(gneiss_example_test PROPERTIES FOLDER "Tests")
```

## 测试什么

- 保护可观察行为、所有权、数据格式和错误边界，优先覆盖可能导致数据丢失、悬空引用、
  重复释放、取消竞态和关闭泄漏的问题。
- 在最低且足够真实的层级验证一个行为。上层补充装配和自身特有策略，不重复下层全部输入组合。
- 不要求每个函数对应测试，也不设测试行数比例、测试数量或全项目覆盖率配额。
  覆盖率可用于发现遗漏，不能代替风险判断。
- 简单转发、查询和低风险可逆修改通常无需专门增加测试。修复实际缺陷时优先增加可稳定复现的回归。

## 架构变更时如何处理

逐项判断受影响断言：需求已取消则删除；行为仍需保留则迁移；已有充分覆盖则合并；
没有覆盖的风险才补测试。删除时在计划或提交说明中说明被取消的契约或已有覆盖位置，
不为保住测试恢复旧接口，不通过跳过失败掩盖未解决问题。

阶段枚举、私有类名、精确调用次数与文件路径只有在确属接口契约时才固定。
稳定模块依赖方向值得检查；源码正则检查不得扩展成任意实现写法的白名单。

## 辅助函数与正式 API

- 辅助函数用于可控环境、数据夹具、等待完成和断言，不在测试层重做资产加载、对象装配等业务流程。
- 多个调用者反复包装同一业务操作时，先检查正式 API 是否缺少完整使用入口；不要自动将包装函数搬进引擎。
- 正式 API 已支持的操作直接调用，例如借用组件后显式复制；避免用测试包装维持已退出的 node、输出参数等接口形态。
- 需要改善正式 API 时，用生产调用场景确定所有权、失败与通知语义，再同步迁移测试；不能只以测试代码变短作为理由。
- 白盒测试确有必要时说明被验证的内部边界；不得为测试便利扩大导出或让夹具维护第二套业务状态。
- 等待辅助必须传播实际推进失败，不能吞掉错误后只报超时；重复提交、重试和冲突断言放在明确验证该行为的用例中。
- 错误与预算断言必须命中生产实现。夹具自行合成的预算拒绝、输出重置等，只能证明夹具行为，不能作为引擎对应能力的验收。

## 异步、生命周期与诊断

- 优先使用可控执行器、完成通知或屏障制造条件。不要把多跑一帧、固定 sleep 当作完成证明。
- 超时用于防止挂死，不等同于性能门槛；等待失败必须能识别未满足的条件。
- 日志回调等跨线程数据使用同步；请求完成、日志送达、后台任务结束、GPU 完成分别判断。
- 检查借用和所有权的外部效果，避免断言未承诺的析构顺序或后台资源瞬时数量。
- 失败输出应标明行为、位置及必要的预期/实际值。新增测试避免仅用数字退出码区分大量失败。
- 不以自动重试掩盖不稳定测试；修复竞态后可针对性重复验证。

## 夹具和性能

固定内容的对象数可作为夹具正确性检查；内部渲染资源总数不作为全引擎不变量。
共享资源的核心检查是身份复用、引用保活和最终释放，不是某种缓存布局的固定数量。
同进程不变性比较可以使用精确图像比较；跨驱动图像验收应说明环境和误差规则。

功能测试与性能基准分开。门槛须注明硬件、构建模式、夹具、测量区间与统计方式；
测量口径改变后不能沿用旧门槛。零耗时可能来自计时精度，不能用大于零证明操作发生。
没有明确预算时保留原始测量；不得把缺失指标默认为零并声称通过。

## 运行分层

日常运行受影响编译和小型定向测试；架构收尾运行相关 CPU 行为与边界检查；
GPU、外部大场景、跨平台和发布矩阵按任务风险及发布要求执行。
未运行项必须说明，编译通过不能描述为运行验收通过。

测试分类按实际依赖审核，不能从目录名称推断。目标标签是 cpu（不需要 GPU）、
integration（跨模块或真实 I/O/进程）、gpu、death（预期异常退出）；标签可以重叠。
benchmark 是显式测量工具，默认不加入常规正确性套件。标签补齐前继续按已核查的测试名选择，
不能把没有 gpu 标签的条目直接当作 CPU 安全集合。


已标注用例可以按执行环境选择（以 Windows Clang Debug 为例）：

```sh
ctest --preset windows-clang-debug -L "^cpu$" --output-on-failure
ctest --preset windows-clang-debug -L "^gpu$" --output-on-failure
```

以上分别运行已审查的 CPU 或 GPU 子集，不代表完整测试集；未标注项仍按名称选择。
完整枚举使用 `ctest --preset windows-clang-debug --show-only=json-v1`。
安装/打包流程单独使用 `-R "^gneiss.runtime.installed-smoke$"`，其 Runtime smoke
会创建渲染后端，需要可用 GPU；不能把安装检查默认视为纯 CPU 测试。
