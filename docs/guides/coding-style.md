# C/C++ 代码风格与语言标准

## 适用范围

本规范适用于 Gneiss 自有的 C11 公共接口、C++20 公共包装、内部实现、示例和测试。第三方代码遵循其上游规范，不进行无关格式化。

项目采用以下语言分层：

- `.h` 提供稳定的 C ABI，必须能被 C11 编译器独立包含。
- `.hpp` 提供 C++20 包装，基于 C API 提供强类型、移动语义和 RAII。
- `.c` 使用 C11；`.cpp`、`.cc` 和 `.cxx` 使用 C++20。
- C++ 包装层不得建立与 C API 平行的第二套运行时状态。

## 自动格式化基线

代码排版以仓库根目录的 [`.clang-format`](../../.clang-format) 为唯一标准：

- 基于 LLVM 风格。
- 使用 2 个空格缩进，不使用制表符。
- 每行最多 100 个字符。
- 指针和引用符号靠近类型，例如 `const char* name` 和 `entity& value`。
- include 按大小写敏感方式排序。
- 大括号、换行和初始化列表交由 `clang-format` 决定。

格式化改动过的自有源码：

```sh
clang-format -i <files...>
```

不要为了功能修改而格式化无关文件。

## 静态检查基线

仓库根目录的 [`.clang-tidy`](../../.clang-tidy) 启用以下检查组：

- `bugprone-*`：常见缺陷和未定义行为。
- `performance-*`：不必要的复制、分配和低效操作。
- `portability-*`：不同编译器和平台之间的可移植性。
- `modernize-*`：适用于 C++20 的现代写法。
- `readability-*`：可维护性和表达清晰度。

第三方目录 `3rd/` 和系统头文件不进入项目静态检查范围。静态检查产生的告警需要结合语义处理，不得通过大范围 `NOLINT` 掩盖问题。

## 命名规则

### 通用命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 文件和目录 | 小写下划线 | `render_service.cpp` |
| C 函数和类型 | `gneiss_` 前缀、小写下划线 | `gneiss_world_create` |
| C 宏 | `GNEISS_` 前缀、大写下划线 | `GNEISS_API` |
| C++ 命名空间 | 小写 | `gneiss` |
| C++ 类型 | 小写下划线 | `render_service` |
| 函数和变量 | 小写下划线 | `create_entity`、`entity_count` |
| 枚举值 | C 使用大写前缀；C++ 使用小写 | `GNEISS_RESULT_OK`、`result::ok` |
| 私有数据成员 | 小写下划线并带末尾下划线 | `world_id_` |
| 模板参数 | 描述性 PascalCase | `ResourceType` |

缩写视为普通单词，例如使用 `entity_id`、`resource_id`，不使用 `entityID` 或 `resourceID`。RID 作为项目术语可以出现在文档中，代码标识符使用 `rid`。

### 布尔值和动作命名

- 布尔变量和查询函数使用 `is_`、`has_`、`can_` 或 `should_` 前缀。
- 创建与销毁使用 `create` / `destroy`，获取借用对象使用 `get`，所有权转移需要在名称或文档中明确。
- 避免 `manager`、`helper`、`data` 等无法表达职责的宽泛名称。

## C11 公共 ABI

### 可用类型

C ABI 只使用 C11 可表达、布局明确的类型：

- 使用 `<stdint.h>` 中的定宽整数。
- ABI 布尔值使用 `uint8_t` 或明确宽度的项目类型，不使用 C++ `bool`。
- 不使用裸 `long`、`size_t` 作为需要跨平台固定宽度的持久字段。
- 字符串和数组使用“指针 + 长度”，并说明编码、所有权和有效期。
- 不暴露 STL、C++ 类、模板、异常、虚函数或后端原生类型。

### 符号与头文件

- 公共 C 符号统一使用 `gneiss_` 前缀。
- 公共宏统一使用 `GNEISS_` 前缀。
- 公共头文件使用 `#pragma once`，并通过 `extern "C"` 兼容 C++ 包含。
- 每个公共 `.h` 必须能够被 C11 编译器独立编译。
- 聚合头只负责包含功能头，不直接堆放功能声明。

```c
#pragma once

#include <stdint.h>

#ifdef __cplusplus
extern "C" {
#endif

typedef uint64_t gneiss_world_t;

typedef enum gneiss_result_t {
  GNEISS_RESULT_OK = 0,
  GNEISS_RESULT_INVALID_ARGUMENT = 1
} gneiss_result_t;

GNEISS_API gneiss_result_t gneiss_world_create(gneiss_world_t* out_world);

#ifdef __cplusplus
}
#endif
```

### ABI、错误与所有权

- 错误通过结果码返回，不允许异常跨越 C ABI。
- 资源使用 64 位整数句柄；零值表示无效句柄。
- 句柄不得暴露指针或后端原生句柄，也不能被视为可持久化 ID。
- 跨动态库边界的资源由创建方销毁，或提供明确成对的创建/销毁函数。
- 可扩展描述结构包含 `struct_size`；已发布字段只在末尾追加，不重排。
- 回调必须说明调用线程、可重入性、用户数据所有权和有效期。
- 公共接口必须记录参数有效性、失败行为、线程安全和父资源失效规则。

## C++20 规范

### 资源与所有权

- 优先使用自动存储期、标准容器和 RAII。
- 独占所有权使用 `std::unique_ptr`；只有确实共享所有权时才使用 `std::shared_ptr`。
- 不使用裸 `new` / `delete`；非拥有指针和引用必须能从上下文看出生命周期。
- C++ 包装对象默认不可复制，可移动类型显式声明移动操作。
- 析构函数不得抛出异常。

### 类型与语言特性

- 优先使用 `enum class`、`constexpr`、`[[nodiscard]]` 和强类型包装表达约束。
- 使用 `nullptr`，不使用 `NULL` 或整数零表示空指针。
- 仅在类型清晰或避免重复复杂类型时使用 `auto`。
- 优先范围 `for`、标准算法和 `<ranges>`；不为简单逻辑引入晦涩模板。
- 编译期约束优先使用 C++20 concepts，并提供能定位问题的约束名称。
- 不使用可变参数 C 风格函数；公共格式化逻辑采用类型安全方案。
- 不依赖编译器扩展，除非位于受隔离的平台实现文件并有回退或明确错误。

### 异常与错误

- C ABI 永不抛出异常。
- 引擎运行时的可预期失败使用结果类型或错误码。
- C++ 包装层可以将不可恢复的构造失败表达为显式结果；是否启用异常必须由项目级 ADR 统一决定。
- 不使用异常完成普通流程控制。

### 并发

- 明确每个公共对象的线程安全级别：线程安全、外部同步或仅限指定线程。
- 主线程、网络线程和工作线程之间的数据所有权必须明确。
- 优先使用标准同步原语；无锁结构必须说明内存序、进度保证和选择依据。
- 不使用 `volatile` 实现线程同步。

## include 规则

每个源文件先包含自身对应头文件，以验证头文件自包含性。其余 include 分组如下，各组之间保留一个空行：

1. 对应的项目头文件；
2. 其他 Gneiss 公共或内部头文件；
3. Granit 和其他第三方头文件；
4. C++ 标准库头文件；
5. C 标准库或平台头文件。

公共头文件只包含完成声明所需的最小依赖。可以前置声明时避免引入重量级内部头，但不能为了减少 include 而创建不合法或脆弱的前置声明。

## 注释与文档

- 所有自有源码和头文件保留 SPDX 许可证头，不记录个人作者和修改历史。
- 代码注释使用中文，解释约束、原因和非显然行为，不逐行复述代码。
- 公共 API 使用简洁的中文 Doxygen 注释。
- Doxygen 优先说明用途、参数、返回值、所有权、生命周期、线程安全、失败行为和限制。
- `TODO` 必须说明待办事项和原因；可跟踪任务应附 Issue 编号。
- 注释失效视为缺陷，修改行为时同步更新。

## 目录与边界

```text
include/gneiss/         C11 API 与 C++20 公共包装
src/                    内部 C++20 实现和平台后端
tests/                  C11、C++20 与行为测试
examples/               可独立运行的最小示例
docs/                   项目文档
3rd/                    锁定版本的第三方依赖
```

- 第三方原生类型和头文件不得通过公共 API 泄漏。
- 仅在单个 `.cpp` 使用的辅助函数、变量和类型放入匿名命名空间。
- 平台差异隔离在具体后端文件，不在业务逻辑中散布平台宏。
- 底层模块不得反向依赖场景、编辑器等高层模块。

## 测试要求

- 公共 `.h` 需要由 C11 编译器独立包含和构建。
- 公共 `.hpp` 需要由 C++20 编译器独立包含和构建。
- 新增 API 或修复缺陷时覆盖成功、失败、生命周期和线程边界。
- RID 测试至少覆盖零值、类型错误、generation 失效、跨服务混用和重复销毁。
- 修改 ABI 时同时验证共享库、静态库、C consumer 和 C++ consumer。
- 不通过关闭警告、跳过测试或降低检查等级掩盖问题。

## 提交前检查

1. 对改动的自有源码运行 `clang-format`。
2. 对相关目标运行 `clang-tidy` 或项目提供的静态检查目标。
3. 使用 C11 编译器验证受影响的 `.h`。
4. 使用 C++20 编译器构建并运行相关测试。
5. 检查公共接口的 ABI、所有权、线程安全和错误语义。
6. 运行 `git diff --check`，确认没有无关格式化或尾随空白。

具体构建、测试和示例运行命令由[构建与测试指南](building.md)统一维护。
