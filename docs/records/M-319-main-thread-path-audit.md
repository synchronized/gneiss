## 实际 Runtime 主循环

| 顺序 | 主线程工作 | 后台边界与同步风险 |
| --- | --- | --- |
| 事件 | 平台窗口消息、关闭判断、输入状态和事件转换 | 原生事件泵和队列处理；仍可能等待 OS 调度 |
| Runtime 更新 | IPC 命令、场景加载推进、进度/日志、可选检查快照和统计、游戏更新 | 仅 cooperative 会在此执行 run_ready；thread 模式不执行后台任务体 |
| 场景推进 | 取任务回执、提交下一步、分批资源暂存/发布、候选节点构造、激活与回收 | 任务队列和渲染回执有锁；分配与对象释放仍可能发生在主线程 |
| 渲染准备 | 帧存储复用、ECS 渲染快照、捕获帧包、提交渲染队列 | 真正渲染及上传由渲染线程执行；取回执和提交队列有短临界区 |
| 循环末尾 | 清理临时绘制列表；无进展时请求有限等待 | 初次取通知锁、条件等待及重新取锁都在调用墙钟内 |

入口分别为 [Application::run](../../src/engine/function/application/application_state.cpp)、
[update_runtime](../../apps/runtime/main.cpp)、
[场景加载推进](../../src/engine/function/application/scene_load_service.cpp) 和
[渲染执行器](../../src/engine/function/render/render_executor.cpp)。

完整 Runtime 测量工程没有 Game Module，命令没有 IPC/stop-file 参数。因此不能将这笔样本
归因于游戏脚本、Editor 场景快照或停止文件检查；这些属于其他宿主配置下的审计项。
启动、单次 run 返回时的 finish_frames 与退出清理在循环统计之外，不能混作本次 86 ms。

## 37.43 ms 任务提交所覆盖的工作

最长样本中 update=37.4732 ms、scene_advance=37.4354 ms、task_submit=37.4279 ms，
三者是包含关系。调用链为场景复验推进 → submit_verification → task_scheduler::submit。

[任务提交](../../src/engine/core/tasks/task_scheduler.cpp) 当前依次执行：

1. 构造描述和回调参数，然后获取主线程与工作线程共用的调度器 mutex。
2. 在锁内检查作用域、容量、前置任务和串行队列。
3. make_shared 创建任务，准备回执字段，再向 std::map 插入任务节点。
4. 更新计数、notify_all 唤醒工作线程，返回并释放锁。

工作线程也在这把锁下选择任务、发布终态；选择过程扫描任务表，串行队列还可能嵌套扫描。
但任务体 execute 在锁外调用，资产读取和哈希由该后台任务体执行。
因此已确认主线程提交路径存在锁与分配，尚不能从旧样本区分锁等待、分配、唤醒或被抢占。
不能将扫描复杂度直接当作根因：本次任务表实际规模与同轮锁持有时间尚未记录。

## 48.52 ms 循环等待所覆盖的工作

[loop_progress::wait](../../src/engine/core/loop_progress.hpp) 先获取通知 mutex，再调用
带谓词的 condition_variable::wait_for。传入 4 ms 是该条件等待请求的期限，
**不是整个函数的耗时上限**；初次取锁也在原 idle_wait 计时内。
条件等待返回还包含重新取锁和线程获得执行机会的时间。
旧样本 idle_wait=48.5241 ms，无法直接判定全部时间在超时睡眠中。

## 新增细分观测与下一步

新增默认关闭的阶段：task_submit_lock（取锁）、task_submit_work（锁内总工作）、
task_submit_allocate（创建任务）、task_submit_insert（任务表插入）、task_submit_notify（唤醒）；
以及 idle_lock（初次取锁）、idle_condition（条件等待调用）。
allocate/insert/notify 嵌套于 work，work 与 lock 嵌套于原 task_submit；
idle 两项嵌套于原 idle_wait，不重复相加，也不删除等待后再声称最大间隔下降。

默认关闭时不读取诊断时钟，不记录逐次明细；启用后仍使用固定容量最长样本。
已有等待、队列、线程数与任务体保持，未将生产工作迁移到别的线程。
条件等待内部的挂起、重新取锁与 OS 调度仍不能仅靠这一层计时进一步分开。

宿主调度器与 Engine 动态库不能依赖共享 thread_local。提交描述仅在同步 submit 期间借用
调用方的计时结果，调度器在保存任务前清除借用指针，返回后再合并入循环观测。
新增测试覆盖无效作用域、成功提交、计时覆盖和任务执行后不再写入借用结果。
这属于内部 C++ 传递，不改变公共 C ABI 或 C++ SDK，也不建立第二套运行时状态。

继续运行同输入诊断对照，核验跨动态库结果并优先核对长提交到底落在哪个子阶段；
若没有复现，保留未复现结论，不把新增计时代码当作根因已修复。

## 协作模式的观测边界

生命周期矩阵中 cooperative-repeat 的最大回调间隔为 239.1535 ms；旧宿主有主动睡眠，
且 run_ready 在主线程执行任务，单个任务不能被帧预算抢占。当前没有这一帧的细分记录，
不能将它直接归因于哈希、锁或睡眠，也不能和线程池 Runtime 的 86.0114 ms 混作同一组。

同一 cooperative-repeat 记录中的来源复验最大步骤为 157.0401 ms，哈希调用最大为
157.0335 ms。源码确认该模式在主线程执行任务体；调度器的 2 ms 驱动预算只能在任务之间
检查，无法中断已经开始的单次 16 MiB 校验。这确认了复验路径的长同步工作，
但不能直接替代资产阶段 257.6851 ms 的归因。计时为调用墙钟，仍包含可能的线程被抢占。
下一步评估协作任务单次字节预算，并保持线程池批次、完整校验和既有验收门槛。

## 协作失败加载分段复现

[旧批次诊断](artifacts/0.50-cooperative-path-diagnostic.json) 保留 4,145 个回调。
按回调入口重建的最大已闭合间隔 233.7671 ms，其中 run_ready 181.6669 ms、宿主睡眠 31.6499 ms、
回调外 20.2506 ms，场景 poll 仅 0.0099 ms。该次没有再次超过 250 ms，
但确认这笔长间隔主要覆盖协作任务执行，不能用无锁入队替代任务分片。
run_ready 内部仍混合任务体和调度开销，尚未将资产阶段细分为读取、哈希与解码。
原 event_interval 字段最大为 233.6493 ms，因起点位于回调内部，保留该旧口径独立判定门槛。

主循环 CSV 写出后才启动独立 Debug 构建；后续同进程重试仅作功能检查，
不采用其重试时长、进程累计 CPU 或工作集作性能证据。原始未插桩失败保留。
失败后的重试、资源清理与图像一致性通过。已将协作准备/复验的读取和哈希字节预算调整为
4 MiB，线程池保留 16 MiB；服务级多轮消费回归通过，完整 Mip 链的纹理保持内容一致。
Release、Debug 共享/静态构建通过，全量回归及完整场景对照尚待完成。
原生文件读取、解析/解码与 OS 调度仍可能超出驱动时间预算，不把字节上限描述为硬期限。

## 输入探针的时间窗关联

关联脚本按同进程 steady_clock 原点重建时间窗。循环记录的 total_ms 包含前置 gap_ms，
故循环内部为 `[start_ms, start_ms + total_ms - gap_ms]`，前置空档单列。
最长 128 个循环以外的区间标为未保留，不能据此断言线程没有运行；整轮阶段累计不能直接
当作探针窗口内的阶段耗时。脚本位置和使用方式见[构建指南](../guides/building.md)。

已有 50 ms 注入对照的第 1 个输入探针观测 115.2283 ms，关联覆盖两轮：第 11 轮重叠
15.07 ms，第 12 轮重叠 100.16 ms，后者 update 累计 97.5496 ms，包含注入停顿。
该结果只验证能够定位已知停顿；请求睡眠时长不代表实际恢复时刻。

前次完整场景诊断的第 266 个输入探针为 22.8571 ms，其中 22.7952 ms 与第 2001 轮
重叠，未保留 0.0619 ms；该轮条件等待 22.8334 ms、update 0.0178 ms。
因此这个具体样本主要覆盖等待，而非主线程业务更新；不能据此替代未采样的 266.238 ms
失败归因。最新响应诊断与发布状态统一见 [M-321](M-321-0.50.0-release-validation.md)。
