# M-312：0.49 加载基线与量化门槛

## 状态与环境

2026-10-07，Release 基线 12 个样本已完成，全部正常退出。性能修改前固定以下门槛。
范围见 [VER-049](../plans/VER-049-0.49.0-loading-stability.md)。

基线代码为 `7647b2a`（相对 v0.48.0 仅规划文档），Windows 10、Intel UHD 630，
驱动 31.0.101.2140。使用 windows-clang-release 的 gneiss_scene_load_baseline；
二进制 SHA-256、资产转换报告和各次结果保存在 build/0.49-baseline-release/summary.json。
测量期间不并行构建；每样本独立进程，不清理操作系统文件缓存，不能把首个样本称为冷缓存。

输入位于外部 asset-cache/intel-sponza：日常 0.43-daily-assets-2，完整 0.44-full-cooked。
保留 553 个节点和 505 个资源，完整配置不降低分辨率、裁剪资产或提高 2 GiB 候选上限。
原 measure_scene_loading.py 的 458 资源断言属于早期输入，不能套用于当前五贴图资产。
逐项输入摘要见 [资产身份清单](artifacts/0.49-asset-identities.json)，全部样本及二进制摘要见
[原始报告](artifacts/0.49-baseline-release.json)；第三方资产不入仓库。
完整 Cook 纹理文件合计 8,053,171,376 字节，不能使用 conversion.json 中 Cook 前的尺寸代替。

## 基线结果

| 输入 / 模式 | 加载中位数 ms | 三次最大主循环间隔 ms | 三次最大进程峰值 bytes |
| --- | ---: | ---: | ---: |
| 日常 / thread | 40,519.07 | 104.57 | 1,402,155,008 |
| 日常 / cooperative | 31,876.98 | 1,831.74 | 1,401,536,512 |
| 完整 / thread | 266,500.45 | 79.17 | 2,509,701,120 |
| 完整 / cooperative | 259,839.91 | 67,367.79 | 2,508,759,040 |

每个样本均为 553 节点、505 资源，同一输入的图像摘要一致。完整候选逻辑
1,773,169,608 字节，其中 CPU 候选 162,645,960 字节，纹理负载逻辑 1,610,614,656 字节；
上传在途峰值 22,369,648 字节。CPU 进程峰值与逻辑资源预算不是同一统计，未测量独立显存。
完整 cooperative 首次最终来源复验约 53.07 秒，对应约 53.14 秒的主循环停顿，
后续样本最坏停顿达到 67.37 秒。该路径是明确的响应性缺口。

## 冻结的验收门槛

同机 Release、同输入与相同测量工具比较；每种输入/模式至少三次，报告所有样本及中位数。
Debug 单列功能验证，不与 Release 混合。以下门槛不因优化结果而放宽：

| 项目 | 门槛与解释 |
| --- | --- |
| 主循环响应 | thread 保持已有 P95 ≤100 ms、最大 ≤250 ms；cooperative 日常与完整也以此为目标 |
| 取消响应 | 请求发出到观察/终态分别测量；各阶段终态 ≤250 ms，清理完成 ≤1 s；迟到结果不得激活 |
| 总加载耗时 | 各模式/输入中位数不高于本轮对应基线的 1.5 倍，避免为缩短单次执行而造成无限调度开销 |
| 内存与容量 | 保持 2 GiB 候选上限；本夹具上传在途峰值 ≤64 MiB（验收目标，不代表所有单资产的硬上限）；各组进程峰值最大值不超过对应基线最大值的 1.1 倍 |
| 激活 | 保留既有 ≤5 ms 门槛 |
| 清理 | 请求独占预留在清理完成后为零；活动/旧帧等合法持有单列，不能把整个 Application 强行清零 |
| 内容 | 节点与资源数量不变；同配置同视角图像对照，无缺失几何/贴图，不以输入裁剪换取通过 |
| 生命周期 | 每模式至少三次切换，读取/准备/上传/复验/ready 取消、失败重试、窗口操作与关闭通过 |

主循环间隔不是每个呈现帧的精确统计；CSV 为主线程采样到的最新呈现间隔。
不声称测得实际独立显存。缓存不受控导致的离群样本保留并解释，不静默丢弃。
若不可切分调用导致门槛无法达到，必须记录阻塞原因并重新评审，不将失败改为通过。

## 源码排查

最终来源复验一次遍历全部文件；读取虽分 64 KiB，任务没有让出执行的边界。
资产准备一次处理完整依赖闭包，仍需分辨哈希、解析和解码的单次最大耗时。
scene_load_service::finish 的原预算在 pending 销毁前采样，缺少清理完成语义。
libuv POSIX 流写入使用 write/writev，自有 I/O 线程未阻塞 SIGPIPE；确定性断管测试待 Linux 验证。
这些是实现排查依据，不等同于已完成的修复或历史故障已被复现。
