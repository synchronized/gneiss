# CAORS 0.7.0 升级与 Web 编译复验

## 版本与范围

Gneiss 从 CAORS 0.4.0 固定提交升级到 0.7.0 的
3b543eb1549156a21e432af91da3abd98727fff8。检查时本地上游工作区干净，HEAD 与远端 HEAD 一致。
归档 SHA256 为 0cdf9d9a585d6ceb4c49ff32eef585c8ceee26d4b09847519511d50b55f5c064。
主开发配置清除旧源码覆盖，实际使用新版校验归档；安装消费依赖版本更新为 0.7。
没有修改上游仓库、创建 PR 或运行上游 Actions。

## 本地验证

- Emscripten 5.0.6、无 pthread、CAORS 静态库，使用 -fexceptions 与
  -sDISABLE_EXCEPTION_CATCHING=0：配置、完整库构建和安装通过。
- 上游 tests/web/consumer 通过独立安装包构建 WASM/JS，在 Node 下 consumer.web 通过；
  创建协作 execution_context 和 asset_manager，并检查 Web 无后台线程能力。
- Windows Clang Debug 的 Gneiss Engine、Editor 和相关测试目标使用新版 CAORS 共享库重建。
  asset-probe、vfs-bridge、application、material-document、editor.asset-edit、
  editor.smoke、texture-load-service 共 7 项通过。
- 静态 Engine（仅 Mesh 开启）与共享 Engine（仅材质开启）的两组轻量配置重建、安装，
  各自 C/C++ 等 4 项 consumer 通过；这两组不启用 Granit 窗口。

Web 验证源码来自干净的上游目录 ../caors/caors-core，所有构建和安装产物均在 Gneiss build
目录；原生验证使用下载的固定归档。Web consumer 指定 caors_DIR 指向独立安装包，
避免宿主包路径搜索与 PowerShell 包装脚本参数拆分造成误判。

本地日志：build/caors-web-070-build.log、build/caors-web-070-consumer-test.log、
build/caors-070-tests.log。不提交生成日志。

## 结论与限制

旧版 atomic<shared_ptr> 编译障碍已在本轮复验中消除。上游采用共享快照能力适配，
Web 明确禁用后台线程池与动态库加载，采用单线程静态平台，不依赖 libuv。
本轮未运行真实浏览器事件循环测试，也没有完成 Gneiss Web 资产 I/O、协作输入宿主或
整体 Web 构建。现有 Gneiss 资源开关和原生平台限制尚在；下一步应按
[收敛计划](../plans/PLAN-051-caors-convergence.md)分离平台装配，不能直接宣称双路径已删除。
