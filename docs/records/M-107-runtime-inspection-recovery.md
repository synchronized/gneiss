# M-107：Runtime 检查流控与恢复实施记录

## 当前结果

M-107 第一阶段已建立显式恢复闭环。Editor 检测到增量序号缺口或镜像失效后，只发送一次
`inspection_resync` 请求；Runtime 在主线程收到请求后生成新的完整快照，成功入队后才清除重同步
意图。若完整快照因发送队列暂满而未入队，Runtime 会在下一采样周期继续尝试。

场景检查消息在 Transport 待写数量达到容量的四分之三时停止入队，为心跳、暂停、恢复和停止等控制
消息保留空间。统计快照仍是可丢弃的低优先级数据，临时过载不会导致 Runtime 退出。

第二阶段增加了有界分片事务。编码器按 64 KiB 单帧上限拆分逻辑快照，单次最多产生 128 个分片；
Runtime 会话在自身有界队列中保留尚未送入 Transport 的分片，并在每次主线程泵送时继续排空。
Editor 支持乱序接收和重复分片，但仅在同一会话、同一序号的全部分片到齐并通过整图校验后原子提交，
因此界面不会观察到半个场景。

## 已验证边界

- `inspection_resync` 可经通用 IPC 协议往返，并由 Runtime 会话转换为主线程动作；
- 重复失效增量不会让 Editor 持续发送重同步请求，完整快照应用成功后允许下一次恢复请求；
- 大逻辑快照可拆为多个协议帧，分片支持乱序与重复，未完成事务不改变当前镜像；
- 既有握手、心跳、暂停、恢复、停止与真实 Editor–Runtime 进程测试保持通过。

## 剩余工作

第三阶段为 Editor 增加独立的 256 帧有界检查输入队列，每次 UI 更新最多应用 8 帧。一次 Transport
轮询中的控制、心跳、状态与日志消息会先处理，检查消息随后按预算消费。输入队列溢出时保留最后
可见镜像、丢弃未完成事务并请求全量同步，避免无界内存增长。

真实进程测试新增连续两次 Play/Stop，验证新会话不会复用旧镜像身份；既有 Transport 有界队列、
握手超时、心跳超时、断线和强制终止测试共同覆盖故障边界。M-108 将完成示例行为与跨平台验收。
