# 候选纹理异步上传接入

日期：2026-10-22。对应[渐进加载计划](../plans/PLAN-051-progressive-render-assets.md) S1。
本批修改生产上传路径，不表示首次占位和场景渐进激活已完成。

## 实现

- `threaded_render_executor` 增加显式 resumable 命令策略：NOT_READY 保留相同序号并排到队尾，
  后续帧和命令可先执行；终态才产生一次回执。没有其他工作时以 1 ms 有限等待限制轮询频率。
  默认 once 策略保持原行为，NOT_READY 仍是终态结果。flush/stop 排空可恢复工作，
  不强制丢弃尚未完成的上传；回调必须自行保存进度并最终结束。
- `granit_render_service::prepare_textures` 使用已有 Granit 异步上传接口，保存当前纹理镜像、
  CPU 引用、操作句柄与批内位置。后续推进查询句柄，不重复提交；成功后才加入准备镜像表。
- 视图创建放在上传提交前，避免提交后创建视图失败导致额外在途清理分支。
  提交日志为 submitted，操作成功终态才记录 ready；保留原日志内容验收。
- 旧 CPU 数据和旧 GPU 镜像在候选等待阶段继续可用；上层现有发布流程仍在成功回执后执行。
  并未提前发布 CPU 内容，也没有放宽无效 RID 检查。

没有新增线程池、没有修改 Granit；复用现有渲染线程和上传批次。
异步操作持有上传数据与目标的后端记录，Granit 的句柄销毁契约保证在途工作安全排空。
Gneiss 同时持有待完成镜像，正常完成后释放操作句柄。

## 适用边界

可恢复策略明确允许后续任务越过当前命令，不能用于必须严格 FIFO 的命令。
当前纹理服务只允许单个在途批次，丢弃命令在对应完成后发起；初始化先 flush，
关闭也在排空后执行 GPU 清理，保持现有调用边界。
命令 execution_ms 统计多次回调的执行时间之和，不包含让出期间等待，不能解释为 GPU 总耗时。

本轮只改候选纹理上传。Mesh 上传、默认纹理创建、同步 GPU 镜像恢复仍可使用同步路径。
CPU 转码、暂存复制和资源创建本身也有耗时，不承诺每次回调具备硬时限。
首次占位、单资产独立发布及普通场景移除 fixed_version 等仍待后续实施。

## 验证

- Windows Clang Debug 全量构建通过，警告视为错误配置未改变。
- 全量 CTest 201/201 通过，55.79 秒，包括真实资产像素、Cooked Lantern、主循环响应、
  场景及编辑器流程。
- 新执行器测试以帧回调解除模拟上传等待，证明等待命令不阻塞后续帧；成功/失败各产生一次
  终态、序号保持、任务引用保活至结束。另测默认 once 的 NOT_READY 不被重新执行。
  最后补充测试后定向重跑执行器测试通过。
- 首次定向测试因缺少异步成功后的 ready 日志失败；补充真实完成日志后完整测试通过，
  未放宽或删除原 Cooked 纹理断言。
- 格式与 diff 空白检查通过。clang-tidy 执行器检查仍报告复杂度、异常边界、锁写法等告警；
  本轮没有关闭检查或批量改写无关代码，不宣称静态检查零告警。

未验证 Linux/macOS、其他 GPU 后端及 Web 渲染；没有同条件前后性能对比。
测试证明当前路径工作和调度可让出，不证明每种设备的上传延迟改善幅度。
