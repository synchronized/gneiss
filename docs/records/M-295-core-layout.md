# M-295：Core 源码布局与依赖边界

日期：2026-10-05。按 ADR-054 迁移基础层，保留公共 SDK 路径与唯一运行时状态。

## 迁移范围

原 Core 的结果、版本、RID、Service 注册、SHA-256 与任务调度源码迁至 `src/engine/core/`；
Reflection 迁至其中的 `reflection/`，通用日志文本校验迁至 `log/`。这组内部头统一使用 `.hpp`。
同步更新 Engine、工具、测试、独立浏览器宿主和边界检查中的引用。

日志投递器使用 Application 句柄与回调协议，暂留 `src/log/`，不随通用日志直接放入 Core。
后续先分离通用事件投递与 Application 协议适配，再调整归属；当前不声称日志边界全部完成。

Core 的包含检查拒绝平台、功能、应用层实现与 Application 协议头，反例验证旧路径、目标路径
和协议头均被拒绝。该检查限于约定的直接包含形式，不代表完整依赖图。

本轮不改变调度策略、线程与取消语义、反射注册和 RID 校验，也不新增公共 ABI 或安装目标。

## 验证

共享与静态全量构建通过。共享全量 CTest 首轮 173/174 通过（205.00 秒），唯一失败为灯笼
Editor—Runtime 工作流第二次启动等待进度超时；当时日志仍处于场景源版本复验。单独复现通过，
确认测试把主循环 running 当成了场景就绪，相关等待条件单独修复，不改变引擎实现。
静态受影响回归 20/20 通过（14.79 秒），覆盖任务、日志、反射、RID、注册表、ABI、头文件、
源版本与安装消费者。

独立 Emscripten 无线程宿主重建通过，真实无头 Chrome 输出 `GNEISS_TASK_WEB_PASS`；
只证明最小任务调度宿主可用，不代表完整引擎 Web 支持。文档链接与差异检查通过。
本轮未运行远端 Actions、Linux/macOS 或发布矩阵。

## 工作流等待条件修复

第二次启动仍使用原有 5 秒启动等待，但要求同时观察 running 与场景 applied，随后再验证
游戏进度、编辑状态清理和正常停止；保留 3 秒进度等待和 20 秒测试总超时。失败诊断增加场景阶段。
没有删除原有断言或改变 Runtime 加载行为。

修复后共享工作流连续 3 次通过（合计 25.94 秒）。其余 173 项沿用同一迁移候选的通过结果，
未因仅修改这一测试而重复全量矩阵。静态配置不提供此动态游戏模块工作流测试，未声称覆盖。
