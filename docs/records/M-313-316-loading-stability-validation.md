# M-313～M-316：加载响应性与生命周期验收

## 状态

2026-10-07，首载重复矩阵 12/12、完整场景生命周期矩阵 18/18 通过。
平台与实际发布状态以 [M-317](M-317-0.49.0-release-validation.md) 为准。
输入、环境、基线和冻结门槛以 [M-312](M-312-loading-stability-baseline.md) 为准。

## 已定位的问题

1. 整批资产准备和最终来源复验没有让出执行的边界。改为资产自有状态与复验游标，
   复用既有执行器和取消语义，嵌套版本包装共享一次来源摘要扫描。
2. 每个状态转换单独等待宿主帧造成吞吐退化。初次分步版本日常 cooperative 加载
   68.27 秒、最长主循环间隔 63.43 ms；响应性改善，但超过约 47.82 秒的吞吐线。
3. 小操作合并后，日常加载 54.34 秒、最大间隔 76.94 ms，仍未通过吞吐线。
   完整场景 266.57 秒，但最大间隔 3,260.96 ms；复验单步最大 3,194.64 ms，
   文件打开最大 2.74 ms、单次 64 KiB 读取最大 3,023.55 ms、哈希最大 9.50 ms。
   由此确认仍存在同步系统读取阻塞，不能归因于哈希后宣称切片已完成。
4. Windows 来源新增可轮询 OVERLAPPED 请求；请求拥有缓冲与文件对象，等待时返回宿主，
   同步入口保留同步读取。实现决策与平台回退边界见 [ADR-057](../decisions/ADR-057-incremental-asset-preparation.md)。
   首个日常样本 53.82 秒、最大间隔 87.72 ms，吞吐仍未通过，继续调整批量并复测。
   同轮完整样本 285.81 秒，最大间隔 170.45 ms、复验阶段最大 97.08 ms；单次打开/读取调用
   最大分别为 3.06/9.53 ms。可轮询路径的读取计时是发起/查询调用耗时，不是完整磁盘请求延迟。
5. 读取批量调整后日常样本仍为 51.32 秒；增加当前批次短 Mesh 的有界预读后，日常样本降至
   42.71 秒、最大间隔 95.72 ms，首次同时达到吞吐和响应门槛，仍需最终重复矩阵。
   同实现完整样本为 238.95 秒、最大间隔 187.25 ms、P95 79.57 ms；候选和上传峰值与基线一致。

原始探索输出位于 build/0.49-trial；[探索数据归档](artifacts/0.49-exploratory-loading.json)
保留测量 JSON 与图像摘要，包括未达标样本。探索代码经历多次修改，不能混为同一候选的重复样本。
未裁剪场景或提高候选上限，也未调整冻结门槛。

## 生命周期复现入口

`scripts/performance/measure_scene_lifecycle.py` 顺序启动测量进程并按冻结门槛判断，
默认覆盖 thread/cooperative 的连续切换、五个取消阶段、失败重试、窗口操作与关闭。
输出目录必须不存在；失败保留 JSON、日志与图像，不会继续运行或混入旧样本。
例如按[构建指南](../guides/building.md)启用 Granit 运行时及图形回归目标、完成 Windows Release 构建后：

```powershell
python -X utf8 -B scripts/performance/measure_scene_lifecycle.py `
  build/windows-clang-release/bin/gneiss_scene_load_baseline.exe `
  D:/sunday/workspace/asset-cache/intel-sponza/0.44-full-cooked `
  --output build/0.49-lifecycle-reproduction
```

可通过 `--modes thread`、`--scenarios cancel-gpu` 缩小复验范围；
`--image-sha256` 指定同一输入和视角的基线摘要。Debug 使用 `--functional-only`，
其结果只证明功能，不能计为 Release 性能门槛通过。测量期间不并行构建或其他 GPU 测试。

### 功能重试计时的解释

预载与失败后的功能重试使用 `preload_scene`，逐帧调用 `app.run(1)`；
Application 的既有短程运行契约会在返回前等待已提交帧回收。
因此 `retry_ms` 包含串行渲染等待，cooperative 只能在这些等待之间推进准备步骤，
不能将它与主循环内持续推进的首载吞吐样本混比。功能重试继续使用原 15 分钟单请求期限，
不修改冻结的首载中位数、主循环响应或取消门槛。
