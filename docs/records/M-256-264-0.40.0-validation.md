# M-256～M-264：0.40.0 统一调度与异步纹理验收

## 状态

2026-09-25，发布验收通过。范围见 [VER-040](../plans/VER-040-0.40.0-cooperative-scheduling.md)，
当前接口及限制以[调度指南](../guides/task-scheduling.md)为准。

## 正确性与生命周期

- 协作模式复用原有任务状态与句柄；验证延迟、依赖、容量、公平性、取消、独立作用域、异常、
  零预算、所属线程及递归驱动拒绝。原线程池 1/2/4 工作者回归保留。
- Editor 导入和作者资产服务在两种模式下执行既有事务、保存竞态、暂停及关闭检查。
- Runtime 纹理服务在两种模式下覆盖首次失败清理、缓存复用、热更新保留 RID、旧帧快照、
  缺失源、批次失败保留旧资源、GPU 失败、提交许可后取消、同步替换冲突及卸载后拒绝迟到结果。
- Application 测试验证跨 DLL 借用宿主执行器及销毁顺序，不在引擎中建立另一套调度状态。
- Editor/Runtime 真实进程联动验证纯纹理更新、损坏 PNG 失败和恢复重试；只在 GPU 上传确认并
  发布候选后返回 applied。Runtime 保序执行，Editor 超额队列可观察地拒绝。
- 连续 resize 测量发现旧帧尺寸与实际交换链尺寸可能不同，导致 pipeline 参数错误；修复后
  取消过期帧并在后续帧重建。被跳过的帧不计为已呈现帧。

## 真实纹理与窗口测量

Windows、Intel Core i5-8600K、Intel UHD 630（驱动 31.0.101.2140）。测试工具生成原创 PNG：
初始 8×8 蓝色纹理更新为 4096×4096 橙色纹理，解码候选为 64 MiB。每次运行移动相机、执行
九次 resize、一次最小化恢复；同步基线、线程池和协作模式各重复三次，Debug/Release 分开。
生成工具及数据采用项目 MIT 许可。

```powershell
python tools/performance/measure_texture_loading.py build/windows-clang-debug/bin/gneiss_texture_load_window_benchmark.exe --output build/0.40-texture-debug-final --samples 3
python tools/performance/measure_texture_loading.py build/windows-clang-release/bin/gneiss_texture_load_window_benchmark.exe --output build/0.40-texture-release --samples 3
```

下表为三次观测的范围；主线程指标是负载开始后的最大 update 间隔，呈现指标包含刻意最小化、
resize 和 GPU 上传，不等同于稳态 FPS。上传列为渲染命令执行耗时；同步基线未单独采集此项。

18 次均完成更新与窗口恢复。完整汇总保存在 [Debug JSON](artifacts/0.40-texture-debug.json)
和 [Release JSON](artifacts/0.40-texture-release.json)，包含排队、提交及帧间隔分位数。
原始 CSV 与逐次日志保留在上述本地输出目录。

线程池减少 CPU 准备造成的主线程停顿，但上传仍占用渲染线程，呈现间隔没有一致改善。
协作模式无法抢占单次解码；2 ms 预算只在任务之间检查。异步准备复查源字节，会增加读取成本。
该样本不代表任意纹理格式、复杂场景或硬实时上限。

Chrome 153.0.8010.50。最小调度宿主通过 HTTP 在真实无头 Chrome 执行 Wasm，输出

无线程构建明确拒绝 thread_pool，没有 pthread 链接要求。完整引擎 Web 和 Emscripten pthreads
均未验证；本结果不能外推到 Granit、libuv、Editor 或 Runtime 的浏览器兼容性。

## 保留限制

公共 SDK 尚未提供异步加载 API；初始场景和混合资产批次仍同步。限额是候选与请求预算，
不代表整个进程的内存上限。原生文件复查不提供跨进程原子快照。跨屏真实 DPI 人工验收和
任意硬件性能保证不属于本版新增结论。原生窗口测试验证实际上传、呈现和恢复；此环境的 GDI
截图未取得 Vulkan 画面，未以空白截图证明颜色正确，逐像素显示比对未完成。
