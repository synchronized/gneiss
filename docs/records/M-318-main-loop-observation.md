# M-318：后台加载主循环观测

## 状态

2026-10-07，测试宿主与引擎内分段诊断、实际 Runtime 12 项重复基线完成；长间隔归因仍在进行。
范围见 [VER-050](../plans/VER-050-0.50.0-main-loop-latency.md)。尚未修改生产加载算法或等待策略；CPU 与吞吐门槛已在 DEV-050 冻结，交互响应门槛待补。

## 旧指标审计

0.49 的 event_interval 在测量宿主相邻更新回调中采样，不是 GPU 帧间隔。
宿主每轮调用 poll_scene_load 后主动 sleep_for(1 ms)，实际唤醒可能更晚。
Application 在回调后处理 render_frame，在下轮回调前处理窗口事件；这些都包含在回调间隔中。
因此旧阶段标签只能关联加载状态，不能直接证明主线程在等待后台工作。

## 新观测

保留原间隔字段，补充样本数、P50/P99 和阈值超限分布；可选 trace 保存逐轮 CSV。
分别计时回调总耗时、协作执行器、场景推进和主动睡眠；回调外残余单列，尚未拆成渲染与事件耗时。
嵌套时间不重复求和，最后未闭合的残余使用 -1；系统调度导致的暂停仍包含在墙钟时间中。
详细模式默认关闭，只在测量后写出，未调整线程数、等待期限或资产规模。
命令与字段边界见[构建指南](../guides/building.md)。

## 首轮观测结果

| 样本 | 最大旧间隔（ms） | 场景推进最大（ms） | 实际睡眠最大（ms） | 回调外最大（ms） |
| --- | ---: | ---: | ---: | ---: |
| 日常 / trace 关闭 | 20.44 | 未采样 | 未采样 | 未采样 |
| 日常 / trace 开启 | 40.10 | 4.02 | 40.07 | 1.87 |
| 完整 / trace 开启 | 73.22 | 31.98 | 71.19 | 36.41 |

表中各列为独立最大值，不能相加。日常最慢闭合样本的场景推进仅 0.0015 ms，
睡眠 40.0706 ms。完整最慢闭合样本为回调 36.8170 ms（其中睡眠 36.7870 ms），
回调外 36.4093 ms；另一次回调 71.2350 ms，其中睡眠 71.1939 ms。
两组实际睡眠中位数均约 15.5 ms，不能把请求的 1 ms 当作实际让出时间。

这是定位线索，不证明 Windows 唤醒延迟的具体原因，也不能归因到后台哈希、锁或 GPU。
Runtime 更新入口没有测量宿主这处固定睡眠，应另做实际 Runtime 对照。
本轮未复现历史 129 ms；场景推进约 32 ms 和回调外约 36 ms 的峰值仍需引擎细分及线程栈解释。
日常只做了一组开关顺序对照，受缓存和系统噪声影响，不作为插桩开销上限或性能改善结论。
未降低等待、修改生产调度或发布新版本。

## 引擎内分段与实际 Runtime 对照

实现提交 `3090688` 增加默认关闭的 GNEISS_LOOP_TRACE，仅观测，不改变加载和调度策略。
固定容量保留最长 128 个循环及全量阶段最大值/超限次数；记录事件、更新、渲染、
场景推进、候选接收/发布、上传回执/提交、收尾及帧准备等，run 结束后写出。
嵌套计时、循环 gap 和多次 run 的含义见构建指南，不能用最长样本推算 P95。

[本轮证据](artifacts/0.50-engine-loop-observation.json) 保存二进制摘要、命令、原始 CSV 摘要、
最长样本和对齐结果；原始文件位于 build/0.50-engine-observation/。沿用 0.49 的设备与输入，
没有并行构建或其他 GPU 测试，不清理系统缓存。此次为单次诊断探索，不作为冻结门槛。

| 加载路径 | 引擎循环最大（ms） | 场景推进最大（ms） | 事件处理最大（ms） | 渲染阶段最大（ms） |
| --- | ---: | ---: | ---: | ---: |
| 日常 / 测量宿主 thread | 68.99 | 1.55 | 0.76 | 0.67 |
| 完整 / 测量宿主 thread | 110.95 | 15.82 | 34.47 | 6.07 |
| 完整 / 实际 Runtime thread | 33.45 | 28.08 | 33.43 | 7.18 |

各列为独立最大值。测量宿主的最长完整场景循环与原回调 CSV 对齐后，
110.93 ms 更新回调中 sleep_for(1 ms) 实际占 110.91 ms，场景推进仅约 0.0014 ms。
这证明本轮该长间隔主要发生在宿主主动等待期间，不证明历史 129 ms 的具体原因。

Runtime 使用同一完整资产的工程内硬链接工程，--smoke 日志确认场景激活与正常退出；
总进程耗时 225.18 秒。循环最长样本主要在事件处理（33.43 ms），
全量循环统计中超过 16.7 ms 共 25 次、超过 33.3 ms 共 1 次、超过 50/100 ms 为零。
这是单次原生启动加载，不能外推到重复切换、窗口交互、其他设备或 Editor。
测量宿主两组仍为 553 节点、505 资源，完整图像与 0.49 一致；Runtime smoke 没有额外捕获图像。

Runtime 记录 38,919,915 次主循环、4,801 个提交/执行帧、38,915,114 次跳过帧构造。
源码显示队列繁忙时跳过构造后继续轮询；次数说明存在大量重复轮询，不能代替 CPU 占用率，
也不能直接证明它造成事件处理峰值。后续须测量 CPU 时间、唤醒/任务到达与输入响应，
再决定是否需要帧节奏或事件等待，不直接插入 sleep 或调整线程数。

| 规模 / 诊断 | 次数 | 进程耗时中位数（s） | 主线程 CPU 中位数（s） | 单核心占用比中位数 | 进程 CPU 中位数（s） |

不是严格的插桩开销上限。CPU 与吞吐验收采用关闭诊断的数据，阶段定位另用开启诊断的数据。

### 已确认问题与未解释样本

主线程几乎持续占用一个核心。结合 render_frame 在队列繁忙时跳过构造并立刻继续主循环，
以及数千万次循环/跳过构造计数，确认有大量重复轮询。不能据此证明所有时间均消耗于某一个函数，
也不能直接说明忙轮询导致了偶发长间隔；M-319 将消除重复轮询列为首个可验证优化方向。

| 规模 | 三次诊断循环最大值（ms） | 超过 50 ms 次数合计 | 超过 100 ms 次数合计 |
| --- | --- | ---: | ---: |
| 日常 | 21.7650 / 7.7931 / 65.6697 | 1 | 0 |
| 完整 | 41.7287 / 66.0063 / 61.6913 | 3 | 0 |

完整第一次最长循环 41.7287 ms，其中纹理推进 41.7014 ms，任务接收 0.0103 ms、
提交 3.0110 ms；其余已计时子项为零，仍有约 38.68 ms 未被子项解释。
完整第二次最长循环 66.0063 ms，其中渲染 65.7195 ms，内部子项未覆盖大部分耗时。
另一循环事件阶段 65.2342 ms，不能仅凭这一总时间认定窗口泵执行了同样长的 CPU 工作。
这些残余包含未细分代码、计时边界和可能的线程失去调度时间，未获得内核栈前不归因于锁或驱动。

本轮 Runtime 没有获取图像或注入窗口交互，不能代替像素、输入延迟、取消/清理与窗口生命周期验收。
四项代码回归已在该实现构建后通过；重复性能期间没有再运行构建与 GPU 测试。
M-318 的重复基线已完成，线程栈证据仍缺；M-319 只冻结 CPU/吞吐等已可测门槛，
尚未完成响应夹具、完整归因或进入 M-320 生产修复。上游接口建议见
